# 飞书来源

更新：2026-11-13，`0.15.0-alpha.5`。飞书是项目的可选来源：名单里的人在配置好的群里 @ 机器人，或在已列出的私聊里发消息，进入现有准入与建单评估；@ 本身不强制建单。执行仍使用已配置的 Codex 或 DSH。确认、提问和结果回到原来的话题。补收与健康读取的边界见[恢复合同](feishu-history-recovery.md)。

2026-11-06 19:24 用本机 `lark-cli` 在私有群「js-superagent 验收」做了一次真实收发：没有 @ 机器人时工单数为 0；@ 之后开出 1 张工单并完成；原话题里能看到接单回复和结果「验收通过 mw4vzm7r」；同一话题再补一句后工单数仍是 1。2026-11-07 复查发现，当时应用没有 `im:message.group_msg`，那句补充其实没有到达，工单数不变不能说明它被收下。官方 Node SDK 长连接没有参加这次验收，实时事件和回复都经 `lark-cli` 进入同一套来源与工单路径。没有第二个飞书账号，名单外用户没有实测。

## 配置

在项目配置里增加 `feishu`。密钥只保留环境变量名或文件路径，不写进配置内容。后台服务必须使用 `appSecretPath`，文件属于当前用户且不给其他用户读权限。

```json
{
  "feishu": {
    "enabled": true,
    "appId": "cli_example",
    "appSecretPath": "/absolute/path/to/feishu-app-secret",
    "botOpenId": "ou_bot",
    "tenantKey": "tenant-key",
    "chats": [
      { "chatId": "oc_group", "type": "group", "mode": "mentions" }
    ]
  }
}
```

`mode` 为 `mentions` 时只接收 @ 机器人的新消息，以及已经进入话题的回复。`all` 还会接收该会话里的其他消息，是否开工仍由策略决定。`type` 可以是 `group`、`p2p` 或 `topic_group`。

策略里为每个要接单的会话加一行，`source` 为 `feishu`，`scope` 同时写 `tenantKey` 和 `chatId`，`actors` 写允许开工的用户 `open_id`：

```json
{
  "policy": {
    "mode": "off",
    "rules": [],
    "sourceRows": [
      {
        "id": "group",
        "source": "feishu",
        "scope": { "tenantKey": "tenant-key", "chatId": "oc_group" },
        "actors": ["ou_alice"],
        "bots": [],
        "admission": {}
      }
    ]
  }
}
```

没有对应策略行的会话可以连上，但消息不会变成工单。`setup check` 会指出缺行的会话。

## 运行

`serve` 和已安装的后台会在主循环上注册来源并打开 WebSocket。历史补收约每 60 秒一次；第一次只记下当前位置，不回放更早的消息。实时消息在 Worker 执行期间仍然接收。连接断开时，待发回复留在队列里，重连后继续发送。

需要另行安装 `@larksuiteoapi/node-sdk`。本包不把它列为依赖。应用需要机器人、收发消息权限，以及长连接事件 `im.message.receive_v1`。

只开「接收群聊中 @ 机器人消息」时，飞书只推送 @ 机器人的群消息：话题里不带 @ 的补充不会到达，历史补收也会因 230027 失败。要接收话题内补充，给应用身份开通 `im:message.group_msg`（获取群组中所有消息）并发布新版本。开通后飞书会推送群里的所有消息，`mentions` 模式仍只处理 @ 机器人的新消息和已有话题里的回复。

`0.15.0-alpha.5` 补收群主消息、配置群内发现的活跃话题，以及宿主仍需跟踪的已订阅话题。群历史与话题历史分别分页；飞书话题接口不支持时间筛选，适配器在本地核对固定扫描窗口。降序读取先暂存完整窗口，再按时间顺序接收；超过 500 条或 1 MiB 时自动改为正序重扫同一窗口，避免补充先于原请求进入领域处理。分页预算用尽后续读，失败保留对应进度，其他容器继续。实时与历史使用相同消息 ID 去重，旧工单的话题身份保持不变，不增加用户配置项。

升级保留原群游标；已有话题依据已接收原请求的平台消息时间补收，不能用延迟处理的时间或将游标重置到现在来跳过断线期间的补充。首次接入新群仍以当前时间建立准入基线；独立的最近 14 天根消息发现只建立话题映射，不回放基线前的旧请求。补齐权限前先检查积压：未接收的旧 @ 可能重新进入正常评估；已经接收过的消息只去重，不重建工单。配置群之外的消息仍不读取。

部署和恢复分别验证应用身份的群历史、话题历史和实时连接。用户身份读取成功不能代替机器人权限。历史错误保留平台错误码与群/话题定位；一个私聊成功不代表所有群已恢复。公开 `businessHealth()` 从本版本起只读后台保存的健康观察；CLI、管理页和心跳查询不更新失败计数或解决告警。没有观察或观察过期时不能报告已经验证健康。旧版本的该方法会写状态，排障时使用已有服务心跳。

群聊里 @ 机器人时，飞书给出的点名身份可能是应用 ID（`cli_…`），也可能是机器人 `open_id`（`ou_…`），两种都按点名处理。Worker 回答飞书提问时，回复发回提问所在的话题。

改飞书配置前先停止正在运行的后台。

## 操作者私信

2026-11-09 起（未发布、未部署）可以在 `feishu` 里加 `"operator": { "openId": "ou_…" }`，把操作者的飞书私信作为本项目操作者对话的入口。设计见[操作者对话与飞书私信](operator-channel-plan.md)。

- 操作者发给机器人的单聊消息不开工单，作为操作者项目消息交给协调者；协调者的回复写回这条消息。其他人的单聊消息不处理。私信会话不用列进 `chats`，也不需要策略行。
- 操作者工单（本地提交的工单，以及协调者根据操作者消息新开的工单）停下提问时，宿主把问题私信给操作者：带结构化选项的发卡片，其余发文字。卡片提交由宿主核对后直接作为回答；之后卡片显示已提交、已在别处回答、已失效或工单已结束。
- 操作者工单完成、失败或受阻时，协调者决定是否发一条短通知。需要配置协调者执行端并开启持续协调；没有协调者时私信文字只排队，提问和卡片照常工作。
- 未列入 `chats` 的操作者私信只经实时连接接收；显式列入的私聊按会话配置补收历史。卡片回调没有补收，服务不在线时点击会显示失败，稍后重新提交即可。

应用还需要：以机器人身份发消息和更新卡片的权限、读取单聊消息的权限；在「事件与回调 → 回调配置」里选长连接并添加 `card.action.trigger`；可用范围包含操作者。

## 不做

成员名单同步、看图研判、未列出的其他群、给 Worker 注入飞书环境变量，以及一个机器人分发到多个项目。仓库里的修改、PR、审阅和 CI 仍然只走 GitHub。

## 真实验收

准备一个测试群和一名名单内用户后：

1. @ 机器人提出一个小任务，确认原话题收到接单回复。
2. 等工单完成后，确认结果回到同一话题且只出现一次。
3. 在同一话题追加一句不带 @ 的补充，确认它进入原工单（工单消息里能看到这句），且没有新开第二张工单。只核对工单数不够：补充没到达时工单数同样不变。
4. 用名单外的账号 @ 机器人，确认没有新工单。
5. 记录原服务状态，停服后发送测试 @ 和原话题内的非 @ 补充，再恢复原服务；核对历史接收路径、原消息 ID、工单输入与原话题回复。重启后收到了消息不一定证明历史补收，必须区分实时重放与历史读取。
6. 在配置群内最近发现的未订阅话题中验证首次 @ 的离线补收；普通非 @ 内容不得因此成为新工单。继续等待实时/历史重叠经过测试区间，确认没有重复工单、输入或结果通知。
