# 第二阶段：独立存储与运行时迁移

本文保留第二阶段完成时的实现与验收记录。后续真实执行器、原生会话与进程监督的当前状态见[第三阶段记录](codex-driver.md)。

## 范围与来源

本阶段把原有 CLI 与 `createProjectAgent()` 接到已经提取的领域 Engine。新增的 SQLite 适配、动作队列、本地 Outbox、旧数据转换和运行时组装参考上游的职责划分独立编写，没有新增复制上游应用层代码。原 `src/core/`、两个领域测试及其 SHA-256 来源清单保持不变。

[第一阶段提取记录](core-extraction.md)保留当时的完成状态；从本阶段起，CLI/SDK 已通过 Engine 操作领域记录，不再是两个互不接通的运行时。独立 `/core` API 仍可单独使用。

## 数据布局

项目配置 `config.json`（当时位于 `.js-superagent/`，现位于项目状态目录）的格式保持 `schemaVersion: 1`。SQLite `state.sqlite` 使用数据库版本 2，二者的版本号分别管理。

| 数据 | 用途 |
|---|---|
| `tickets` | 原 v1 工单原样保留，作为迁移来源和历史档案 |
| `domain_triggers`、`domain_dispositions` | 事件与事件去向 |
| `domain_threads`、`domain_decisions` | 话题订阅、决策和授权依据 |
| `domain_tickets` | 当前领域工单、授权、派工、输入和报告状态 |
| `kv` | 公开 ID 映射、兼容历史、项目执行所有权、迁移标记等 |
| `effects` | 待执行动作、代次、领取身份、尝试次数、错误和到期时间 |
| `receipts` | 本地消息及其 `pending`、`sent`、`dropped` 状态 |

公开工单 ID、原始请求、消息和执行报告继续通过旧 API 读取。领域工单的派工与状态由 `getDomainTicket(publicId)` 检查。取消后重试可对应新的领域工单，但公开 ID 不变；已停止的领域记录仍保留。

## v1 升级流程

1. 识别数据库版本，拒绝未知的更新版本。对 v1 中的运行中记录先检查执行所有者；活进程或不能确认的所有者在备份和改表之前被拒绝，数据库保持 v1，旧 CLI 仍可打开并处理原任务。
2. v1 数据库升级前，通过 SQLite `VACUUM INTO` 一致性导出到唯一临时文件，检查快照完整性及 v1 版本后，原子发布为 `state.sqlite.v1-backup`。已有同名备份不覆盖，但会只读核验；坏备份会明确阻止升级。异常时清理本次临时文件，避免把半成品当作可恢复备份。
3. 建立 v2 表结构，保留原 `tickets`。
4. 校验全部旧记录，包括项目归属、状态、时间、消息和报告。某条不合法时不导入任何新工单或待执行动作。
5. 在同一事务中建立领域记录、兼容元数据和必要的启动动作，再保存导入完成标记。重复初始化不重复导入。

表结构升级和工单导入是两个步骤。若导入失败，v2 空表可能已经存在，但旧 `tickets` 及备份保留，导入事务会回滚；修复来源问题后可再次初始化。迁移不会调用模型或执行项目任务。

## 旧状态的转换

| 旧状态 | 导入结果 |
|---|---|
| `queued` | 创建待启动派工和持久化启动动作 |
| `waiting` | 保留等待状态与问题，等待本地回复 |
| `completed` | 保留结束记录，不重新执行 |
| `failed` / `interrupted` | 保留失败或中断视图，等待显式重试 |
| `cancelled` | 记录人为停止；再次重试需要新的领域授权 |
| `running` | 只有确认相同主机的 owner 进程已经退出才导入为中断；活进程或无法确认时拒绝迁移 |

导入的授权和决策明确标记为 `legacy-import`，表示旧本地委托的历史转换，不伪装为一次新模型研判。原消息和报告不丢弃；旧数据库未记录的原生会话读取事实不会凭空补造。

## 执行与停止

`runNext()` 处理持久队列，最多运行一轮 Driver；`start({ intervalMs: 100 })` 在当前宿主进程持续调度。`stop()` 停止调度、发出取消信号并等待 Driver 退出；随后可以 `close()`。它们是 SDK 生命周期方法，没有创建后台服务，也没有新增 `serve` CLI。

领域更新、元数据和动作在同一同步事务内提交，外部 Handler 随后才执行。队列的代次和领取 token 防止旧尝试删除新排队内容；全项目执行记录保证原目录串行工作。Driver 返回前后按领域工单、派工和运行身份核对，拒绝迟到结果。

同机死进程的遗留执行会标为中断，需要检查外部修改后显式 `retry()`。不确认其他主机、PID 复用或无法读取的进程已停止。运行时停止同样不会自动重复执行被打断的工作。队列是至少一次处理，实际外部动作仍由适配器负责幂等或恢复核查。

## 授权与通知边界

本地操作者由宿主绑定为 `local/operator`，明确提交进入 Engine 的授权与工单流程。当前没有真实语义 Assessor，`scope` 仍是范围文本，没有自动识别“顺便做另一项工作”的能力。远端来源和主动工作政策未开放。

`cancel()` 撤回旧授权；取消后的 `retry()` 新建领域委托并关联旧历史。失败或中断重试则在原授权下建立新的派工。Driver 额外接收 `domainTicket` 和 `assignmentId`，原参数和报告格式保留。

Outbox 只处理本地消息收据，`notifications()` 不会向外部发送消息；不支持的渠道保持等待。本地 `sent` 不能作为远端送达证据。真实模型、工作区隔离、外部渠道和成果验证仍待后续实现。

## 备份恢复注意事项

备份保留升级前的 v1 状态，不包含之后新增的工单、回复或执行结果。恢复前必须停止所有访问该项目状态的运行时和进程，保存当前状态及需要保留的新数据，再由操作者决定手动恢复；不能在数据库仍被打开时覆盖文件。恢复旧备份会丢失备份之后的新状态，本包没有自动回退或自动覆盖命令。

在包目录运行 `npm run check`，验证上游核心校验、类型、领域行为、兼容 API、存储事务、队列、迁移与隔离打包。测试使用协议替身和临时目录，不代表已完成真实模型任务或跨平台生产验收。本轮在 Node.js 24.22.1 上完成：

- 49 项 Node 测试通过，包含原有 CLI/SDK 回归、迁移、队列、存储、真实进程取消和 SIGKILL 后恢复，以及结果落库失败时禁止自动重放。
- 144 项未修改的上游领域测试，在内存仓库和新 SQLite 仓库上分别全部通过。
- 来源校验、类型检查、构建、离线 tarball 安装、JavaScript/TypeScript 消费端、已安装 CLI/SDK 接通 Engine 检查通过；无 DSH/Cordis 依赖。
- 仓库根目录 `npm run check` 通过。

验证使用临时测试项目，没有迁移用户真实工作库、调用真实模型或执行发布。
