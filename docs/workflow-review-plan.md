## 1. 目标与边界

完成后，系统能让 PR 描述随实现更新、执行必要审阅动作、有界处理机器人审阅、识别原生 @mention 委托、恢复未保存草稿，并在 DSH 交付 ready 后继续提供已核验的原生预览。

- 保持独立 npm 包，不依赖 js-agent-runtime；保留 CLI/SDK 工单入口、Codex app-server、DSH SDK、第三方 Harness 注册入口。沿用核心、Store、Effects、Outbox、权限和进程监督，不重造通用工作流引擎。
- 核心提取文件继续保持上游原样。新增记录与行为主要位于应用层、渠道、宿主工具和适配器。
- **W18 继续暂缓**：不自动采用原生 pending 队列、不重发旧输入、不发空消息、不改原生日志、不使用私有唤醒接口。
- **后台保持停止**，生产库不打开或迁移，不安装、启动或切换服务，不升级本机 DSH/Codex。隔离验收进程使用临时目录并在结束时回收。
- 不加入自动合并、fork PR、飞书配置、通用联网／技能平台或集中多项目管理。代码 ready、PR 待审、CI 观察、预览可用是不同事实。
- 上游审阅操作与 bot 三轮上限主要是 prompt/skill 规约；本地为适配器独立性而提供受控动作和持久记录，不声称照搬了上游宿主状态机。
- 本计划不执行实现、远端写入、提交推送、npm 发布或部署；后续按计划实施也不自动包含这些发布动作。

2. 新远端动作须明确配置允许的动作与目标范围。旧 `draft-pr` 配置继续创建草稿；升级不自动请求 reviewer、resolve 线程或转正式 PR。本地交付模式不产生 GitHub 写入。

6. 旧库只读不升级。生产升级和回退仍须单独执行，回退前核对新版本期间的远端动作，不靠恢复旧库撤销 GitHub 已发生动作。
7. 团队自定义提示词不被新默认内容覆盖，沿用默认版本比较与明确采用流程。既有会话普通下一轮按现行规约装配，恢复仍核对原执行快照；未知能力的第三方适配器不收到其未声明支持的工具或原生预览合同。

## 4. W30：PR 描述与审阅操作

### 4.1 同一个 PR 反映最新实现

- 新建与后续交付都生成“当前方案、验证、实际限制”的标题和描述；不把轮次日志、bot run ID 或聊天历史堆进描述。
- 复用已有 PR 后更新内容，先确认仓库、PR 所有权、开放状态、目标 head 和当前授权，再沿用现有锁与交付收据写入。
- 保存上次宿主写入基线。标题被人修改时保留并显示冲突；描述使用明确的受管理段，保留段外人工内容。旧 PR 没有可靠基线时先核对，不直接全量覆盖。
- 写入前重读、比对基线，写入后读回。GitHub 内容更新缺少可靠条件写入时，明确其并发窗口；不能把“先读后写”描述为原子防覆盖。
- PR 描述更新失败不重推已成功的代码，也不丢失交付记录；分别显示代码已推送、描述待同步、PR 待审状态。

### 4.2 三类必要审阅动作

复用现有宿主业务工具与持久 Effects，提供 SDK／CLI／面板可用的同一动作路径。Worker 只能提交结构化意图，不能获得通用 gh 或任意 GraphQL 写入权限。

| 动作 | 条件与行为 |
| --- | --- |
| 转为正式待审 | 仅配置允许且属于当前工单的 PR；ready 报告、已推送 head、代码验证一致，相关待处理要求已结算；配置选定的 CI 有已知阻塞时不自动转待审。读回 `isDraft=false` 才报告成功，不宣称全部 GitHub required checks 已通过 |
| 请求审阅者 | 仅配置允许的用户／团队，核对当前 PR 和 head；不从不可信评论自动扩展名单。已请求或已有覆盖本次意图的审阅时不重复通知；未允许主动请求时可显示建议 |
| 解决审阅线程 | 使用真实 GraphQL thread ID，绑定当前 PR、原评论和对应修复证据；确认修复已推送且验证对应当前 head。只处理已解决的问题，不因模型写了“fixed”就解决所有线程；不实施的建议在原线程简短解释 |

原处回复沿用 Outbox、marker 和 W19 的删除后回退规则。解决线程和回复是两种动作，遵守上游“已修复则静默解决，需要解释才回复”的规约。

每次执行前重验暂停、工单授权、PR 绑定与 head；取消或目标变化使旧意图失效。先持久化意图再请求网络，失败保留原因；结果未知先查询当前 draft、reviewer／review 状态或 thread 状态，不能盲目重发。副作用无法确认则待检查。权限不足显示具体缺项，不切换账号绕过，也不自动修改 App 权限。

### 改动与有限验收

主要位置：`delivery.mjs`、`channels/github.mjs`、`channels/github-app.mjs`、`runtime/agent-tools.mjs`、`runtime/prompt-registry.mjs`、`index.mjs`，及类型、CLI 和详情展示。必要时增加一个专用审阅动作模块，保持入口薄。

一组模拟 GitHub＋临时 Git 的闭环：首次草稿 → 后续修改更新描述 → 请求审阅 → 修复后解决原线程 → 按配置转待审。附带人工改写冲突、head 变化、权限不足及“远端成功但本地丢收据”的关键分支；证明不会重推代码或重复通知。两个内置适配器使用同一宿主动作合同，不各建一套实现。

## 5. W31：机器人审阅收敛

- 默认最多三轮，允许项目设置更严格的上限。预算绑定 repository＋稳定 PR ID＋bot 身份，跨 Worker、重启、工单和会话接续保留；head 变化不清零。
- “一轮”是可核验的同一 bot run／review，不是一条评论。多个行内 finding、编辑版本、轮询／Webhook 重投归入同轮；重复事件不耗新轮数。
- 在准备向 Worker 派发该轮修复前，事务性保留轮次；同轮重试复用原记录，两个 Worker 不能同时抢到第四轮。报告记录已处理、拒绝、未解决等处置，不能依赖模型自己记住次数。
- 无法获得稳定 run 身份时保存 `unknown` 和原始证据，补读可证明的关联；不按时间窗口、正文相似度或每条评论猜一轮。仍无法确定时保留观察并等待明确处理，不把未知当无限免费轮次。
- 达到上限后继续收件和展示，但不因后续 bot run 新建修复、恢复工单或向活跃 Worker 注入新的修复要求；按需读取不授予额外工作。与真人／CI 混合到达时分别处理，不能搭便车绕过上限。
- 人工审阅、真人新要求、CI 不共用 bot 预算。真人可明确批准有限追加轮次，记录来源、数量和政策版本；普通“继续”及 bot 文本不会自动重置预算。
- 旧 PR 优先从可靠已保存处理报告和远端 review/run 身份建立历史；只看到 review 不等于实际处理过。无法还原已处理轮数时标为历史未知，通过一次明确的本地初始化决定可用剩余额度，不伪造零起点。
- 超限不逐条通知人。正常交付报告说明实际未解决问题；严重阻塞沿用现有提问／告警路径，不因此又启动一轮机器人修复。

主要位置：GitHub 标准化／补读、Policy 后的续作门禁、调度／live-input 路径、报告和宿主审阅动作、详情展示及默认团队规约。保持 bot 永远不能成为真人授权者。

一组场景覆盖同轮多评论、重复、三轮后第四轮不唤醒，数据库重开／换 Worker／后续工单不清零；真人与 CI 仍可按原规则处理。补一个未知 run／旧历史的保守分支，不测试大量 bot 产品。

## 6. W32：原生 @mention 明确委托

- 与 `/js-superagent` 并存，共用一个 addressed 解析器；支持正文不同位置对正确部署账号的 mention，保留完整原文和评论版本。
- 目标身份来自认证后的渠道事实（gh 用户或 GitHub App bot），不是从正文、自报名称或任意别名猜测。身份无法核验时 slash 入口保持正常，mention 入口显示配置问题。
- 精确匹配登录名边界、大小写和 bot 身份；代码块、行内代码、引用旧消息等非当前寻址内容不单独形成明确委托。仅有 mention 没有具体请求可进入澄清，不直接执行。
- Issue／PR 正文、Issue／PR 评论、review 与行内评论使用同一识别结果；仍须经过当前账号授权、仓库／对象范围、Policy、已有关联和当前 head 检查。被 mention 不赋予发送者权限。
- 仅寻址事实改变：mention 不自动取消、不扩展原工单范围，也不把不可信 bot 变成人。已有绑定工单的普通跟进继续有效，无须每次 mention。
- 发现复用已有轮询和 Webhook，覆盖尚未绑定工单的新 Issue／PR、评论和行内评论。mention 专用发现启用后，即使普通 receive-all／comments／reviewComments 未开启，也能按明确范围读取或补读匹配消息，不能只改已绑定流的解析器。配置界面说明范围，只把匹配消息交给原准入路径，不隐式开启全部评论接单。首次启用建立游标基线；历史 ignored 事件不自动重评，排队 Webhook selector 仍按原版本去重规则处理。
- 不要求 GitHub App 使用个人通知接口。若 gh 通知发现后续另行提供，它只影响发现，不另造授权规则；本轮不以新增 notifications 通道作为完成前提。

主要位置：`github-intake.mjs`、`github-pull-intake.mjs`、`channels/github*.mjs`、`github-webhook-inbox.mjs`、`runtime/repository-source.mjs`、Policy 配置及页面。

一组宿主场景在“未绑定对象、普通发现流关闭、mention 开启”条件下覆盖新 Issue／PR 正文及行内 mention → 原准入 → 工单 → 原处回复，并与轮询／Webhook 重复观察合并。少量反向分支覆盖引用 mention、错误账号、未授权人、bot、编辑和首次启用；不创建真实 GitHub 对象。

## 7. W33：草稿恢复与三方合并

- 用同一轻量草稿模块保存 `{base,value,revision,formatVersion,updatedAt}`；复用现有协调消息草稿机制，覆盖协调配置、Worker、来源、调度、恢复、交付和提示词编辑块。
- 使用 `sessionStorage` 保证同标签页刷新可恢复；key 包含稳定项目／实例身份和编辑块，回复按 ticket 区分，会话操作按 ticket＋session 区分。端口复用或切换项目不能读到其他项目草稿；不承诺浏览器关闭后的持久保存。
- 设置按字段做三方合并：只有本地变化保留本地、只有服务端变化采用服务端、两侧相同直接合并、同字段不同值列出冲突。数组和自由文本先作为原子字段；不引入协同编辑或文本自动拼接框架。
- 合并结果仍是未保存草稿，需要现有显式保存动作。提示词“默认版本更新”比较与“并发保存”比较各自保留，不能互相覆盖。
- 保存请求期间继续编辑时，成功响应只清除已发送版本，保留更新的草稿。失败、409、重载、旧格式和存储不可用都有明确行为；不能因恢复草稿自动发送回复或执行会话替换。
- 只保存允许的非秘密字段；认证 token、CSRF、App 私钥等不进入草稿对象。存储容量／权限失败退回页面内存并提示草稿未持久保存，不覆盖服务端。

主要位置：`src/ui/app.js` 及一个小型草稿模块；需要时更新静态资源服务清单。服务端继续使用现有 expectedRevision，不新增数据库编辑协议。

一组状态转换检查覆盖不同字段合并与同字段冲突；一次本地隔离页面验收覆盖编辑 → 刷新恢复 → 并发修改 → 冲突选择 → 保存，以及发送过程中继续输入不丢失。可使用内置浏览器，不涉及 GitHub 登录或生产服务。

## 8. W34：DSH 原生预览在 ready 后留存

### 8.1 先明确可证明的能力

只针对已支持且可核验公开合同的 DSH alpha.2 声明此能力，rc.5 不假定等价。检查原生 job 能否提供稳定身份及所属进程、端口归属能否关联、收取器能否抑制完成自动唤醒，以及现有 SDK 监督器是否可以安全转移期限。必要时最多一个临时 profile＋loopback provider 的短探针，不安装或升级执行端。

若公开合同不足，具体记录缺少哪种证据；保留受管预览作为替代，但不能因此把原生路径标成完成。不得放开所有原生 job 或绕过 W18 来满足验收。

### 8.2 目标行为

1. 原生 job 必须显式登记为当前 Assignment 的预览，匹配允许的预览配置和 loopback 地址，并核验端口由该 job 所属进程持有。普通构建、测试、迁移等 job 不因 Worker 称其“无关”而得到 ready 豁免。
2. ready 的依据是当前代码内容、已完成验证、实际报告和已读取输入。所有非预览后台工作已结算，剩余 job 都有有效预览登记，才能保留预览并交付 ready；报告后新到输入使旧交接边界重新核对。
3. 分离模型轮次期限、普通命令期限与预览租约期限。交接成功后，SDK 进程的监督计时器同步转为预览持有状态；不能只修改数据库 deadline，留下旧 transport 超时杀进程。
4. 复用现有预览期限：默认 30 分钟，单次租约最多两小时；允许当前授权下人工续期／新的合法交接续期，续期不受最初 run deadline 截断，也不重新执行服务器命令。最终上限为 Assignment 生命周期和项目限制，不自动无限续期。
5. 先安装收取器并保存可核验归属，再释放 Worker 名额；接受前结果留在当前 owner，拒绝或异常保留原 owner，继承已修复的交接事务规则。不得跳过 guardian 检查或伪造进程退出。
6. 预览结束只收取结果并更新可用状态，不自动唤醒模型、不把已交付 ready 改为假失败；下一授权轮次按原 job 身份读取一次结果。面板分开展示工单待审与预览有效／到期。
7. 到期、取消、撤权、Assignment 结束、会话替换、宿主停止时回收所属进程和工具桥；正常服务停止不留下孤儿。暂停不自动续期，原租约按时到期。
8. 崩溃重开只核对／清理旧归属和证据；不重建预览、不自动采用 pending 队列。未知进程身份进入检查，不能按裸 PID 杀其他进程。
9. Codex 继续使用现有受管 preview 路径；仅在共用租约合同需要时同步修正原 run 期限截断，不强迫其实现 DSH 原生 jobs。

主要位置：`drivers/dsh.mjs`、`dsh-process.mjs`、`dsh-native-jobs.mjs`、工具桥、`runtime/native-handoff.mjs`、`runtime/preview.mjs`、`runtime/jobs.mjs` 和宿主归属监督；类型及详情加入可选能力／预览字段。

一组假 SDK／短本地服务器场景验证 ready 释放名额后仍可访问、跨原 run 期限的续期、结果静默收取；反向覆盖普通测试 job 不允许 ready、交接拒绝、新输入竞争与到期／停止回收。使用缩短的测试期限，不实际等待半小时；最多一个真实本机 SDK＋loopback 短场景核对协议链路。
