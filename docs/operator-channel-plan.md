## 1. 目标与边界

操作者和 js-superagent 之间有一个对话。入口有两个：本地（CLI、SDK、面板）和飞书私信。飞书私信只是这个对话的通道，不属于哪张工单。私信里的内容是什么意思、要发什么给操作者，都由 js-superagent 自己决定。

- 收：操作者在私信里发的每条消息都是操作者项目消息，交给协调者判断，不再直接开工单。
- 发：需要操作者做决定的提问由宿主保证送达；结果和失败由协调者决定怎么告诉操作者；进展不发。
- 卡片：需要选择时，飞书私信显示成卡片。卡片提交由宿主直接核对后转给工单，不经过模型理解。
- 业务层（例如本仓库的长期任务层）和 Worker 不知道飞书。Worker 只在自己的工单里提问；业务层只提交工单、读取结果。

从群和 GitHub 来的工单不变：确认、提问和结果仍回到原对话。

## 2. 操作者对话

每个项目一个操作者对话。操作者是本地操作者，以及项目配置里声明的一个飞书 `open_id`。这条声明是部署配置，由宿主执行，模型和业务层不能选收件人。

| 入口 | 收 | 发 |
|---|---|---|
| 本地 | `coordinate`、`reply`、面板 | 面板的待办和协调记录 |
| 飞书私信 | 操作者发给机器人的单聊消息、卡片提交 | 机器人主动发给操作者的消息和卡片 |

操作者发起的工单（本地 `submit`，以及协调者根据操作者消息 `request` 出的工单）称为操作者工单。它们的提问和结果属于操作者对话。

## 3. 收

**私信文字。** 单聊消息的发送人是配置的操作者时，宿主把它记成一条操作者项目消息：来源是飞书，带会话和消息编号。协调者按现有动作处理：回复、新开工作、给工单补信息、查进展、停止、管理操作。回复写回消息来的入口。其他人发来的单聊消息不进入操作者对话，记为过滤。

**卡片提交。** 卡片上的选择对应某张工单的某一次提问。宿主核对后直接作为这张工单的回答，不交给协调者。核对内容：

1. 点击的人是配置的操作者，租户一致；
2. 被点的卡片消息编号和会话编号，等于为这次提问发出时记下的那条；
3. 这次提问仍是工单当前的提问；
4. 同一次提问只接受第一份回答，不管它来自卡片、私信文字还是 CLI；
5. 必填项都已填写，选项在允许范围内。

**回答一次提问。** 协调者增加一个动作：把操作者的回答转给指定工单的当前提问。它只能转述某条操作者消息里的原话；宿主核对这条消息来自操作者，且提问仍未回答。协调者不能替人回答，这条规则不变。

## 4. 发

**提问必达。** 操作者工单停在等待且带提问时，宿主把提问发到飞书私信：有结构化选项的发卡片，没有的发文字。同时在面板里显示。不依赖协调者模型，也不会被合并掉。

**结果和失败。** 操作者工单完成、失败或受阻时，事件进入协调收件箱。配置了飞书操作者时，宿主在协调上下文提供 `operatorNotification.required=true`、目标工单与 `hostResultDelivery=local-only`：本地结果记录和卡片已提交均不代表完成私信已发送。协调者必须返回恰好一条指向该工单的 `notify`，用短消息说明完成、失败或需要操作者处理的事项；进展不发。空动作、错工单或多条通知被拒绝，保留可检查的失败事件，经 `coordination retry` 重试，不会虚假标记成功。不替模型编造结果，也不能把 Worker 完成声称为业务层已结算。

**提问关闭。** 提问被回答、被新提问替换，或工单被取消时，已发出的卡片更新成对应状态：已提交（显示每项选择）、已在别处回答、已失效、已取消。

**通知操作者。** 新增动作，只能发到操作者对话，可选关联一张工单。宿主按事件去重，同一事件只发一次。

## 5. 结构化提问与答案

Worker 报告里的提问增加一个可选字段 `decision`，和现有的 `question` 一起给出。`question` 是一句话说明，供文字通道使用。

```json
{
  "question": "第 3 回合有 5 个候选，请逐个决定。",
  "decision": {
    "items": [{ "id": "C0001", "title": "Constructing richer readings", "summary": "Andy Matuschak，2026-09-04", "url": "https://..." }],
    "options": [{ "id": "adopted", "label": "采纳" }, { "id": "rejected", "label": "拒绝" }, { "id": "later", "label": "稍后" }],
    "reason": "required"
  }
}
```

- 上限：条目 1–10 个，选项 2–4 个；标题 200 字、摘要 500 字以内；链接只接受 https；`reason` 为 `required`、`optional` 或 `none`。超限时报告无效。
- 字段通用，不知道业务含义。DSH、Cursor、Codex 三个执行端的报告校验都要接受它。
- 文字通道（本地、GitHub、飞书文字）把它显示成编号列表。
- 回答记录在工单上：提问编号、每项的选项和理由、回答人、入口、时间。SDK 的工单详情可以读取。Worker 续接时收到一段可读文字和同样内容的 JSON。
- CLI 和 SDK 的 `reply` 增加结构化答案参数，和卡片提交走同一套核对。

**业务审阅证据。** 可信提交者可用 `submit({text, attentionSnapshotPaths})` 声明 1–10 个工作区相对文件。宿主在提问发出及任何回答前保存不可变 UTF-8 原文、SHA-256、提问编号与选项，公开 `listAttentionSnapshots(id)` 读取；路径不得穿越、经过符号链接或指向常见凭据文件，总量不超过 1 MiB。检查、捕获与首次写入在同一数据库事务内，不能被另一个进程的回答或快照覆盖。捕获失败拦发／拦答，`getDetailed().attention.snapshotError` 提供原因；未答时可以恢复，已答后不追补。未指定文件的旧工单不受影响。宿主只保存通用证据，候选、预算和入库核对仍属于 longrun。

## 6. 飞书通道

现有的「回复到已登记会话的话题」保留。新增：

- **主动私信**：按操作者 `open_id` 发文字或卡片，返回会话编号和消息编号；单聊会话编号由宿主记下，用于后续核对。
- **卡片**：由通道把结构化提问画成表单：每项一个选择和一个理由输入框，一个提交按钮。按钮只带提问编号和一个随机串。
- **更新卡片**：按第 4 节的状态更新已发卡片。
- **卡片回调**：长连接注册 `card.action.trigger`，单独解析，不复用收消息的解析。回调里先在一个事务内完成核对和记录，再当场返回提示和只读卡片。飞书要求 3 秒内应答，所以不能等 Worker。
- **连接状态**：只有真正持有飞书连接的进程才写连接状态。现在任何进程打开再关闭运行时都会写 `stopped`。

卡片回调只能实时到达，没有补收。服务不在线时，点击会在卡片上显示失败，操作者稍后重新提交。

## 7. 配置

项目配置 `feishu` 增加操作者：

```json
{ "feishu": { "operator": { "openId": "ou_..." } } }
```

协调者：配置协调者执行端，开启持续协调。没有协调者时，私信文字只排队，面板显示需要配置；卡片提交和提问必达不依赖协调者，照常工作。

飞书开发者后台（改完发布新版本）：

- 权限：以机器人身份发消息、更新卡片、读取单聊消息；
- 事件与回调：长连接接收 `im.message.receive_v1`；在回调配置里选长连接并添加 `card.action.trigger`；
- 可用范围包含操作者。

改飞书配置前先停止后台。

## 8. 与业务层和 js-agent-runtime 的边界

| 组件 | 负责 | 不碰 |
|---|---|---|
| js-superagent | 工单、执行、操作者对话、通道、卡片、答案核对与记录 | 业务规则 |
| 业务层（例如长期任务层） | 提交工单，在工单说明里要求 Worker 按结构化格式提问，读取结果和答案做业务核对 | 通道、收件人、飞书 |
| js-agent-runtime | 被受管任务调用，跑一次子任务 | 工单、人、通道 |

本仓库长期任务层对应的改动：回合指令要求 Worker 有候选时用 `decision` 提问；收回结果时核对候选库里的状态和理由等于工单上记录的答案；`longrun reply` 改为提交结构化答案；读取服务时不在自己的进程里运行项目运行时。

## 9. 与上游的差异

- 上游不把不同渠道的身份对应起来，主会话只在请求所在的对话说话。这里增加「操作者对话」：本地操作者和配置的飞书私信是同一个对话的两个入口。这是部署配置，不是领域里的身份映射。
- 上游的提问是结构化字段，渠道显示成文字。这里增加结构化选项，飞书显示成卡片；卡片答案由宿主确定性核对。
- 其余回复规则不变：群和 GitHub 工单回到原对话，协调者不替人回答。
