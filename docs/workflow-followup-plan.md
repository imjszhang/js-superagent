日期：2026-11-02（Asia/Shanghai）。状态：**W24–W29 已实现并完成限定验证；DSH 原生交接仅声明 alpha.2 支持**。当前工作区版本 `0.7.0-alpha.0`／schema 8；逐项证据与限制见 [交付记录](workflow-followup-acceptance.md)。下文保留实施合同，不能把尚未核验的目标当成已完成能力。

代码基线：`a67a9901457505431e3d3f230e81a2fa6aff3288`，包 `0.6.0-alpha.0`、schema 7。对照上游公开 `dsh-superagent-prototype` 的 `6337fc823ce20251c8de8085948165c81aaa701e`。接续 [W15–W23](workflow-continuity-plan.md) 和 [DSH alpha.2 适配](dsh-alpha2-compatibility.md)。本计划只补最近源码审查确认的五项流程差距，不把计划或历史验收写成新能力已完成。

## 1. 目标与固定范围

完成后，允许的人可在已关闭讨论中继续原工单；等待 CI 的活跃工单可收到恢复反馈；已配置准入规则在 GitHub 各入口一致生效；尚未绑定工单的行内委托可进入接单流程；DSH 在原生命令仍运行时也能及时把需要人处理的结果交出来，并正确管理剩余进程。

- js-superagent 独立维护工单、权限、存储、调度、工作区、交付和收据；不依赖 js-agent-runtime，不加载上游插件运行业务。
- 保留 CLI/SDK 工单入口、Codex app-server、DSH SDK、实例级 Harness Registry；新增能力按适配器实际声明，不要求 Codex 复制 DSH 的原生机制。不恢复旧 exec/headless/Driver 注入。
- 优先修改应用层和适配器，原样提取的领域内核保持不变。若发现核心合同无法表达必要行为，先记录具体原因和最小差异，不能改摘要掩盖修改。
- **W18 继续暂缓**。保留 pending 身份、只读检查和 `native-pending-wakeup-unsupported`；不重发原输入、插入空消息、调用私有唤醒方法或修改原生日志。
- **生产后台保持停止**。计划与后续实施不安装、启动、切换服务，不迁移生产库，不升级本机执行端。隔离的短期测试进程结束后必须回收。
- GitHub 轮询、Webhook、App 和 gh 认证保留；本地 CLI/SDK 不依赖 GitHub。新入口不能改变默认授权、交付模式或自动恢复开关。
- 本轮不实施自动合并、fork PR、飞书配置、通用 provider/技能/联网平台、集中多项目服务、固定公网入口或 npm 发布。
- PR 转正式待审／解决审阅讨论／机器人轮次策略、按需团队手册、面板跨刷新草稿列为后续候选，不插入本轮主线。仅随本轮修正相关旧文案和状态展示。
- 用户已授权实现 W24–W29；Git 提交推送、发布和部署不因源码实现完成而自动发生。

## 3. 共用合同、数据与迁移

### 3.1 继续使用现有运行时

复用 Store、Engine、Effects、Outbox、SourceRegistry、工作区和进程监督设施，不另造消息系统或调度器。抽出小型共享入口，避免再给 Issue、PR、仓库发现流和 Webhook 各自复制一套判断。

统一处理顺序：可信来源事实与接收范围 → 原始事件身份／版本去重 → 核对订阅与现有归属 → 按当前政策分别决定候选准入、订阅上下文投递及原工单接续 → 原委托及执行目标检查 → 派工／回传。新候选不通过 gate，不等于合法订阅上下文应被丢弃；允许记录／投递上下文也不等于允许唤醒、恢复、执行或发消息。记录“接收”“可作为候选”“可继续已有工单”“可执行／可发送”四种不同结论及原因，不能互相替代。

| 增量记录 | 内容与不变量 |
| --- | --- |
| 来源与续作代次 | 稳定 ticket ID、原始 trigger／讨论／review root、前后执行代次、原／新 workspace provision、分支／base／head、会话 lineage、交付与 PR 归属；历史记录不可覆盖 |
| CI 观察 | repository、目标及代次、head、check app/name 或 status context/actor、原生 ID／版本、运行状态、失败集合、完整性、基线／变化版本；观测事实与唤醒决定分开 |
| 准入事实 | source 配置代次、policy revision、真实 actor 身份、归类为 bot 的依据、scope、explicit/inferred、匹配规则与拒绝原因 |
| 审阅发现 | canonical event ID／修订、PR、review/root/comment ID、历史位置与 commit、当前 head、发现游标／Webhook ID、归属与研判结果 |
| DSH 交接持有记录 | assignment/run/session、native version、job ID、原生事件序号、owner/guardian 代次、报告与输入边界、保留／静默收取／退出结果、回收原因；不能把进程消失写成成功 |

工作区交付版本为 `0.7.0-alpha.0`，新执行语义使用 **schema 8**，W24 写入路径已接入升级保护。旧库只读与显式升级／回退的检查结果以 [交付记录](workflow-followup-acceptance.md) 为准；生产库未打开或迁移。

迁移要求：

1. 只读 status、show、历史查询、SDK 导入不升级生产库。显式升级须确认 owner/guardian 已停止，持维护锁做一致性备份，再原子升级。
2. 旧 ticket、session、workspace、输入收据和已发送结果保留；有充分身份事实时映射为初始执行代次，不能从文字猜测归属。缺证据的旧记录显示待检查。
3. 不重放历史 ignored 评论、不批量重排 failed 工单、不把旧关闭事件重新当新任务。历史保留事件可通过既有显式重评入口处理，重评仍受当前政策约束。
4. 新发现流默认关闭；启用时建立基线，不扫历史创建任务。已持久化待处理的 Webhook 事件单独保留，不能被基线推进吞掉。
5. 已显式配置的 bots/admission 本轮开始在遗漏入口生效；升级预览须显示其实际接收范围变化。不新增默认名单、规则或权限，也不为了启用这些规则而修改生产配置。
6. 新增公开字段采用可选增量。旧状态字段、CLI 命令、SDK 工单 ID 保持；无新增适配能力的注册实现保留原行为，不能推断其支持进程交接。
7. 回退只在停止后用备份准备，先核对备份之后的远端动作；旧包不能强读 schema 8，不自动重放回退期间的消息或交付。

## 4. W24：关闭讨论后的真人接续

### 行为

1. 将“可读取／回复的来源讨论”与“可修改的当前执行目标”分开。关闭／合并状态不直接阻断人类评论接收；目标已删除、不可读、锁定和授权撤销仍按现有规则处理。
2. 仅当前获准的真人消息可以恢复非人工停止的原工单。原工单继续判断请求是否在范围内，超范围交回研判；上下文订阅不变成请求归属，bot、CI、状态快照不能单独恢复已完成工单。
3. 关闭前已经到达的输入与关闭后新输入都保留其实际顺序。旧 PR 的重复 close 观察不得结束正在处理新输入的工单，也不得结束新的交付代次。
4. 在接续准备阶段先以只读上下文和目标检查区分历史解释与代码续作；需要模型判断时使用受限只读研判，不先启动旧绑定的可写 Worker。仅解释或查看历史时，允许读取原讨论和必要原始上下文，不为一次问答强行创建新分支。回复仍回原 Issue／PR／review root，沿用目的地检查和 marker 去重。
5. 确需代码修改且旧执行 PR 已关闭或合并时，在现有授权内建立新的 owned 续作工作区、分支及交付代次，工单 ID 与历史不变。已合并 PR 从经核对的当前目标分支建立续作；未合并而关闭的 PR，根据明确请求选择其已核对变更或目标分支，目标不明确时提出具体问题。不能默认重开旧 PR、重写默认分支或继续向已合并分支推送。
6. 新工作区不能静默改变旧 native session 的 cwd。先检查旧 run／输入／工具／交付已结算，再通过宿主明确的续作绑定创建新会话代次，记录原因及 lineage；保留原会话。新目标与会话绑定完成前不得开放对旧 PR 工作区的写入。旧工作区脏、结果不明、多个交付目标不唯一、原 pending 未消费时进入具体检查状态，不丢弃变更，不绕过 W18。
7. 如原工单还有唯一有效的开放执行目标，优先在其合法绑定上续作，不能每收到一条旧讨论评论就新建工作区。交付仍服从原配置：本地交付保持本地，草稿 PR 交付才产生新草稿 PR。

### 改动位置与完成条件

主要涉及 `channels/github.mjs`、`channels/github-repository.mjs`、`github-webhook-inbox.mjs`、`index.mjs` 的绑定／续作／执行门禁，及 `workspaces.mjs`、`delivery.mjs`、历史读取和回复目的地校验。需要增加讨论与当前目标的投影，不以删除一处 closed 判断宣称完成。

一个定向场景组覆盖：关闭 Issue 真人跟进；合并 PR 真人跟进；人工停止／撤权不恢复；旧 close 不结束新工作；解释只回原处；代码续作保留同 ticket、新目标与新会话 lineage，未写旧 PR；脏工作区／未知输入拒绝自动转换。使用模拟 GitHub 和临时 Git 仓库，不创建远端对象。

## 5. W25：CI 变化和恢复反馈

### 行为

1. 接收可信 CI 的运行中、失败、成功及其他终态观察，按目标代次和 head 保存；延续现有 checkApps、statusContexts、statusActors，不扩大可信 CI 来源。
2. 对仍活跃、正在等待结果的工单，将有意义的变化作为原委托内的上下文输入；失败变为运行中不冒充修复，单项成功不冒充全部通过。是否可以结束仍由实际检查和 Worker 判断。
3. 检查集合来自当前 CI 配置选定范围和该 head 的可信观察，保存集合版本。check 使用 app 身份、名称及可获得的 suite／workflow 身份区分，status 使用 context／actor；保留原生 run ID 和时间／尝试事实，同名重跑只在可证明先后关系时替代，否则保持待核对。读取完整、已观察故障均被对应新结果解除且选定集合不再运行时，才报告“已观察故障恢复”；检查缺失、仍运行、局部读取失败保持未知／未确认。没有明确、完整的 required-check 定义和证据时，不宣称 GitHub 所有必需检查已通过。对象隔离不能变成“没读到失败就是成功”。
4. 默认分支 CI 在同一故障讨论中记录失败集合变化与恢复，不为一个转绿事件自动新建修复工单。已完成／人工停止／撤权工单不因 CI 成功恢复；现有显式 CI 失败续作策略与本轮成功反馈分开，不把成功伪装成人类委托。
5. 初次启用或升级后建立基线；旧 head 成功不能清除新 head 失败。对同一次检查的重复、过期和乱序观察去重，只有重新出现的真实状态变化才生成新版本输入。
6. 回传仍遵守安静默认原则：CI 状态变化本身不逐条给人发通知；需要处理或有可交付结果时才沿用现有回传。

### 改动位置与完成条件

主要涉及 `github-pull-intake.mjs`、`channels/github.mjs`、`channels/github-repository.mjs`、`index.mjs` 和 CI 状态投影。

一个表驱动场景组覆盖失败 → 运行中 → 全部成功；重复成功只投递一次；单项成功／局部读取失败不报全绿；旧 head／乱序不回滚；默认分支只更新原故障；已完成工单不因绿灯启动。与 W24 共用一次临时数据库重开，验证基线及变化身份保留。

## 6. W26：贯通 GitHub 准入与反馈策略

### 行为

1. 移除仓库发现流和 PR 反馈在 Policy 之前吞掉 bot／名单外发送者的重复判断，改为共用当前接收范围、Policy 和工单归属检查。网络身份校验和仓库边界保留。新候选 gate、合法订阅的上下文投递、原委托下的反馈接续分别判定，不把三者合成一次允许／拒绝。
2. 普通 Issue、PR 总评论、review、行内评论使用同一 actor 语义；原生 Bot/App 及显式配置为审阅机器人的普通账号都不能被当真人授权者。保存真实账号事实与策略归类，不能仅凭正文或 `[bot]` 后缀猜身份。
3. 列名 bot 只产生 inferred 候选，或在已有有效委托中作为受限反馈；不能停止／恢复已完工单、扩大范围或授权发布。已有 owner、上下文订阅及新候选分别处理，不把所有 bot 评论直接送给任意 Worker。
4. `off / observe / auto` 语义保留：observe 记录研判而不执行，auto 仍要求匹配启用规则；原允许真人的明确请求继续使用既有 explicit 授权。没有新配置时，原默认接收行为不扩大。
5. 排队、即时输入交付、执行、补读和远端回复前重查当前政策；撤权和暂停优先。自身回执与重复 bot 事件不会形成反馈环。机器人多轮审阅策略留待后续，不能把本轮事件去重称为已实现三轮上限。
6. 管理端展示当前来源的准入依据及拒绝原因，避免出现“页面已允许、入口仍硬拒绝”的矛盾。

### 改动位置与完成条件

主要涉及 `policy.mjs`、`github-intake.mjs`、`github-pull-intake.mjs`、`channels/github-repository.mjs`、`index.mjs` 和相关配置投影。

一组关键组合即可：允许真人、列名原生 bot、被配置为 bot 的 User 账号、名单外发送者；off／observe／auto；已有 owner／新候选；队列中撤权。证明“允许观察”不变成明确授权、“bot 身份”不被转换为人类恢复事件，保持默认配置兼容。

## 7. W27：未绑定 PR 的行内委托接单

### 行为

1. 为仓库源增加显式启用的行内审阅发现范围，初始默认关闭；优先复用现有来源设置、游标、对象失败隔离和 bounded pagination。轮询读取仓库 review comments，不要求先有 ticket binding。
2. Webhook 在配置范围内可以接收尚未绑定 PR 的行内事件 selector；它只排队待核对的来源事实，不直接授予执行权限。签名、installation、repository 和重投去重仍按原链路校验，然后权威补读 PR 和评论。
3. 轮询／Webhook 共用原始事件 ID 和编辑版本，保留 review/root/comment ID、路径／行号、原 commit、当前 head 和原文。历史 diff 位置标为历史证据；执行前核对当前 head，不能把过期行号当当前代码。
4. 已有明确归属的请求交原工单；未归属的进入同一准入和研判，不另建 review 专用调度器。并发首条消息通过事务和归属重查避免同一请求重复建单；真正独立的不同请求仍可由研判分开，不能按“同一个 PR”强制合并所有工作。
5. 原文中的明确命令只使用现有语法；不在本轮扩大任意 @mention 或 topic similarity 的接单范围。fork PR 继续拒绝，head 变化重新核对，授权不足只记录原因。
6. 接单确认、提问和结果在正确原处发送，沿用 W19 root 关联、删除后受控回退和 W16 顺序／marker 对账。确认接收不等于工作完成。

### 改动位置与完成条件

主要涉及 `runtime/repository-source.mjs`、`channels/github-repository.mjs`、`github-webhook-inbox.mjs`、`github-pull-intake.mjs`、`index.mjs`、类型和来源设置界面。

一个端到端宿主 fixture 覆盖：未绑定 PR 行内明确委托 → 研判 → ticket → 模拟 Worker → 原处回复；轮询和 Webhook 重复／并发只接一次；已有绑定仍用原工单；编辑、过期 head、fork、删除 root 各用小表驱动分支。验证首次基线不吞持久待处理事件，不调用真实 GitHub 写入。

## 8. W28：DSH 原生长命令期间的人工交接

### 先核对公开能力

当前 `executeDshTurn` 在 native jobs 清空后返回并 shutdown，宿主也要求 run 所属 guardian 全部退出。因此不能只提前 return 或跳过进程退出检查。

先核对已支持的精确 DSH 版本是否能通过公开 SDK／公开插件合同读取和管理原生 job、改变结果交付方式、在人工交接后静默收取结果并保持进程受管。最多增加一个短期本地协议探针，使用临时 profile 和 loopback 模拟 provider；不安装旧版本，不调用外网模型。若仅 alpha.2 有可验证支持，则仅对该版本声明新能力，rc.5 保留原行为及明确说明。

不能把 `quiet` 之类的参数名当成无副作用证明：须核实它是否向 native inbox 插入结果、是否唤醒模型，以及下一真实人类输入如何消费这些结果。若公开合同不足，则单独记录 W28 未完成的具体环节，不用私有接口、改日志、丢队列或静默杀掉命令冒充上游交接。

本机 alpha.2 公开实现已提供一条具体候选路线：`dsh-jobs` 的 `list/get/wait/readAt/kill` 与完成事件的 `awaited` 标记，配合 `tool-jobs` 对已等待结果不自动通知的行为。上游 [collectJob](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/executor/background.ts#L125) 也使用循环 `jobs.wait`。优先在现有薄插件内加入仅针对当前 Session 的后台收取器：先注册等待者，再持久化交接及释放名额；命令结束时保存有界实际输出。这里仅有源码可行性依据，尚未证明本地适配器已经接通。

### 目标设计

1. 分开“本次模型轮次完成”“等待人处理”“Assignment 仍持有后台进程”。在现有 Harness 边界增加可选交接合同，由 DSH 声明支持；不把 DSH job API 扩散到工单核心，不强迫其他适配器实现。
2. Worker 本轮确有已核对的 ready、等待问题、blocked／failed 报告，且其后没有新输入时，在真实 turn/end 和最终报告一致后，先安装收取器、持久化报告、读取证据和交接状态，再释放 Worker 名额。完成工作所必需的检查仍未结束时不能宣称 ready。已有 progress 提问不变；普通无人工交接的后台任务继续按既有等待策略运行。
3. 需要保留的原生命令和 SDK 进程以 assignment 级受管持有记录继续存在。owner/guardian 从当前 run 向明确持有者转移须可核对；不能取消所有权登记来骗过退出检查。运行时需另有明确进程数量与清理约束，释放 Worker 名额不等于无限增加后台进程。记录并沿用既有任务期限，交接不能刷新执行预算。
4. 交接后的 job 完成只保存结果，不自动启动模型、不撤销人的问题、不自行报告 ready。若公开 API 只能静默注入结果，则保留原生身份与因果证据，留到下一真实输入处理，不能额外发送假用户提示。
5. 人回复时，经过授权、取消和名额检查，再在有效 session/workspace 绑定下接续；旧 job 结果按原身份核对且只处理一次。Session 独占权和工具桥必须绑定到新 run 的有效授权上下文，不能继续调用旧 run 的回调。对新消息与交接同时发生的竞态重查输入序列，不能把新输入丢在交接边界。全部 job 已结束且会话空闲时可以关闭 SDK，但须先保存可核对的结果，后续不能依赖已销毁的原生输出缓冲。
6. 工单／Assignment 结束、取消、替换会话、撤权或宿主关闭时，回收所属进程并核对退出；保持现有业务暂停的语义，不把 pause 随意改成 kill。正常关停须在截止时间内清理，异常退出留下 interrupted 及检查原因，不能据此自动重跑命令。
7. 跨进程重启只沿用 W17 可证明的终态收取与检查。遇到待处理原生队列仍走 W18 暂缓分支，不声称“人工交接支持”同时解决“崩溃后原队列自动采用”。
8. 受管 command／child／preview 的已有行为保持；原生 shell job 与宿主 job 的身份不可混用。ready 且无后续审阅的本地工单结束时仍清理进程，不能以 ready 为由永久留进程。

### 改动位置与完成条件

主要涉及 `drivers/dsh.mjs`、`drivers/dsh-process.mjs`、DSH 薄工具桥、`harness/registry.mjs`、`index.mjs`、进程所有权／恢复记录和状态投影。复用现有任务监督设施；仅增加原生任务适配，不另建用户可见的第二套后台任务系统。

一组协议 fixture 检查交接、抢先到达的人类输入、完成不唤醒、取消与重开；一个真实本机 DSH SDK＋本地模拟 provider 短场景检查“长命令仍运行 → 问题／就绪已可见且名额释放 → 人回复或命令完成 → 正确收取 → 全部进程退出”。复用前置探针，已证明的分支不再重跑。报告必须区分 fixture、真实原生协议与外网模型实测；本轮不做后者。
