# 飞书输入连续性、评估恢复与停止可靠性：实施计划

状态：已审阅并授权实施，正在实现与验收。日期：2026-11-13。

本计划经审阅后进入实施阶段。实现、发布及项目验收均以“不改变原型职责和授权边界、不增加用户配置项”为约束；以下合同作为回归与交付标准，不将计划描述当作已完成事实。

## 1. 基线、事实与设计依据

核对基线：

- js-superagent `0.15.0-alpha.5`，提交 `58b0249e9326c30d3958e3709a1eb05201e5f623`。
- js-superagent-skill `0.6.6`，提交 `22a25ed0cb75533293bba83af73afcad4993d754`。
- dsh-superagent-prototype，提交 `8c32a9dc5d72c033816c6a8110b37f40cf94fba4`。

前次验收发现三处既有缺口，均不能归因为单纯缺少飞书权限：

| 缺口 | 已核实事实 | 仍须区分的推断 |
| --- | --- | --- |
| 建单前补充被过滤 | 宿主在 Engine.receive 之前执行工作准入。没有订阅工单的非 @ 补充被记为 filtered；随后历史补收会按同一消息 ID 去重，不能补回 | 不能由此推断所有非 @ 消息都应成为工作请求 |
| 上下文变化使评估永久失败 | 材料会话和读取集合会核验版本；评估路径把部分版本失效记成不可重试的 internal。手工重新评估原请求可以成功 | 并发工单启动与失败时序、全局摘要代码相符，但旧日志未保存变化字段，不能断言当时究竟是哪一个字段触发 |
| 停服后子进程仍在收消息 | 一次历史轮询长期未结束；停止等待超时，包装进程已退出，运行子进程仍存活并续租。服务管理只检查 launchd，没有完整检查子进程 | 当时没有请求栈，不能指认某个具体 HTTP 接口；SDK 读取缺少有效取消、停止顺序及进程检查均为已确认的代码缺口 |

原型对照：

- `src/sources/registry.ts`、`src/sources/feishu.ts`：来源先限制监听范围，不在适配器里替协调者判定工作。
- `src/core/intake.ts`、`src/core/engine.ts`：收到的范围内输入去重、关联话题，交给已有订阅或 pending。
- `src/core/evals.ts`：按话题批次评估；没有有效授权输入时不创建工单；评估中的后来消息留待下一轮；策略失效和超时具有既有处理方式。
- `src/app/runtime.ts`、`src/infra/commands.ts`：停止复用单一 promise，先关闭入口／中止生命周期，再等待在途工作；外部命令有取消与超时边界。
- 原型没有本项目同款材料会话、服务包装和单输入 decideTrigger 扩展。对应修复应明确为本地宿主或本地扩展修补，不能声称直接照搬原型。

## 2. 必须保持的职责与行为

| 组件 | 应承担的责任 | 本次不得越界 |
| --- | --- | --- |
| 飞书适配器、SourceRegistry | 范围校验、标准化、去重、游标、读取取消 | 不判定业务意图，不建单，不替消息赋予显式授权 |
| 项目宿主 ProjectRuntime | 接收资格、调用评估、材料授权、提交结果、生命周期 | 不根据“消息看起来像补充”直接塞给最新工单，不绕过核心或材料检查 |
| 协调者／assessor | 对宿主提供的事实提出 accept、attach、stop、ignore 等判断 | 不自行获取额外权限，不直接操作队列、进程或数据库 |
| 工单核心 Engine | pending、Eval、授权、工单所有权和终止规则 | 不依赖飞书 SDK、材料实现或服务管理；不增加新调度器 |
| 执行者、DSH、longrun | 按已批准工单执行、处理已交付输入 | 不因本次修复改变工作目录、材料绑定、执行恢复或报告协议 |
| 服务管理 | 管理并核实本服务拥有的进程 | 不按裸 PID 杀进程，不误报停止，不擅自强杀执行者 |
| skill | 安装、兼容性核验、操作说明和验收 | 不复制业务状态机，不靠提示词弥补宿主缺陷，不重写用户授权配置 |

硬性不变量：

1. 群 @ 是按现行策略进入评估的依据，不等于必须建单。非 @ 补充保留原身份，不变成 explicit 请求。
2. 保留输入不等于准许工作，也不等于准许读取项目材料。每位作者、每个目标工单、每个输出位置分别按现有规则核验。
3. 复用现有 Thread.pending、Eval、Effects、Outbox；不另建缓冲队列、任务系统或重试服务。
4. 旧请求不被新请求替换；已建立的工单不重复建立；人工停止和撤权不得被补充消息恢复。
5. 不改 `auto` 的工作目录选择、不改当前材料绑定与未提交内容读取合同，不改 knowledge 的职责。
6. 不降低材料 freshness、provenance、读取集合或输出授权检查；不缩小全局材料会话摘要。
7. 不自动回放旧 filtered／ignored 消息，不清空游标或去重记录，不批量重跑旧 internal 失败。
8. 不增加用户配置项或权限；保留现有群范围、仅 @ 发起、机器人预算及私聊协调者配置。

## 3. 修复一：保留合格的话题补充，仍由原流程作判断

### 3.1 宿主接收与复核

修改 [src/index.mjs](../src/index.mjs) 的 `#receiveSource`、`#assess`，在 [src/policy.mjs](../src/policy.mjs) 集中实现可复用的资格检查。

只有满足以下条件的飞书非 @ 话题回复，才进入窄例外：群在当前配置范围内；平台身份和话题归属可信且一致；作者是当前规则列明的真人；不是机器人、contextOnly、私聊协调者消息；拒绝原因仅为其没有独立发起工作的资格。不能把任意 gate 拒绝都当成可保留的补充。

话题关联只使用平台标准化的 root／parent 和既有 thread key，并核对来源、租户和群一致；不从正文或模型判断“应该是同一话题”。普通非 @ 根消息保留现有适配器忽略行为，不进入这个例外。需要记录例外分类时只能由宿主生成受信审计信息，不能接受消息自报的 meta 作为资格证明。

在现有合法订阅交付未接管消息时，以 `engine.receive(trigger, { ticketIds: [] })` 进入既有 pending。禁止使用无条件初次 fanout 绕过宿主检查。正常准入、现有订阅交付和其他来源分支保持原语义。

评估开始前和结果提交前，逐条复核本次窄例外接纳的飞书补充仍满足上述资格；同时通过现有规则确认批次的独立授权仍有效，不能把补充提升为授权来源。撤权、移除群、身份不符的补充通过既有单输入 unavailable 结束，其余输入重新评估。不能只检查批次主消息或 policyVersion。

其他飞书明确请求、私聊协调者、GitHub、机器人及其他来源继续使用各自现有的专属校验，不统一套用新增名单检查或重新定义其准入。

跨作者补充可按既有人员规则参与，但沿用逐作者材料读取授权及输出位置校验。材料不足时不得借主请求者的权限建单或附加工单。

### 3.2 仅完善本地单输入 ignore 扩展

[src/core/evals.ts](../src/core/evals.ts) 中已有 `decideTrigger` 是本地扩展。当前同批非 @ 输入即使只被判为 ignore，也因自身 gate 不通过而抛错。

本次仅允许：当前 Eval、当前 policyVersion 下，没有执行者拥有的输入，可以单独终结为 ignore，即使它没有独立发起工作的资格。记录实际 gate 和该输入自身的授权强度，不继承主请求的 explicit 身份。继续拒绝过期 Eval、已有 worker 所有权，以及通过该窄接口发起 accept／attach／stop。

不改原型的批次选主规则、Mandate、接受工单、停止工单和 followup 生命周期。GitHub answer 仍经过专属显式授权检查。更新 [docs/upstream-core.json](upstream-core.json) 的本地目标哈希和 localModification 说明，保留真实上游哈希；运行核心差异检查。

### 3.3 时间边界

| 消息到达时机 | 保证 | 不作出的保证 |
| --- | --- | --- |
| @ 和补充都在评估前 | 同批提供给评估者；可以接受工作、只忽略无关补充，或依据撤回消息忽略原请求 | 不由接入代码替评估者决定自然语言含义 |
| 评估进行中收到补充 | 持久保存在 pending；下一轮可根据已存在工单选择 attach、stop 或 ignore | 不强行修改在途评估；不保证自然语言取消早于第一轮执行 |
| 建单后收到补充 | 走现有订阅和 followup；相同消息只交付一次 | 不随意关联“最新工单”，不恢复人工终止工单 |
| 孤立非 @ 已单独被忽略，之后 @ 才到 | 保留原型当前语义，不重新翻出已结算消息 | 不新增全量乱序回溯和历史合并机制 |

尚未建单时的“别调查了”应由评估者忽略原请求，不能虚构工单执行 stop。正常完成后的真人跟进仍可按既有规则恢复；人工停止或撤权后不得恢复。首次收到的迟到消息按当前正常接收规则处理，不能与重复的旧 filtered／ignored 消息混为一谈。

上述语义评估保证以项目已配置 assessor 为前提。没有 assessor 时现有明确 @ 的同步接单捷径保持原样并单独回归；不能因新增 pending 隐式要求用户补配置，也不能宣称没有语义评估者的路径会判断补充或撤回含义。

## 4. 修复二：上下文变化只作有限刷新，不放松校验

### 4.1 可信错误分类

涉及 [src/runtime/assessment.mjs](../src/runtime/assessment.mjs)、[src/runtime/coordination-context.mjs](../src/runtime/coordination-context.mjs)、[src/context-requests.mjs](../src/context-requests.mjs) 以及 `ProjectRuntime.#assess` 和材料会话核验。

由宿主生成结构化的“本次上下文快照已变化”错误，携带有限的诊断分类和 attempt 标识。模型文字、普通错误里的 stale 单词、过期回调、任意 MATERIAL_* 或候选关联拒绝，都不能自动获得刷新资格。

评估开始保存授权标记，包括 policyVersion、材料配置 revision、原消息身份与输出路由。刷新前重新核对原 Eval、owner、候选所有权、授权标记和原输入材料 provenance。只有授权未变、旧尝试事实版本变化才自动刷新。撤权、路由变化、原材料授权失效继续按既有拒绝／重新准入处理。

`runBoundedAssessment` 不能吞掉这种结构化失效，也不能把取消和授权拒绝统一变成模型的 unavailable；这些错误须交回宿主分别处理。普通读取失败和模型越界读取仍保留现有合同。

### 4.2 保留 Eval，重新执行评估尝试

不新增 core API。符合条件时，原子记录刷新原因与额度，然后通过既有 `Later` 保留同一个 assessment effect。下一次重新取得 `engine.candidate()`，建立新的材料会话、读取集合、关联信息、模型会话和 runId／owner token，不复用旧模型结果或旧 facts。

- 固定最多 **2 次自动上下文刷新**，不增加用户开关。
- 同一 Eval 的 deadline 不因刷新延长；既有暂停时间处理保持不变。
- 在现有 KV 中按原 trigger 保存 cycle、refreshesUsed、lastRefreshRunId 等最小元数据。一次 attempt 对每个参与输入最多计一次。
- 合批、拆批、自动 Eval 过期重排、停止和重启不清零额度。合批刷新必须核验并计入所有参与输入，不能只刷新一部分事实再提交整批结果。
- 某输入额度耗尽时，以既有单输入 unavailable 结束该输入，其余输入沿既有拆批机制重新评估；它们的额度继续保留。
- 只有明确人工重评原请求被实际受理，且没有既有工单或待评估所有权冲突，才开启新 cycle。
- 不借用 Effects.attempts、模型格式修正次数或 workRetry；它们的含义不同。`autoRetry:false` 对普通网络重试的现有含义不变。

旧回调、checkpoint 和结果提交必须受 owner token／attempt 约束。旧尝试的守护执行仍活着时，不抢占 ownership 开新尝试。暂停或停止期间不启动模型刷新，也不因等待重复扣额度。

### 4.3 状态与结果回执

自动刷新期间保留“评估中”，不提前写终局失败、假建单结果或发送失败回执。成功仍通过原事务建单并登记回执。

耗尽后记录独立的结构化错误，清楚表达“上下文持续变化，有限刷新已用尽；请求保留，可以重评”。通过现有恢复入口重评原请求，不制造替代请求。

目前群失败回执只放行两种材料授权错误。为使新终局状态可被原请求者看到，在 [src/runtime/assessment-status.mjs](../src/runtime/assessment-status.mjs) 和 `#assessmentReceipt` 中，仅增加此固定宿主状态的回执证明与模板：

- 只对仍有权限的原明确 @ 请求、原群／原话题发送；私聊沿现有原请求结果路径。
- 非 @ 补充不借此获得主动群回复资格。
- 多输入中只有一条额度耗尽时，只记录和通知该 trigger；在失败记录及证明中明确已结算输入集合，不能遍历整批发送失败，也不能仅凭“属于 candidate”就允许失败回执。
- 不包含材料正文、任意异常文本或模型生成解释；发送时重新核验身份和路由。
- 复用现有 Outbox 和稳定消息 ID，正常路径与重启后不产生重复排队。
- 保留先前错误的诊断历史；旧 internal 记录不自动转换为待执行工作。

## 5. 修复三：真正取消读取，只有进程退出才确认停服

### 5.1 飞书读取的取消必须到达 HTTP 层

修改 [src/channels/feishu.mjs](../src/channels/feishu.mjs)，可抽出内部 transport 模块，不新增依赖或用户选项。

当前所用 SDK 的 API 参数组装不会把随意追加的 signal／timeout 透传到请求层。实现必须使用 SDK 支持的每连接 `httpInstance` 注入，保持其响应转换、代理及请求合同，不修改 SDK 全局默认实例或 node_modules。

给历史、话题、上下文读取及其鉴权／连接准备增加真实 AbortSignal 和固定的有限请求预算。首版采用单次读取操作 **30 秒** 上限，预算覆盖该操作的鉴权和 SDK 内部重试；停止信号立即中止读取，不等超时。保留原有每轮页数预算、公平调度和续扫规则，不引入新的历史扫描窗口或全量回放。

需用实际锁定 SDK 配合本地可控 HTTP 服务验证：挂起响应会被真正取消，socket 关闭，调用返回且不继续隐式重试。只用 Promise.race 让外层返回而底层继续运行，不算通过。

HTTP transport 不覆盖原生 WebSocket 握手。当前 SDK 的 endpoint discovery 已有 15 秒请求上限，但握手需显式设置 `handshakeTimeoutMs`；`ws.start()` 也不等待握手结束。本版固定内部握手上限为 10 秒，利用并验证 SDK 的 close／generation 防复活能力。合同是“HTTP 真取消、握手有界退出”，不能将 await start 或 close 返回等同于所有握手 socket 已立即关闭。

读取超时按现有容器失败规则保留失败窗口、允许其他容器已有进展；停服取消时，未提交轮次不能继续入库或推进游标。SourceRegistry 的事件与游标原子提交、owner token 校验保持不变。

### 5.2 停止顺序与连接代际

修改 [src/sources.mjs](../src/sources.mjs)、`ProjectRuntime.#connectFeishu`、`#disconnectFeishu`、`stop`：

1. 通过共享 stop promise 幂等进入 stopping；首先封闭新消息、卡片动作、新轮询与新外发入口。
2. 使旧连接回调失效，立即发起关闭 WS 并取消在途读取；关闭连接和注销 source 分开，不能先删除仍持有轮询 owner 的 source。
3. 等待已开始的事务、读取、评估和现有执行停止流程全部实际 settle。一项拒绝不能让 Promise.all 提前进入 finally 并释放其他仍在使用的 ownership。轮询取消后不提交尚未接受的消息；未接受消息由下次历史补收恢复。
4. 仅在实际工作结束后释放 source／runtime ownership，完成连接注销与资源清理。

连接启动每次使用内部 generation，并跟踪 connect promise；动态导入、创建连接、start 的 resolve／reject，以及旧 onState、消息与卡片回调在跨 await 后或提交边界检查 generation 和 stopping。防止“停止时连接尚未建立、稍后反而重新连上”。清理失败或仍有在途工作时，保留停止状态与所有权，不允许 start 提前重新开放。

[bin/js-superagent.mjs](../bin/js-superagent.mjs) 的信号入口立即启动上述停止栅栏，不先串行等待 HTTP 管理入口关闭；管理入口关闭与 runtime drain 协同完成。

保留暂停与停止的区别：业务暂停仍可按既有合同接收消息；stop 返回后 SDK 对象可按既有 restart 合同再次启动。自定义 source 若不响应取消，不能靠提前删除 owner 或假装已停止绕过它。

### 5.3 外发与进程边界

新读取超时不能顺手变成所有消息写入的自动重试规则。已经发出的 POST 可能已被飞书接受；停止不得把这种未知结果自动当成失败再发。

- 阻止停服后开始新外发；已在途写操作沿用既有 Outbox 和回执处理。
- 不增加写入超时后的自动重发，不改稳定消息 ID，不清空未确认回执。
- 若在途写入、执行者或不合作的自定义适配器无法退出，报告“停止未完成”，不宣布安全离线，不强杀，也不启动第二实例。

修改 [src/service.mjs](../src/service.mjs)、[src/service-health.mjs](../src/service-health.mjs)，复用 [src/machine-coordination.mjs](../src/machine-coordination.mjs) 的进程身份检查：

- 即使 launchd 已卸载、包装进程已退出，也读取本服务保存的 runtime 身份并核对 child。
- 停止顺序为禁自启、校验身份、向确认属于本服务的 wrapper 发 SIGTERM、等待 wrapper 和 child 退出、最后 bootout；不先 bootout 活 wrapper，把后续处置隐含交给 launchd。
- 使用 host、boot、PID、启动身份与 runId 校验；PID 重用、身份未知、旧记录冲突不能当作可杀进程。
- stop 可向确认属于本服务且仍存活的子进程补发 SIGTERM；不增加自动 SIGKILL。
- 只有包装进程和工作子进程均确认退出，才返回停止完成；超时或身份不明保留诊断并失败返回。
- 区分新安装且从未启动的服务与存在不可验证遗留运行记录的服务；不能让新安装无故被阻断，也不能将遗留记录当作“从未启动”。
- start、restart、install／迁移、uninstall 共享同一停止前置检查，不允许孤儿子进程存在时替换或重启服务。
- 保留 loaded／running 的原含义，并增加必要的“停止未完成”可观测结果，更新公共类型及 CLI 展示；这是状态报告，不是新配置。
- health／status 只读，不关闭进程、不重置故障、不自动恢复用户已停服务。Patrol 的显式恢复条件和维护锁继续生效。
- 一致性备份仍要求服务与数据库 owner 都已停；不因新的状态检查省略原有数据库所有权验证。

## 7. 测试矩阵

测试采用确定性的时钟、受控 Promise 和伪平台／本地 HTTP 服务；真实模型仅作为最终验收，不用随机时序代替合同测试。

| 范围 | 必测场景 | 核心断言 |
| --- | --- | --- |
| 输入时间 | 异步 assessor 下评估前、评估中、建单后三种补充；无 assessor 的旧同步接单路径 | 持久保留，按既有批次或订阅处理，不无条件 fanout，不引入隐式配置要求 |
| 输入选择 | 同批前后顺序；忽略补充；撤回原请求；多个请求与多个已有工单 | 不误丢其他请求，不伪造 stop，不选择“最新工单” |
| 输入负向 | 孤立非 @；旧 filtered／ignored；未列名作者、机器人、contextOnly、其他群和跨话题 | 不新增工作，不回放历史，不借用 @ 的身份 |
| 权限变化 | 接收后／评估中撤权、移除群、材料读取权不足、输出路由变化 | 逐输入隔离，材料及输出拒绝继续生效 |
| 工单生命周期 | 人工停止后补充、正常完成后跟进、现有 worker 所有权 | 不恢复人工终止；正常 followup 不回归；核心 ignore 不抢 worker 输入 |
| 去重和重启 | WS／历史重复、未完成 pending 重启、事务回滚 | 一个消息 ID 不重复建单、交付或推进游标 |
| stale 恢复 | 另一工单启动、读取中变化、提交前变化、连续变化 | 旧结果不提交；最多两次刷新；成功只建立一张原工单 |
| stale 持久边界 | 额度落盘前后崩溃、自动 Eval 重排、拆批合批、暂停停止 | 额度不清零、不重复扣；同 Eval deadline 不延长 |
| stale 拒绝 | 假 stale 文本、旧 callback、撤权、失效材料、已被接管输入 | 不自动获得刷新资格，不绕过 ownership |
| stale 通知 | 成功、中间刷新、额度耗尽、发送前撤权、非 @ 补充 | 中间不误报失败；固定终局通知符合原路由；不泄露材料 |
| HTTP 真实合同 | 实际 SDK 的历史／话题／上下文／鉴权挂起、内部重试、正常响应 | transport 真的取消、正常返回形状不变、无后台残留请求 |
| 游标和健康 | 单容器超时、其他容器成功、停服中完成响应、源失去 owner | 不丢失败窗口、不越权提交，超时不报健康 |
| 连接生命周期 | connect 与 stop 竞争、旧连接回调、重复 stop、重启、暂停 | 停止期间无新入站写入，旧代回调不污染新连接，暂停仍能接收 |
| 进程管理 | wrapper 退出 child 存活、PID 重用、身份未知、真实退出 | 不误报停止、不误杀、不启第二实例 |
| 停服交叉操作 | restart、install／迁移、uninstall、patrol、backup | 共用相同退出事实，不绕过维护锁或用户停服意图 |
| 外发 | 已接受但响应延迟、停止前后排队、重复 stop、重启 | 本修复不引入重复发送；未知结果不能伪装已安全停止 |
| 跨来源与执行 | GitHub、私聊协调者、bot 预算、DSH 报告、材料与工作目录 | 既有行为保持，全套现有回归通过 |

主要测试位置为现有 `test/feishu-*.test.mjs`、`test/sources.test.mjs`、`test/source-runtime.test.mjs`、`test/assessment-*.test.mjs`、`test/context-requests.test.mjs`、`test/material-assessment-receipt.test.mjs`、`test/conversation-recovery*.test.mjs`、`test/service*.test.mjs`，以及内存核心和 SQLite 核心测试。新增测试文件只在现有分组不能清楚承载时使用。

## 9. 完整检查、发布、同步与回退

后续代码实施获准后才进入以下流程：

1. 核心执行 `npm run check`，含发布一致性、核心哈希、构建、类型、runtime、内存 core、SQLite core 和 package consumer；skill 执行其完整 `npm run check`。新行为需补精确发布包的兼容核验。
2. 检查工作区差异，拆清提交；CI 通过后按 [releasing.md](releasing.md) 发布同一干净提交生成的包。下一个 alpha 号以发布时 registry 为准，不预占版本，也不从 dirty 工作区打包。
3. 记录项目依赖、运行配置、服务包装、业务文件状态和旧工单基线。确认包装及子进程均退出，再做受支持的一致性备份。
4. 安装并验证准确的已发布包，更新匹配 skill；生成入口按目标项目要求同步。保留本地 knowledge、材料授权、群配置、环境引用、游标、已有工单与未提交业务内容。
5. 启动后核对新旧进程身份和 source 健康，执行下面的真实验收。没有需要新增的飞书权限，不借本次升级扩大群可见范围。
6. 回退不是直接重装旧包。先确认停止，再保留升级后输入／回执证据，按支持的 restore 流程核对备份与新增记录；不让旧包写入不理解的内部状态，不通过清游标、删工单或删 owner 制造“恢复成功”。

## 10. 真实验收与完成标准

只在后续授权的执行阶段，使用 lark-cli 和授权身份发送测试消息。每项使用新的可识别测试标记，不扫描或重发旧失败请求。

1. **快速补充：** 群 @ 后立即在同话题补充。证据必须说明补充在评估前、评估中还是建单后进入；核对其后续评估／输入去向，不能只看回复里出现相似文字。
2. **普通聊天与撤回：** 验证孤立非 @ 不建单；受控回归覆盖同批撤回与评估中撤回，真实验收不虚称后者一定抢在执行前生效。
3. **并发请求：** 两个独立话题先后发起请求，核对并发上下文变化的恢复、刷新次数和原请求工单数。故意反复变化、崩溃、撤权等故障注入在隔离环境完成，不破坏生产网络或权限。
4. **严格离线补收：** 先证明包装和子进程均退出，再发送 @ 与话题补充。指定测试消息首次入站须有历史 source 证据；WS 先重投的消息只能计入去重验收，不能冒充历史补收，应另用可证明历史首次接收的样本。若补充先被单独忽略、之后 @ 才到，按已声明的乱序限制记录，不为通过验收而偷偷重放。
5. **现有工单跟进：** 同话题非 @ 补充沿既有输入处理并回复原话题；不重复开单，不恢复人工停止工单。
6. **最新材料回归：** 使用已获准的未提交测试内容核对材料读取，确认本次没有改变工作目录选择或退回旧快照。结束后只清理本次可识别测试内容，保留原有用户改动。
7. **停服和最终状态：** 隔离环境验证历史请求挂起时的真取消与假退出防护；生产只做正常停止／启动核验，最后恢复原运行状态。

完成必须同时满足：已接受工作的消息 ID → source 入站 → pending／Eval → 工单／输入 → Outbox／平台回复可对应；合法 ignore／filtered 分支的证据止于相应判定，并确认无工单及无未授权主动回复；无额外配置；旧工单和业务基线不变；不依赖手工数据库修补；完整自动检查、精确包验证及真实验收均通过。若权限、模型语义或进程身份未能核实，分别记录局限，不将其折算为成功。

## 11. 明确留在范围之外

- 不把 @ 变成必建单，不把非 @ 都变成工作，不改原型的批次及工单所有权。
- 不增加“先到的孤立补充被忽略后，自动与迟到 @ 合并”的新历史恢复语义。
- 不保证评估中自然语言取消先于已经允许开始的执行；若要这种保证，需单独设计执行屏障，不能暗中加入。
- 不缩小全局材料摘要，不改材料读权限、输出权限和历史模型会话的隔离边界。
- 不重构 DSH、longrun、executor、workspace，不改变自动任务和长期任务设计。
- 不建立通用未知发送结果恢复系统，不增加强杀兜底。无法证实停止时，宁可明确报告未完成，也不能冒充已停止。

这些范围外行为中，前两项时间限制来自现有批次模型；全局摘要和在途外发限制来自现有安全与副作用边界。三项缺口修复不以消除这些限制为前提。
