# 工作流程可靠性与实际差距补齐计划

日期：2026-11-02（Asia/Shanghai）。状态：**W7–W14 已实现并进行有限验收，范围与保留限制见 [交付记录](workflow-reliability-delivery.md)**。

基线为已提交并推送的 js-superagent `f814f11` / `0.4.0-alpha.0`；上游为本次审读时的公开 main `6337fc823ce20251c8de8085948165c81aaa701e`。本计划接续 [W0–W6](workflow-alignment-plan.md)，使用 W7–W14 编号。上一轮交付及其证据保持历史记录；以下保留原实施要求，具体完成证据由交付记录区分 fixture、原生协议与真实模型。

## 1. 目标和范围

用户在 Issue/PR 或本地继续讨论时，系统能理解评论修改和审阅结论；协调请求不会因一次短暂错误永久停住；执行异常后能核对已经发生的工作和消息，再决定接续；协调者能补读真正需要的上下文；DSH Worker 能按项目规则工作，并在长命令期间及时处理新输入。

保留以下边界：

- js-superagent 独立维护工单、授权、渠道、存储、工作区、调度、验证和交付，无 js-agent-runtime 依赖，不加载上游 dsh-superagent 插件代管业务。
- CLI/SDK 工单入口、Codex app-server、DSH SDK、实例级 Harness Registry 均保留。原生协议与差异留在适配器，宿主只消费有证据的业务状态；不恢复已删除的 exec/headless/旧 Driver 引擎。
- 原样领域 core 原则上不改；优先修应用层接线和两个内置适配器。若确有核心问题，先单列原因，不能悄悄改写上游来源摘要。
- **生产后台保持停止。**计划和实施均不自动安装、启动、切换生产服务、迁移生产数据库或改变默认执行端；查询、导入 SDK、init 和消息入队不启动模型。
- 不做通用 provider/技能/联网平台、不新增 Harness、不接管 DSH 原生 UI、不自动合并、不安排飞书实测。
- fork PR 支持和任意动态子任务编排保持现有范围，作为后续产品选择；本轮补长命令的及时响应，不以开放全部原生能力替代它。

## 2. 差距到交付的映射

| 编号 | 当前缺口 | 本轮用户可见结果 |
| --- | --- | --- |
| W7 | 评论仅按 ID 去重；审阅状态过滤过多 | 编辑后的要求作为新版本进入原工单；批准、要求修改及撤销批准成为明确状态事实 |
| W8 | 协调事件普通失败后没有重试入口 | 同一事件可明确重试；可识别的短暂故障有限重试，已有动作不重复 |
| W9 | 内置适配器没有原生中断历史核对 | Codex/DSH 对可核对的中断沿原会话接续；不明外部结果有明确检查原因 |
| W10 | 实时投递失败同轮不再尝试；DSH 未确认回执阻断重开 | 确定未发送时重试；已消费、仍排队和结果未知分开处理，交接不双发 |
| W11 | 持续协调只能看近期摘要 | 可以定位旧工单并补读完整相关记录，再提出受限动作 |
| W12 | DSH 自动项目规则加载关闭 | 在授权工作区内加载适用项目规则，清楚记录实际使用版本 |
| W13 | DSH 未设置上游的短前台等待 | 长命令转后台后 Worker 可及时进入下一步；取消和结束仍收回所属进程 |
| W14 | 新状态、兼容和证据需要收口 | CLI/SDK/面板能解释当前状态、允许动作和真实支持范围，提供可安装包 |

建议实施顺序：**W7 → W8 → W9 → W10 → W11 → W12 → W13 → W14**。W9 先确定原生历史与回执核对合同，W10 复用它；W13 依赖 W10 的实时输入状态和既有任务管理。其余阶段可独立审阅，不另建统一大框架。

## 3. W7：GitHub 评论版本与审阅结论（优先）

### 评论编辑

1. 分离稳定的远端对象身份和事件版本。Issue 评论、PR 评论、行内评论/审阅以 repository、kind、native ID 定位原对象；按可靠原生更新时间/状态生成版本，并保存内容摘要。正文不是身份，编辑不改变作者或原讨论归属。
2. 同步调整轮询产出、事件规范化、ID 校验、链接拼接和 Webhook 触发后的同步。Webhook delivery ID 只负责投递去重，不能代替业务版本身份；轮询和 Webhook 对同一版本只接收一次。
3. 新版本在原工单授权下作为更正输入处理。旧版本已读取/已执行时保留历史，明确告诉 Worker 哪条要求被更正，不撤销已发生动作；尚未交付的旧版本可被更新版本替代并保留关系。迟到旧版本不得覆盖新版本；内容未变的重复观察不重复派工。
4. 编辑未接单或曾被过滤的评论时，按当前准入重新判断，不能一概假设它已属于工单；编辑已接单的原请求也不能无条件另开重复工单。权限、Mandate、PR head、取消状态继续检查。
5. 历史 ID-only 去重记录建立兼容映射。能证明已有文本/时间的直接对齐；不能证明的首次新同步建立基线，不批量重放旧评论，并提供明确重新评估方式。不能为了支持编辑删除旧去重记录。

### 审阅状态

持久记录审阅的 state、review ID、作者、commit/head、时间和正文。APPROVED、CHANGES_REQUESTED、DISMISSED 即使无正文也生成可读状态事实；空 COMMENTED 无新增信息可忽略。撤销批准和状态变化按版本处理。Worker 输入明确注明审阅状态，不能只传正文。

审阅结论仍服从人的身份、授权、目标 commit 和工单状态。批准不授予合并权限；普通批准不能解除未知故障或复活取消任务。当前 head 上合法审阅可继续待审阅工单；过期 head 记录为历史，不作为当前结论。

**文件：**`channels/github.mjs`、`channels/github-repository.mjs`、`github-intake.mjs`、`github-pull-intake.mjs`、运行时接收/去重与必要面板记录。

**完成条件：**一个小型表驱动 fixture 覆盖编辑、重复/乱序版本、旧记录基线及三种审阅状态；同一次编辑只生成一个有效输入，不重复开工单；空正文批准可被观察，合并权限不变。远端写入不作为默认验收要求。

## 4. W8：协调事件失败后的接续（优先）

1. 在现有协调收件记录上增加失败类别、尝试次数、下次时间、总截止时间、最后原因和处理代次。继续使用已有 owner、Store 事务和动作收据，不新增常驻队列服务。
2. 新增 SDK `retryCoordination(id)`、CLI `coordination retry <event-id>` 和面板重试按钮（最终命名在实现时保持一致）。只重新入队，不直接启动模型。保留原事件 ID、操作者、正文和历史；completed 事件返回已完成，不重复执行动作。
3. unsupported 只有修正适配器/配置且能力满足后才可重试；配置、权限、无效报告等错误要求明确修复。可确认的瞬时失败提供最多三次自动尝试和退避，自动协调重试作为独立显式设置，旧配置不增加模型调用。
4. 次数、期限跨重开保留；暂停/停止期间不领取，旧进程尚未退出不重试。状态过期重新研判也消耗有界预算，不能与网络重试叠成无限循环。单条失败不阻塞其他可处理工单。
5. 每次使用当前政策和有效上下文；提交动作重查事件代次、政策、已读记录及目标工单。原事件的同一动作通过稳定收据去重；已经提交动作但回传失败走 Outbox 对账，不能重做动作。
6. 旧 failed/unsupported 记录仍可查询，由明确重试接续，不在升级时批量唤醒。

**文件：**`runtime/coordination.mjs`、`index.mjs`、`coordinator.mjs`、CLI、管理接口和类型。

**完成条件：**虚拟时钟与一个模拟协调者覆盖短暂失败、重开、人工重试、completed 拒绝重复、暂停/停止、旧 owner 与权限变化；不重复运行真实模型场景。

## 5. W9：Codex/DSH 原生恢复核对

### 先确认协议证据

实施开始时只检查当前支持版本的本机协议/源码与少量历史样本，分别列出 Codex app-server 和 DSH SDK 可读取的会话、turn、消息、工具调用/结果、取消及 pending 输入信息。固定实际版本与解析合同，不自动升级原生 CLI。优先公开只读协议；若只能读持久文件，解析限制在适配器内并验证格式版本，不直接修改原生日志或队列。

使用现有可选 `inspectRecovery()` 扩展必要证据即可，不新建恢复平台。不能用“进程死了”“最后一条日志像成功”或错误正文中的 429 作为安全续作证明。

### 接续判定

| 核对结果 | 行为 |
| --- | --- |
| 原生轮次已完成，结果可关联 | 幂等接收尚未持久化的报告/输入确认，继续宿主验证/交付对账，不重复执行 Worker |
| 原生已停止，工具结果已配对，无未知外部动作 | 根据当前 autoResume 设置走原核心中断接续；同会话、工作区、授权，加入恢复说明 |
| 明确未开始的暂时启动错误 | 沿用启动前有限重试 |
| 可证明收尾的暂时模型/连接错误 | 在原生自身重试结束后进入已有宿主有界恢复，不重发原任务全文 |
| 原生仍活跃、工具结果缺失、身份/配置不匹配或日志不支持 | 停在需要检查，给出可操作原因，不开第二执行或替换会话冒充恢复 |

恢复前检查旧 owner/guardian、workspace/原生绑定、原授权、取消/暂停、新反馈、受管任务、采纳 journal 与交付收据。原生记录只能证明执行事实，不能提高任务授权。对已经完成的工具调用复用收据；没有收据的外部写入不能猜测成功或失败。

保留原有最多三次宿主尝试及共享截止时间；重开不重置预算，退避释放槽位。明确 stop/cancel 不因重开自动复活；查询/init 只呈现事实，核对与接续由显式 run/serve 或明确检查入口触发。人工 retry/replace 使旧自动计划失效。

**文件：**两个内置适配器、必要的原生记录读取模块、`runtime/recovery.mjs`、运行时中断恢复入口、类型与追溯投影。

**完成条件：**每个内置适配器至少证明一条真实格式、可核对的中断接续路径，并有 completed/unknown 的负向断言。仅模拟自定义 `inspectRecovery()` 不算内置能力完成。协议确实无法提供证据的分支须明确列为未补齐，不能把所有中断统一留人工却宣布本阶段完成；已知不安全情形保持人工是正确结果。

## 6. W10：实时输入投递与跨进程对账

1. 将发送结果区分为：确定未发送、已接收未消费、已消费、结果未知、永久拒绝。新增信息向后兼容；适配器没有提供证据时按未知处理，不能默认可重发。
2. 对明确未发送，例如执行端尚未就绪，按持久记录有限退避重试；初始 2 秒、上限 60 秒，并受当前执行期限和停止条件约束。当前轮次已结束则回归正常下一轮输入，不留无限重试任务。
3. 每个业务输入使用稳定 ID；尝试记录包含 assignment/run/session、native message ID、消费位置及版本。同轮重复请求复用收据，不按新 attempt 生成新业务输入。
4. 使用 W9 的原生核对：已进入历史则补确认；仍在原生队列则等待或使用原生支持的精确撤回后重投；确认不存在才重新交付。无法区分时保持未知，不写原生日志去伪造清理。
5. 在取消、重开、换 Assignment、替换会话和多条反馈竞争时，检查 owner/代次。旧回执不能确认新轮次输入；消费证据早于 RPC 返回不能被降级；旧最终报告不能吞掉更新要求。
6. 清楚定义“已读”：进入原生模型上下文的证据与报告/轮次完成的业务确认分别保存。Codex 现有 model-final-ack 仍有效，不强制它伪装为 DSH 的消息事件。失败回执不等于消息丢失，界面显示下一步。

**文件：**`#sendLiveInputs`、两个适配器的 sendInput/消费校验、回执持久化、输入状态投影与面板。

**完成条件：**一个脚本化协议场景覆盖未就绪后成功、接收后断连、读取确认丢失、换 Assignment 和取消；断点重开后消息不丢、不双发、不错误标已读。分别核对两个适配器支持范围，不扩展负载测试。

## 7. W11：持续协调的受限补读

1. 复用候选研判已有的受限读取循环与上下文服务，为 `handleEvent()` 增加 read 结果，再返回最终动作。读操作不是动作收据，不执行代码、不访问任意文件或网络。
2. 首次摘要保持小而有界，明确标注省略数量；提供按公开工单 ID、Issue/PR 链接或文字搜索定位旧工单的入口，不能只允许补读最初 100 条里的对象。
3. 可读内容限定为本项目工单/报告、输入、讨论、判断与必要源记录；分页、总字节、最多读轮数和总时间沿用现有预算机制。原生原始 transcript/凭据不直接暴露给模型；确有需要只返回适配器生成的必要事实。
4. 补读得到的目标加入本次允许动作集合，并记录 read-set 版本；提交前核对所有相关已读记录、政策与目标 Mandate。记录变化则有界重评，不根据旧摘要修改当前工单。
5. 普通进度/已发送结果保持不唤醒模型；问题仍归人回答，跨工单 note 只传事实。超出范围或读取预算不足明确说明，不臆造上下文。

**文件：**`coordinator.mjs`、`context.mjs`/现有读取服务、协调上下文装配与结果校验、类型。

**完成条件：**模拟一个不在初始摘要中的旧工单，能搜索、分页补读并正确返回一次动作；读取期间更新记录时拒绝过期动作；两个内置协调适配器共用合同。

## 8. W12：项目规则加载

本项只恢复编码工作所需的项目规则，不建立技能平台。

1. 先核对 Codex 当前原生规则读取行为和 DSH 固定版本的 agent-instructions 路径/层级规则。优先为 DSH Worker/Child 启用范围明确的原生读取；若原生无法限定范围，使用宿主的小型规则装配器。选定一条主路径，不能同时重复注入。
2. 首期以工作区中的 `AGENTS.md` 及该执行端已明确支持的层级/覆盖文件为范围；不顺带宣称支持所有 Agent 的配置文件。记录根目录规则与子目录规则的作用域，不能把一个子目录约定提升为整个项目规则。
3. 以实际 worktree/目录副本为边界，验证 realpath，拒绝符号链接越界和全局 home 的隐式继承；限量读取并在截断/冲突时给出提示。项目规则不能修改宿主授权、开启渠道发布或解除进程归属。
4. 将加载路径、内容摘要、作用域和原生版本写入执行追溯；已有会话按既有绑定策略处理规则变化，不能静默重复积累冲突指令。Codex 保留其正常项目读取行为并说明与 DSH 的实际差异。
5. 协调角色继续只读、无执行工具；不因 Worker 开启规则读取而向协调者注入无边界的项目指令。

**文件：**DSH profile/提示词装配、必要工作区规则解析、执行快照/绑定/类型与文档；Codex 只改确有重复或缺失的部分。

**完成条件：**一个临时项目含根/子目录规则和越界链接，检查适用范围、加载证据与权限优先级；一次受控原生调用确认实际 prompt 收到规则。不得仅以配置开关存在认定已生效。

## 9. W13：长命令期间及时接收反馈

1. 固定版本核对 DSH shell 和 job wait 的前台等待设置，Worker 使用约 5 秒的短等待，长命令转为后台作业；这个阈值不是整条命令的执行超时，也不能承诺 5 秒内模型一定回复。
2. 优先使用原生支持的超时/作业事件，由适配器将必要生命周期交给现有宿主进程/任务归属管理。不另建后台任务框架；原生作业若不能可靠枚举与收尾，则使用现有受管命令路径，并明确不支持的行为，不能直接放开无人监管的 daemon。
3. 后台结果回到原 Worker，同一命令不因转后台而重启。新消息在下一步可消费；ready 不能越过未完成普通任务。人工交接后只保留符合现有 preview lease 规则的预览，其他任务按当前合同清理。
4. 取消、timeout、替换 Assignment、宿主停止都应收回所属进程。保留受控子任务配置与资源限制，不为对齐这一项开放任意原生子 Agent。

**文件：**DSH profile、协议事件适配、必要的既有 jobs/guardian 接线；Codex 只验证相关合同不退化。

**完成条件：**一条约 8–12 秒的临时命令配一条运行中反馈，证明前台等待有界、反馈随后进入模型上下文、结果只交一次；同一受控脚本追加取消检查并确认无残留进程。使用模拟 provider，不做长时间观察。

## 10. W14：兼容、展示与有限验收

### 兼容和迁移

保留现有 `createProjectAgent()`、submit/run/reply/retry/cancel、GitHub 轮询/Webhook 和管理入口。新增协调重试、读取及原生核对能力在现有 Registry 合同增量表达；第三方适配器可明确声明不足，宿主不得偷偷换执行端。未知原生版本拒绝解析/自动恢复，并给出修复方向。

优先增加 metadata。若事件版本或恢复语义使旧包不能安全读取，提升必要的最低读取/schema 版本；先校验设置、修订与停止条件，再一致性备份并原子迁移。旧配置不启用新自动重试，升级不重放历史消息，不自动替换会话。迁移只在临时副本验收，生产保持原样。回退采用备份，不用旧包强读新状态。

面板和 details/trace 只补必要显示：评论修订/审阅结论、协调失败原因与重试、投递等待/已接收/消费证据/待核对、恢复尝试与检查原因、适用项目规则。避免让用户理解原生协议字段才能完成日常操作。

### 验收预算

| 类别 | 范围和上限 |
| --- | --- |
| 业务逻辑 | 每阶段一个小型表驱动/定向测试组，覆盖上述关键状态转换；仅复验修复影响的用例 |
| 原生协议 | Codex、DSH 各一个受控本地脚本，合并恢复、输入、规则读取断言；DSH 长命令加入同脚本。使用固定版本和模拟 provider/协议进程，不跑模型矩阵 |
| 真实模型 | 默认复用既有主链路证据；只有新协议/规则行为无法由上述方式证明时，最多两个短本地任务（每个执行端一个），不逐功能新建任务 |
| GitHub | fixture 验证编辑、审阅、乱序和 Webhook/轮询去重；默认不新增远端 Issue/PR、不做 CI 故障。若实施发现必须远端确认，先说明具体缺口，不恢复整套历史验收 |
| 静态与包 | 类型、core 来源摘要、相关语法、一次干净目录安装与 CLI/SDK 小检查；根项目规定的静态文档/技能检查和索引更新 |
| 面板 | 仅新增状态、按钮和权限拒绝的定向检查；不重跑完整浏览器验收 |

不运行完整历史 843 项、全平台/模型矩阵、长时间后台观察、全部 App/Webhook/预览组合或生产服务重启。每项证据标明是代码审读、fixture、真实 CLI + 模拟 provider，还是实际模型；不能互相替代。

### 收口标准

1. W7–W13 各自完成条件有证据，或明确列为未完成分支；不能只提供通用接口却声称两个内置适配器都已支持。
2. 同一事件、输入或外部动作在重投/重开后不重复，且权限或明确停止仍阻止接续。
3. 两个内置执行端和本地 CLI/SDK 保留可用；已删除旧引擎不回流，无 js-agent-runtime 依赖。
4. 交付源码、针对性检查、当前差距矩阵、迁移/使用说明与本地安装包。验收前冻结相关源码摘要；后续修改仅重验受影响项，不宣称旧真实证据覆盖新代码。
5. 后台最终只读核对为停止、无所属验收进程残留。没有迁移生产、发布 npm、自动合并或推送；提交/推送由后续明确指令决定。
