# Worker 输入交接与宿主故障通知修复计划

状态：P0–P7 已完成，alpha.13 已通过 GitHub 受信发布并同步获授权的目标项目；P8 本轮真实恢复及群聊验收已执行，保留 4 项严格历史首收覆盖缺口，不能标记全项通过。日期：2026-11-16（Asia/Shanghai）。包发布、部署和各项真实验收分别留证，本文件不把前两项视为最后一项完成。

本地验收：1,686 项 Node 测试、两组各 154 项 core/SQLite 测试及干净安装包检查通过。初始缺原文与缺通知测试均先复现失败；新增测试涵盖三种执行适配器、52 项宿主通知/证明场景及 4 项真实 GitHub 适配器的模拟远端场景。原型导入校验通过，生产 Engine 与三个 Driver 未修改。真实模型、飞书和原工单恢复在发布后分别验收，不以隔离通过代替。

发布后验收：原阻塞工单经检查后仅显式恢复一次，同工单、同会话完成，原补充实际消费并在原话题回复。真实群 @ 建单、建单前快速补充、运行中补充、完成后同工单跟进、当前未提交材料读取、非 @ 不建单及回复去重通过；真实历史轮询越过三个目标话题的验收窗口后，无重复工单或结果。独立复核 193 项中 189 项通过，4 项未覆盖均为离线样本被延迟 WebSocket 重投先收到，不能作为“仅历史补收首次接收”的证据。未改游标、强制轮询、增加额度或补跑替代样本。

验收原始记录保持不变。另有一条原始断言要求单次读取整份材料；实际跟进请求只要求重新核对大小、完整 SHA-256 和依赖版本，这些字段均有本轮真实工具回执，按请求语义复核通过，不声称未读取的中间正文已读。验收中旧话题出现一次传输超时并自然恢复；另观察到既有材料保护把确认回执撤回称为“原结果未发送”的措辞问题，随后真实结果已成功发送。这两项单独留证，不扩大本次修改范围或宣称已修复。收尾服务健康、无活动执行。

## 1. 目标与已核实事实

修复两个相连的宿主缺口：已归属工单、已分配给本轮执行的补充原文没有稳定进入初始上下文；宿主因缺少完整读取证明而阻塞结果后，普通飞书群没有收到对应故障通知。

验收中已确认：

- 原请求和补充均已接收，评估正常 accept/attach，没有再次耗尽评估刷新额度。
- 补充在 Worker 启动前已形成领域 Input，但 `host.messages` 只有根请求。执行者列出 Input 目录后没有读取补充原文。
- 初始 pack 约 2.7 KB，返回正文页约 24 KB，没有实际预算拒绝；“exceeded the verified context budget” 是未读保护的通用文案，不能据此判断额度不足。
- 原生执行返回 ready；宿主最终门禁将其覆盖为 blocked，保留未读输入。故障分类在这一覆盖之前计算，因此没有保存相应宿主故障类别。
- 本轮工作事件为 recorded、requiresCoordination=false；只有接单回执，没有故障／结果的待发回执。未回复发生在入队之前，不是飞书发送、权限或 transport 失败。

公开测试只使用合成项目、消息和身份。真实群、工单、消息 ID、原生日志及项目材料留在目标项目专属运行时证据目录，不复制到本仓计划、测试或发布说明中。

## 3. 组件改动边界

| 组件 | 本版工作 | 不改变的职责 |
| --- | --- | --- |
| js-superagent 宿主 | 本轮输入投影、最终未读故障分类、可信故障 notice 入队及发送前检查 | 不替模型做业务判断，不扩大授权，不创建替代工单 |
| 共享 Worker context | 优先呈现本轮原文，准确说明完整／截断／未呈现的覆盖事实 | 保持初始字节、条数、分页与总读取限制 |
| 受限读取工具 | 保留读取证明；仅在需要准确诊断时记录受信预算拒绝事实 | 目录、note、Input 元数据不升级为用户原文 |
| DSH／Codex app-server／Cursor 适配器 | 验证共享 pack 和消费证明契约；仅必要时适配内部投影字段 | 不改原生进程、Session、acknowledgement 或恢复协议 |
| Engine | 无生产修改 | 保持 Input、Assignment、Mandate、reply、retry、stop 语义 |
| 协调者／assessor | 能查询宿主保存的故障与回执事实 | 不为本故障增加模型回合，不代读补充、不自动恢复或重复通知 |
| Outbox／渠道 | 复用原持久队列、排序、权限复核、撤回与传输重试 | 不增加重试、轮询、来源范围或新发件身份 |
| js-superagent-skill | 发布时补准确版本兼容声明、测试和运维说明 | knowledge 不承载运行中输入，不复制状态机或接管通知 |
| DSH 内核、js-agent-runtime、js-longrun | 不修改依赖源码或职责 | longrun 的冻结输入、核验、结算不变 |
| lark-cli | 后续已授权的身份检查、真实发送及 bot 回读验收 | 不成为生产消息消费者或故障发送兜底 |

不恢复已退役的 `codex` exec 或 `dsh-headless`。自定义 Driver 沿用声明的能力，不静默授予 bounded context 能力。

## 4. 固定行为合同

### 4.1 当前执行输入视图

修改落点：[src/index.mjs](../src/index.mjs) 的 `#execute()`、`#workerResources()`；共享纯投影逻辑可提取为小模块，不能形成第二个状态库。

1. 在既有 `#reconcileUncertainInputs()` 完成后，以经核对的 `execution.inputs` 为本轮待消费名单。保留原 run、Assignment、领域工单及原生会话身份。
2. trigger 类型 Input 使用 Store 中同一原 Trigger 的正文、ID、时间和来源事实，形成可被所有现有驱动使用的 message 记录。`input.note` 只是路由说明，不能代替正文或增加授权。
3. 已有 message 优先保留原 ID／版本形状；按原 triggerId 稳定去重。新增原文记录使用稳定 ID，不通过重排旧记录改变索引派生 ID，避免使旧消费证明失配。
4. 现有普通 fanout、评估 attach、历史已附加但未处理的输入通过同一投影获得正文；不在 attach 时再维护一套持久消息副本来补洞。
5. 保留 context-only、retired/superseded、bot gate 和当前授权限制。已退役、未分配、仅供背景或未知投递的记录不得因进入视图而成为本轮执行指令。
6. 找不到原文时保留可诊断的缺口，不从摘要猜测、不自动清除 Input、不虚记已读。
7. 生命周期 Input 仍是独立事实，不能用它的 triggerId 代替原消息消费。已消费的历史生命周期记录不挤占当前必读输入。

### 4.2 有界打包及真实消费证明

修改落点：[src/runtime/worker-context.mjs](../src/runtime/worker-context.mjs)，必要的类型同步在 `src/index.d.ts`；[src/runtime/agent-tools.mjs](../src/runtime/agent-tools.mjs) 维持读取核验。

- 不增加现有 `initialBytes/pageBytes/readBytes/maxReads`，不提高初始消息条数限制；完整授权范围仍不可截断。
- 在现有空间内优先安排本轮待处理原文，再安排历史消息与报告；优先级不改变原文时间或业务顺序。
- 覆盖说明分别表示历史列表省略数和本轮输入完整／截断／未呈现的事实。`omittedMessages=0` 不再被当成全部本轮输入已交付的证据。
- 未完整呈现的正文提供受限、版本化、实际可读的引用；引用自身也服从预算。工具资源、只读 manifest 和初始 pack 来自同一投影，不能展示不可读取的引用。
- 默认沿用 bounded-context v1 的可选内部扩展，不新增用户配置或适配器能力等级。只有契约测试证明必要时才调整内部类型；不得借机升级会话权限或更换会话。
- `contextDelivered` 只确认实际投递的完整卡片；`contextConsumption()` 仍区分 Input 元数据、生命周期事实和用户原文。完整同版本分页才形成原文消费证明。
- DSH 继续依赖匹配的入队回执及原生 user/message；Codex app-server、Cursor 继续在各自已验证的完成边界确认初始卡片。Cursor 没有原文工具读取证明时，截断正文仍须阻塞，manifest 文件存在不能视为已读。
- 本轮启动后新增输入继续走原实时投递／后续派发路径；未知投递仍先核对或 adoption，不能被重新塞进初始 pack 绕过检查。

### 4.3 未读故障分类

修改落点：`#execute()` 最终报告门禁和提交事务；可增加小型纯 helper，避免将分类散落于不同通知分支。

- 保持现有最终未读判定和拒收范围；不顺手改变各 report state 的读取要求。
- 当且仅当宿主实际发现本批次有缺少完整消费证明的必读输入时，生成受信故障，例如内部 `code: WORKER_INPUT_UNREAD`、`origin: host-context-unread`、`requiresInspection: true`。
- 分类与最终 report 覆盖一致保存，解决“先算 failure，后改 blocked，最终缺 failure”的顺序问题。已有权限、停止、会话身份等更强拒绝不能被新分类掩盖。
- 保留 blocked、原未读 ID 与原生执行记录；兼容视图仍可投影为 failed，不改变领域 outcome，不删除原输入。
- 固定摘要准确说明必读原文未完整消费。只有宿主记录了实际预算拒绝才附预算原因；不能匹配模型／异常自由文本来认定超预算。必要诊断限定 ID、总数和原因，不存正文、任意堆栈或凭据。
- 不标为 `business` 来获得普通人类跟进续作，也不冒充 `native-execution` 进入原生报告自动修复。既有恢复次数、截止时间与配置保持。
- 明确本地 `retry` 仍可在人工核对后恢复原票；新增故障类型不会自动 inspect/adopt 已被宿主拒收的原生 ready，也不会引入新的审批循环。

### 4.4 受限宿主故障 notice

修改落点：`#execute()` 结果提交、Outbox 的现有授权接线；建议新增 `src/runtime/host-failure-notice.mjs` 保存固定模板、证明和校验。不修改 `src/core/replies.ts`。

**触发范围固定为本版宿主确认的必读输入未消费故障。** 普通业务 blocked/failed、waiting、progress、模型声称同名 code 或历史错误字符串均不触发新路径。

入队合同：

1. 由宿主故障记录建立 `kind: notice`，与 blocked 报告、故障证明和待发动作在同一事务提交。网络发送仍在事务外。
2. 证明绑定原领域／公开工单、Assignment、run、原因、原来源身份与原渠道、固定模板及内容摘要。正文只表达本轮未完成、输入保留及现有检查恢复路径，不转发模型 ready、补充正文或材料结论。
3. 目的地使用可信的原请求渠道。仅原始持久记录能证明等价原目的地时才沿用既有回退；无法证明则保留不可送达原因，不用当前配置猜测。不选择最后一条补充的渠道、不广播订阅话题、不转发到操作者私聊。
4. 同一故障与目的地使用稳定 receipt ID；同一提交回调重入、重启和传输恢复复用原回执和文本。不按模型措辞或当前时间制造新消息。
5. 该通知不依赖 `more === false`，因为未读输入会继续待处理；但通知不消耗 Input、不闭单、不构成 attention/answer/result 或恢复授权。
6. 与已有 GitHub failure notice、operator 通知及真实 attention 路径统一判重：一个故障在同一目的地只由一个发送责任方处理。不为这一宿主故障追加协调者模型回合或重复通知；其他业务报告路径保持原样。

发送前合同：

- 验证故障确实存在、证明与消息未被修改、原身份和当前授权仍成立；工单人工停止、源关闭、应用／租户／群身份变化时不转投其他目标。
- 参考现有材料撤回 notice 的固定模板和宿主证明模式。固定无材料事实不依赖文件正文新鲜度；这不等于所有 notice 豁免材料保护。包含任何材料结论的消息继续使用原披露检查，模型或篡改文本不能获得例外。
- 证明需绑定应用与租户等原始路由身份，不能仅凭同名群或当前 operator 配置接管旧通知。
- 已开始新恢复回合或后续状态已取代旧故障时，撤回可以证明尚未发起网络发送的旧故障通知，避免迟到通知误称当前仍阻塞。`pending` 本身不证明未发送；in-flight 或响应丢失的请求保留未知／在途事实，不创建替代消息、不声称远端已撤回。已被远端接受的消息保留真实送达事实。
- 沿用现有 Outbox 顺序、退避、幂等键和不可送达语义；未知发送结果不生成替代回执，不新增重试次数或发送循环。通知自身失败不递归生成通知。
- 本地保证同一故障的持久回执唯一，远端去重沿用渠道现有能力并实测。不得将此扩大为任意网络故障下外部副作用恰好一次的承诺；没有可信证据时保留未知状态。
- 协调者和诊断区分 recorded、queued、sent、dropped；排队不等于已送达，送达不等于恢复。

### 4.5 历史与升级

- 不改写旧 Input、已读记录、错误报告、原生上下文快照和发送回执；不为旧记录补造已读或故障证明。
- 新投影只用于新开始的、合法恢复的执行轮次。没有本轮输入清单的旧合同维持原语义，不能把全部历史输入猜成待执行列表。
- 新 notice 只由新产生的可信故障创建。升级不扫描旧 blocked 批量补发，不解析旧英文文案来伪造类型。
- 计划使用现有元数据扩展，无数据库 schema 或历史游标升级；若实施发现必须迁移，先回到计划审查，不临时扩大范围。同 schema 不代表旧包可安全写回新状态。
- 本轮旧阻塞工单没有 failure 元数据。先人工核对已有原生轨迹、进程／作业退出、外部交付和未读归属，再显式 `retry` 原 ticket 一次。不能声称现有 `session inspect` 自动完成了原生执行核验，也不能 `reevaluate` 原根候选或新建工单。
- 恢复保留原票、会话和工作区；如现有检查发现未知副作用、会话不匹配或未知投递，停在原恢复边界，不自动换会话或继续尝试。

## 5. 实施顺序与交付物

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| P0 冻结合同与重现 | 用合成 fixture 固定 attach-before-run 漏原文、未读阻塞缺分类／缺群 notice；记录基线和原型证据 | 修复前针对性测试能确定性失败；不调用真实生产运行态 |

| P2 受信故障分类 | 最终未读故障、准确摘要、有限诊断、恢复语义 | 不误触发 business/native 自动恢复；原状态和读屏障保留 |
| P3 原渠道 notice | 固定证明、事务入队、发送前身份核验、旧通知取代及跨路径去重 | 故意漏读时保留 blocked，并且原目标最多一条固定故障通知 |
| P4 交叉回归与文档 | 三驱动、实时／恢复、材料、其他报告路径、Outbox 故障与兼容测试 | 下节全部强制项通过；更新实际行为文档，不将计划当验收结果 |
| P5 包与 skill | 下一准确补丁版本、CHANGELOG、候选 tarball、skill 精确兼容及测试 | 全量检查、干净消费者、skill 候选包检查通过 |
| P6 提交与受信发布 | 独立审阅、PR／main 检查、GitHub OIDC 发布、签名和来源核验 | 准确 registry 包匹配冻结源码与 tarball，发布与部署分别记录 |
| P7 项目同步与原票恢复 | 停稳备份、准确安装、保留配置、恢复原服务、显式恢复原票 | 原补充被验证消费、原单完成、真实原话题回复一次 |
| P8 完整真实回归 | 在线／离线／话题／当前材料／回复及重叠去重 | 逐项真实证据与限制齐全；留存明确 pass／fail，服务按原意图收尾 |

P1 与 P2/P3 的隔离设计和测试可并行，最终提交点、输入证明和输出授权必须一起审阅。用户已授权 P6–P8；仅在前置检查通过后依次提交、发布、部署和恢复，实际结果单独记录。

建议提交分组：输入交接及契约测试；故障分类与 notice 及负向测试；文档／版本／包验证。skill 单独提交其兼容和运维改动。各仓库只提交本任务文件，不夹带目标项目原有业务改动。

## 6. 强制测试矩阵

| 维度 | 正向断言 | 必须保留的拒绝／边界 |
| --- | --- | --- |
| attach-before-run 与普通 fanout | 同一原 trigger 原文一次进入当前批次；原消息身份及范围一致 | note／目录／Input 元数据不能替代正文 |
| 原有已附加 Input、多个补充、原始批次 | 无需数据迁移即可在新轮次展示未读原文 | 不把历史已消费、未分配输入变成本轮指令 |
| record ID 与版本 | 旧回执 ID 可匹配，新记录 ID 稳定 | 不因排序、重建视图或结束时换新证明消除版本冲突 |
| 预算／条数／长原文 | 当前输入优先，未完整展示有可读引用 | 保持现有限额；截断和不完整分页不能标已读 |
| lifecycle 与 trigger | 两类输入分别形成消费证明 | 读 resumed／policy 元数据不能代替原用户消息 |
| 实时输入／启动竞态 | 一次初始交付或原实时交付，消费归属正确 | 不重发、不漏单、不借另一轮／另一会话证明 |
| 退役／旁观／机器人 | 原有授权和过滤继续适用 | 不恢复 superseded 输入、不升级 context-only 或 bot 权限 |
| 原生投递证明 | DSH、Codex app-server、Cursor 各自契约通过，保留经身份核验的交付与消费协议 | 单独 ack、manifest 存在、失败／取消前未消费的消息不能算已读 |
| 最终门禁和故障分类 | 宿主未读生成明确故障，保留原 Input | 不误称预算不足，不将业务／权限／取消错误覆盖为本故障 |
| 通知入队原子性 | 报告、证明、receipt、effect 同成同败 | 回滚、重复回调、重启不生成第二份通知 |
| 通知身份与内容 | 原 run 的固定事实发到原合法渠道 | 模型伪造 code、改正文／路由、多渠道广播均拒绝 |
| 状态与通知竞争 | 后续恢复取代可证明未发的旧通知；已发送事实保留 | pending／in-flight／响应丢失不能虚称未发或远端撤回；取消／撤权优先，旧失败不冒充当前状态 |
| 材料与路由 | 固定无正文事实按严格宿主证明处理 | 不以 notice 名义泄露正文，换 app／tenant／群不能接管旧通知 |
| 其他报告路径 | ready、attention、answer、GitHub、operator 正常行为不回归 | 普通 blocked/failed/progress 不获得新外发许可；不重复发送同一故障 |
| 显式恢复 | 新旧未读失败核对后 retry 原票，新 Assignment/run 读取原输入 | 重启不自动执行；不 adopt 被拒收 ready；重复 retry 不多建 Assignment；群不新增恢复权限 |
| 传输与历史兼容 | 同一 receipt／幂等键恢复；旧记录仍可查 | 结果未知不换 ID 重发；旧 blocked 不补造 notice；不可送达不转私聊 |
| alpha.12 评估回归 | 无关读取不耗尽评估刷新，真实依赖变化仍受检 | 两次刷新与原截止时间不变；知识／材料／会话隔离不放宽 |

优先复用 `lifecycle-context-runtime.test.mjs`、`live-input-runtime.test.mjs`、`dsh-context-delivery.test.mjs`、`codex-app-server.test.mjs`、`cursor-agent.test.mjs`、`conversation-recovery-contract.test.mjs`、`ticket-recovery-contract.test.mjs`、`feishu-runtime.test.mjs`、`operator-channel.test.mjs`、材料与 Outbox 既有测试；新增少量独立输入投影和可信故障通知测试。以当前仓库实际文件为准，不恢复退役适配器测试来制造兼容性。

## 8. 真实验收与收尾

### 8.1 分开验证正常消费和故障兜底

- 隔离测试使用真实宿主、受控执行适配器和模拟渠道，故意只读目录／不读正文，证明仍 blocked、原输入未消费、固定 notice 一次入队／送达，以及重启／传输重复不产生第二条。不得为制造负例修改生产 Driver 或预算。
- 原生驱动契约测试验证新初始投影实际传入对应原生回合；真实 DSH 正向样本再验证原文标记、读取证明和最终报告。受控负例不能声称真实模型必然漏读或真实飞书已触发故障通知。
- 若真实验收自然出现未读失败，保存原样本并验证固定通知，不自动恢复以美化自动通过结果。其他新故障先界定原因，不无限扩大本补丁。

### 8.2 原失败工单恢复

先只读核对原票状态、未读 Input、原生会话及执行轨迹、工作区、已退出进程／作业、待交付和权限。满足现有恢复条件后，通过公开本地入口明确 retry 原 ticket 一次；原候选已经有工单，不 reevaluate，不发送替代请求。

检查原 ticket 和原 session／工作区身份保留，新 Assignment/run 实际获得并消费原补充；原失败与旧回执保留；新报告包含该原补充要求且准确读取当前获准未提交材料；bot 身份从原话题读回真实结果。旧失败不会因升级补发通知，这与新故障通知测试分开报告。

### 8.3 完整飞书矩阵

使用既有授权身份和 profile；发送用明确 user 身份，回读用同应用 bot 身份。不得以普通文本机器人名字代替平台 mentions。

1. 在线群 @ 建单；立即补充；证明首次接收早于建单，初轮报告在任何后续重述前已经含原补充要求。
2. 运行中补充、完成后跟进沿同一工单；普通非 @ 根与未授权消息不建单。
3. 全部活动执行停稳后正常停服，证明原父子进程退出；离线群根 @、其补充，以及已发现但未订阅话题中的首次 @／补充在停服期间没有本地入站记录。
4. 启动原服务，等待自然实时／历史恢复。逐条记录 firstReceivedVia；WS 重投先收不能记作 history-first。不得清游标、手工 poll、注入消息或重复发送来改变结果。真实历史首次接收覆盖不足须标明，不能宣称完整纯历史矩阵通过。
5. 核对所有输入唯一归属、原文消费、新旧工单数量及当前未提交材料版本／哈希；未读、旧 worktree 或旧报告不能代替本轮事实。
6. 从平台读取完整话题，将每条 bot 消息映射到唯一回执及实际报告／宿主通知。区分接单 ack、故障 notice、问题和最终结果。
7. 保存 settled 快照，等待每个目标话题的自然历史游标都越过该快照区间，再比较工单、输入、评估、回执与平台消息；同时排除 settled 之前已经出现的重复正文，不能只比末尾 ID 集合。
8. 收尾核对服务、实时、历史和活动执行；保留所有失败和 transport 告警，不清状态或谎称已根治。临时观察器退出，原服务保持原运行意图，业务文件不因测试改变。

### 8.4 完成标准与停止条件

- 源码完成：P0–P4 强制测试全部通过，原型和组件边界审阅没有未解决问题。
- 发布部署完成：准确包与来源可核验，skill 兼容检查及目标项目不变量检查通过，原服务恢复。
- 原票恢复完成：原未读输入形成真实消费证明、原票完成、原话题实际送达结果。
- 真实回归完成：按各样本实际路径逐项报告。业务失败、未送达或历史路径未覆盖不能被健康快照、接单 ack 或原生 turn completed 抵消。
- 新回归失败保留原状态与证据，不自动 retry、不新建替代工作、不提高额度。若超出本计划范围，完成只读定位并单独说明，不能把未全过写成通过。

最终交付说明分开列出源码测试、发布／部署、原票显式恢复、新请求自动流程及未覆盖／未通过项，并链接项目本地证据。计划完成不自动授权现在开始这些实施动作。
