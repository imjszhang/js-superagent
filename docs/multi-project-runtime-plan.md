# 多项目独立运行实施计划

状态：M0–M6 已完成实现与有限定向验证，工作区版本为 `0.9.0-alpha.0`／schema 10；实际用法、验证范围和边界见[操作与交付说明](multi-project-runtime.md)。本文件保留基于 2026-11-03 工作区 `643a90ba` 后检查制定的设计要求，其中“拟议”指制定计划时的接口；最终行为以实现说明为准。未升级生产状态或启用主仓库后台，真实双项目长期运行尚未验收。

## 1. 产品定位与完成目标

**js-superagent 是项目级的持久 Agent 运行时。** 每个项目拥有自己的配置、工单、数据库、工作区、执行会话、日志、凭据引用和后台服务。用户可以在多个不同项目中分别安装、启用自动启动、暂停和卸载，操作一个项目不会误操作另一个项目。

保留 CLI/SDK 工单入口、Codex app-server、DSH SDK、GitHub App、专用 GitHub 用户和轮询/Webhook。继续独立于 js-agent-runtime。适配器遵循各自真实能力，不强行统一原生会话、登录或恢复实现。W18 原生待处理队列自动唤醒继续暂缓。

本轮补齐五类实际问题：同仓库重复接单、Webhook 端口冲突、共享账号通知扫描互相影响、复制/移动后的身份混淆，以及多个项目的总执行量失控。保留已经有效的项目隔离，不重写领域内核。

完成后的默认体验：

- 不同项目、不同 GitHub 仓库可以各自运行、重启恢复，停止其中一个不影响其他项目。
- 同一个项目的 CLI、SDK、后台不能同时争抢执行权；只读查看与纯本地提交不因此失效。
- 同一本机用户下，同一个 GitHub 仓库默认归一个项目接单和回传；配置冲突给出明确归属，不以重复评论的方式暴露问题。
- 轮询不需要监听端口；Webhook 地址稳定且冲突可诊断；错误配置不会导致后台持续快速重启。
- 复制项目与搬迁项目是两个明确操作；不静默继承别人的工单和服务。
- 可以显式设置本机总执行上限，任务等待时仍可收件、查看和取消。

## 2. 架构边界

### 项目状态与本机协调分开

项目的 `.js-superagent/` 仍是业务状态的唯一来源。新增一个**当前操作系统用户的本机登记库**，仅协调身份、归属、租约和资源，不保存工单正文、模型会话或密钥，也不新增常驻中央进程。

| 位置 | 保存内容 | 生命周期 |
| --- | --- | --- |
| 项目 `.js-superagent/` | 配置、工单、会话、游标、执行记录、服务配置与凭据引用 | 跟随项目，沿用备份/迁移机制 |
| 项目本地实例标记 | 实例 ID、规范化根目录、状态身份、格式版本 | Git 忽略；显式初始化或迁移时创建 |
| 当前用户本机登记库 | 项目位置、仓库归属、运行租约、端口声明、可选执行槽位 | 可检查、修复；不随 Git 克隆 |
| Codex/DSH 原生目录 | 执行端自身的登录、设置和会话 | 按适配器能力管理，不冒充统一可迁移数据 |

登记库使用 Node 内置 SQLite 和短事务，复用现有技术栈。默认放在系统用户状态目录：macOS 的 `~/Library/Application Support/js-superagent/`，Linux 的 `$XDG_STATE_HOME/js-superagent/`（未设置时使用 `~/.local/state/js-superagent/`）。目录和文件仅当前用户可访问；路径由宿主在创建适配器子进程前固定，不能被 DSH 的隔离 HOME 改写。生产进程使用同一个默认目录；测试通过依赖注入隔离，不提供随意换目录绕过冲突的普通配置。

导入包和只读命令不创建登记库。初始化、显式升级或第一次已授权的运行建立所需记录。登记库损坏、归属不明或协议不兼容时，暂停需要协调的副作用，仍允许查询、诊断和停止；不能静默退回无保护运行。重建前盘点活跃进程，不能删库后假定所有资源空闲。

### 保证范围

本轮保证范围是**同一机器、同一操作系统用户、采用新协调协议的 js-superagent 实例**。本机登记不能约束另一台机器、另一个系统用户、手工运行的第三方程序或已运行的旧版本。

一个远端仓库跨机器只部署一个自动执行者，作为本轮运维约束写入文档和诊断说明。跨机器高可用、分布式锁、中央任务平台、同仓库多项目分区接单不纳入本轮。不同 slash 命令、Issue 白名单或不同机器人账号不构成完整分区证明，尤其不能隔离所有 PR/审阅反馈。

## 3. 实施顺序

使用独立编号 M0–M6，避免与历史 W 阶段混淆。每阶段同时交付实现、公开类型、必要 CLI/SDK 接线、定向检查及说明。

| 阶段 | 交付 | 依赖 | 完成标准 |
| --- | --- | --- | --- |
| M0 | 项目实例身份、本机登记和公共执行租约 | 无 | 两个独立项目互不阻塞，同项目多入口只有一个执行者 |
| M1 | GitHub 仓库归属与重复接单防护 | M0 | 同仓库冲突在宿主副作用前被阻止，停止/重启不丢归属 |
| M2 | Webhook 端口与后台启动失败治理 | M0；接入 M1 的冲突错误 | 两项目端口冲突可诊断，永久错误不造成快速重启循环 |
| M3 | 按仓库读取专用账号通知 | M1 的渠道边界 | A 仓库通知量不耗尽 B 项目的扫描页数，游标可接续 |
| M4 | 新实例初始化与原项目搬迁 | M0–M2 | 复制不会隐式接管，搬迁可恢复/回退且保持停止 |
| M5 | 可选的本机总执行上限 | M0；复用 M4 的实例归属 | 多项目遵守上限，等待可取消，崩溃不遗失槽位归属 |
| M6 | 升级、诊断、文档和有限验收收口 | M0–M5 | CLI/SDK/两执行端兼容；明确已验证与未验证范围 |

按 M0 → M1 → M2 → M3 → M4 → M5 → M6 实施。优先完成前四项，之后处理迁移和资源控制；不以资源控制为由拖延接单防重。

## 4. M0：项目身份与公共执行租约

### 身份定义

- 保留现有 `projectId`、工单 ID 和历史回传标记，不能在普通升级时重新生成。
- 增加本地 `instanceId` 和根目录标记，区分“这个项目的历史身份”与“这个路径上的本地实例”。状态库关联同一实例，复制整份状态不能绕过检查。
- 根目录使用真实路径；同一路径的符号链接视作同一实例，同名但不同路径的独立项目视作不同实例。
- 首次纳管旧项目时核对现有服务 owner、manifest、状态库和登记记录。证据冲突时保留原数据并要求选择 M4 的处理路径，不自动抢占。只有配置、没有本地状态的新 checkout，也须明确初始化实例；不能因为配置里的 projectId 相同就把它当成已有运行者。

### 执行边界

新增内部协调模块（拟为 `src/runtime/coordination.mjs`）和公共副作用入口。租约保护必须在运行时层实现，不能只加在 `service start`：

| 路径 | 处理 |
| --- | --- |
| `run`、`serve`、SDK 调度、管理界面触发执行 | 取得项目执行租约 |
| 来源轮询、GitHub 同步、Webhook 消费、Outbox、手工交付 | 复用当前租约或短期取得租约；涉及 GitHub 再校验 M1 归属 |
| 恢复、验证、子 Agent/托管任务启动 | 在实际启动/发送前经过同一入口 |
| `status`、列表、日志和只读面板 | 不取得独占执行租约，不启动工作 |
| `submit`、`reply` 等纯本地入队 | 仍可并发提交，沿用本地事务；后续执行由持租约者推进 |

租约保存 owner token、递增代次、PID、进程启动身份、本机启动标识和心跳。取得、续期、释放通过事务比较所有权；旧进程不得释放新进程的租约。SDK 同一进程内的多个实例也必须区分，嵌套调用复用租约而不是自锁。

心跳过期只是检查线索，不能单靠超时/PID 抢占。原进程或其受管子进程仍活跃时，不启动新的冲突执行者；无法证明已退出时显示待核对。暂停/取消停止新派工，确认所属执行与子进程退出后释放。新副作用前复核代次；失去租约时阻止继续发送和启动，按已有进程归属规则收尾，不按程序名批量杀进程。

GitHub 请求和模型工具一旦已发出，不能通过本地代次撤销；继续沿用既有意图、收据、远端读回和未知结果处理。不得把本机租约描述为跨系统的恰好一次执行。

主要修改：`config.mjs`、`index.mjs`、`sources.mjs`、运行时公共入口和公开类型；不重写领域 `core`。

## 5. M1：GitHub 仓库归属与防重复接单

为本机 GitHub 处理建立两层约束：**持久仓库归属**标明由哪个项目负责，**运行租约**标明当前谁在推进。停止服务只释放运行租约，不自动让其他项目接管仓库。

1. 使用 GitHub 主机和经核验的 repository ID 作为最终归属键，规范化 `owner/repo` 作为查询信息和核验前的临时冲突键。仓库重命名不能绕过；不同账号/App 指向同一仓库仍然冲突。不因此扩展目前未支持的 GitHub 主机能力。
2. 安装、配置保存和 doctor 展示已知冲突；第一次启用 GitHub 执行以原子操作建立归属。配置可以被保存用于准备，但不能在冲突状态下执行。
3. 覆盖自动接单、显式 `github sync`、已绑定 Issue/PR 反馈、CI 接续、Webhook 消费和结果回传。不能只锁“创建新工单”而允许第二个实例继续发送。
4. 发生冲突时返回稳定错误码、归属项目路径及处理办法；其他项目继续运行。本项目仍能查看、纯本地提交和停止。要继续本地执行，须明确关闭 GitHub 功能，不静默改变运行模式。
5. 一个项目内的轮询与 Webhook 继续共存，共用现有事件去重；多个 worktree 仍归源项目运行时，不各自注册接单者。
6. 改仓库时先暂停相关入口并清点原仓库工单、Outbox、未知发送结果；未处理完不自动释放旧归属。释放须确认无活跃执行和未决远端动作，不提供跳过检查的普通 `--force`。
7. 跨项目移交仓库必须明确执行释放/重新绑定，保留审计记录。它不等于迁移工单；新项目建立明确的发现基线，不重放旧任务。需要保留全部接续状态时，使用 M4 搬迁原项目。

新增拟议 CLI：`github binding status`、`github binding release --plan/--apply`，并提供等价 SDK 方法。释放操作只修改经核验属于本项目的登记，不删除远端 Issue/PR。默认不实现同仓库多实例分区或接管模式。

主要修改：渠道接入、`runtime/repository-source.mjs`、`github-intake.mjs`、`sources.mjs`、`delivery.mjs`、公共 Outbox 路径和状态展示。

## 6. M2：端口与后台启动失败治理

### 稳定端口

- 轮询仍是默认方式，不增加监听器。管理界面和内部 DSH 工具继续使用动态端口。
- 保留已有显式 Webhook 端口；新安装增加拟议 `service install --mode webhook --port auto`，在安装时选择并保存一个具体端口，之后重启沿用。不在每次启动时随机改地址。
- 自动选择先检查本机登记和实际占用，再保存项目端口声明；绑定失败始终以操作系统实际结果为准。声明不等于已占用 socket，处理预检与启动之间的竞态。
- 检查通配地址、IPv4/IPv6 等可能重叠的监听范围。显式端口被其他项目或外部程序占用时给出清楚诊断，不自动终止对方。
- 安装后端口被抢占则阻塞并提示重新选择；端口改变时列出需同步的 HTTPS 转发配置，不自动更改远端 App 设置。

GitHub App 的事件发往 App 设置中的 Webhook URL；多个本地监听器不会因此自动获得各自仓库的事件。本轮默认用轮询支持多个项目；共用 App 且必须用 Webhook 时，需要已有外部入口按仓库路由，或分别配置 App。不新增共享 Webhook 网关，也不让某项目覆盖其他项目使用的 App 回调。依据：[GitHub App Webhook 说明](https://docs.github.com/en/apps/creating-github-apps/writing-code-for-a-github-app/building-a-github-app-that-responds-to-webhook-events)。

### 启动状态

启动分为检查 → 取得归属/租约 → 实际监听 → 报告 ready。中途失败只清理本次取得的资源；不能提前显示运行成功。

把“端口占用、配置错误、身份冲突、密钥缺失”等不会自行解决的错误记为持久阻塞状态；让后台包装器以可识别的退出状态结束，并调整 launchd 的重启条件，阻止这类错误快速反复拉起。暂时网络故障保留有上限、带退避的重试。修复后通过显式 `service start/restart` 重新核验，不能只删除错误记录。

保留 `service stop` 的停止并禁用自动启动语义。已停止的服务升级后仍停止；安装不启动；故障时 `status/stop/uninstall` 均可用。`service status` 区分已安装、已加载、进程存在、业务就绪和启动阻塞，避免“有 PID 就算正常”。

主要修改：`service.mjs`、服务包装器、`github-webhook.mjs`、CLI 和 `background-service.md`。

## 7. M3：专用账号按仓库读取通知

将每项目读取全账号 `/notifications` 后过滤，改为读取 `/repos/{owner}/{repo}/notifications`。该接口由 GitHub 官方提供；本项目使用的账号/权限要针对目标仓库探测，不把 App token 当成通知接口凭据。依据：[仓库通知接口](https://docs.github.com/en/rest/activity/notifications#list-repository-notifications-for-the-authenticated-user)。

- 同步修改 `github-account.mjs` 的 notifications 白名单、probe 和测试，只允许配置仓库的 GET；不能为改端点而放宽成任意 URL/任意仓库读取。
- 延续通知仅作线索、重读原文、授权检查、身份固定、关联反馈和不标记已读的行为；App 模式保留原轮询，不强制改认证。
- 根据对应接口的真实分页规则和响应链接判断结束，不复用错误页长假设。固定本轮时间范围，持久化未完成扫描窗口/续页，并对边界重叠去重；页数上限只限制单轮工作量，不通过无限重扫第一页或跳过尾部来“成功”。
- 游标升级保留原始启用时间、已处理边界、待重试线程和仓库观察流游标，不重新基线而丢掉升级期间消息。首次启用仍不重放历史；扫描窗口完整读完才推进完成水位。
- 保留 `X-Poll-Interval`，增加启动抖动和限流退避；在端点实际支持时采用条件请求，明确处理 304。收到限流后不当作空结果推进游标。
- 共享账号的 API 配额仍共享。优先减少无关读取和遵守限流，不承诺配额隔离，不新增中央通知抓取进程。当前逐请求固定 token/身份核验先保留，缓存优化不属于本轮必要改动。
- 来源状态显示当前仓库、扫描进度、待重试数及下次允许轮询时间；错误不包含 token。

定向检查覆盖两个仓库共用账号、分页超过单轮预算、读取中断与重启、同时间戳边界、限流和旧游标迁移。更换账号或仓库仍需显式重置对应发现身份，不能自动承接不同身份游标。

## 8. M4：复制与搬迁

提供明确的两条路径，以下命令为拟议接口：

| 用户意图 | 操作 | 数据处理 |
| --- | --- | --- |
| 复制代码后建立另一个项目 | `project reinitialize --as-new --plan/--apply` | 新 projectId/instanceId；旧本地状态先归档；不继承任务、会话、服务或有效租约 |
| 保留同一项目历史、换目录 | `project relocate --from <原路径> --plan/--apply` | 保留 projectId/instanceId、工单和收据；核对迁移归属与可迁移路径 |

普通 `init` 对新空目录的行为保持简单；发现已有复制状态时转入显式选择，不静默清库。只有受版本管理的配置、没有本地状态时，也区分“采用既有项目配置”与“建立新项目”，不沿用未知的后台授权。新实例只迁移允许的非秘密配置，GitHub 接单和后台默认关闭；凭据引用须单独核对，不复制秘密文件。

搬迁过程：生成变更清单 → 取得项目迁移维护锁并封住所有写入口 → 核对旧执行者/子进程已退出 → 一致备份配置与状态 → 更新已知宿主路径和登记 → 重建新位置服务定义 → 验证 → 保持停止。维护期间，平时允许并发的 submit/reply、配置写入和 Webhook 落盘也须暂停或明确拒绝，不能穿插到备份/搬迁中；只读查看保留。各步持久化进度，失败可继续或回滚；原目录缺失时必须有实例/备份证据，不能仅凭路径不存在接管。

不能全库字符串替换：分别处理 worktree 的 gitDir/commonDir、workspace owner、服务 manifest/label、日志路径、受管任务和凭据引用。超出项目的共享路径不移动；不自动修复未知 Git 结构，不删除旧目录。旧服务只按原 owner/label 精确卸载或禁用。

原生会话按能力处理：DSH 绑定 cwd、版本和模型，Codex 也有原生会话路径约束。不能证明可迁移时保留历史并标为需新会话接续，不伪造绑定或宣称无缝 resume。活跃/未知进程、预览、pending 输入和未知远端写入必须先核对；W18 不因搬迁被绕过。

主要修改：`config.mjs`、`runtime-migration`、`service.mjs`、`workspaces.mjs`、Harness 绑定检查和新的项目维护命令。

## 9. M5：可选本机总执行上限

保留每项目 `maxWorkers`，新增当前用户本机政策 `maxActiveExecutions`，默认不设上限，升级不改变既有吞吐。用户显式设置后，所有采用新协议的项目都参与；单个项目不能自行退出限制。

- Worker、协调者和受管子 Agent 的真实模型执行共用槽位；同一原生会话内部续作不重复计费，派生的并行执行必须另取槽位。
- 槽位不足时排队，来源读取、本地入队、只读状态和取消仍可用；等待超时不被记成模型执行失败。
- 采用简单的项目间轮转，项目内沿用现有优先级。长期占用/等待能被看到，不在本轮引入复杂全局调度器。
- 父执行等待子 Agent 时明确交接槽位，防止上限为 1 时父任务占位等子任务、子任务又永远等不到槽位。无法安全交接的并行调用返回明确的资源限制结果。
- 槽位仅在模型回合和所属活跃执行确实结束后释放；提问且执行已停可释放，恢复重新申请。崩溃后的子进程未核对前不能释放给另一任务。
- 预览服务、普通后台命令和模型账户费用不是同一种资源。继续沿用各项目现有租约/额度，展示数量但不宣称该上限能保证 CPU、内存、所有子进程数或服务商额度的全机硬限制。

拟议入口：`machine status`、`machine limits set --max-active-executions <n>`、`machine limits clear`，SDK 提供等价方法；`projects list` 展示登记项目、运行状态、仓库归属及等待原因。政策与槽位只放本机登记库，不写入任何项目的共享 Git 配置。

Codex 可继续共享当前用户的登录/全局设置，项目的线程/工单归属独立。全局登录和配置修改会影响使用者，在 doctor 显示共享来源；不为隔离而私自复制凭据或重写 CODEX_HOME。DSH 继续保持现有会话目录隔离。共用 CLI 可执行文件的升级可能同时影响多个项目，展示版本/路径；本轮不接管全局工具更新。

## 10. 升级、回退与公开接口

1. 保留已有 CLI 命令、SDK 工单方法、配置字段和项目服务 label 算法。新增字段可选；实例标记、登记协议和来源游标分别带版本，不能把可共享的项目配置与本地身份混为一体。
2. 初始化、升级与搬迁生成可审阅清单。现有 schema 9 只读查询不升级；新执行语义通过现有最低写入版本/迁移机制保护，具体 schema 号在实现时确定。
3. 旧版本不会遵守新协调协议。启用保护前盘点已安装和正在运行的旧服务、前台执行与受管子进程；先停止旧写者，再备份和纳管。数据库版本门槛不声称能中止已经运行的旧进程。
4. 多版本包共用登记库须协商协议兼容范围；未知新语义拒绝抢占或重置登记。旧/损坏登记的修复先生成计划，不能把其他项目活动记录一并清空。
5. 运行中的仓库/端口配置变更走停派工、等待、更新、重检流程，避免内存旧配置与新归属不同步。公开 SDK 也执行相同约束。
6. 迁移备份覆盖项目状态和本项目登记变更；回退只处理所属记录，不整体回滚共享登记库。只有停止新写者并核对原生执行/远端动作后才允许恢复旧版本。
7. 更新 README 的项目级定位、安装/多项目用法、后台、专用账号、工作区和迁移说明；明确新命令何时可用。实际实现前，本文件的接口均为拟议。

## 11. 有限验收与交付门槛

默认只使用两个临时项目、临时登记库、可控短子进程、假的 launchctl/模型/GitHub 传输和本地短时监听器。不启动主仓库后台，不调用付费模型，不创建真实 Issue/PR，不做开机重启或长时间压力测试。

| 检查组 | 最小场景 |
| --- | --- |
| 身份与执行权 | 同名不同目录、符号链接别名、同根目录 CLI/SDK 并发、复制配置/复制全状态 |
| 租约恢复 | 原进程死亡后接续、PID 重用、活进程心跳过期不抢占、旧 token 不释放新 owner、子进程遗留 |
| GitHub 归属 | 不同仓库并行、同仓库跨 App/账号冲突、Webhook+轮询同实例去重、停止不释放持久归属 |
| 端口/服务 | 自动端口持久、显式冲突、预检后被占用、永久失败不循环、停止一个项目不影响另一个 |
| 通知接续 | 每项目只读自己的仓库、超页预算续扫、失败重试、限流与旧游标迁移 |
| 搬迁 | 新实例不继承任务、原实例保留历史、过程打断后继续/回退、原生会话不能迁移时明确降级 |
| 总执行量 | 两项目遵守上限、等待可取消、父子任务不死锁、重启后核对旧槽位 |
| 兼容 | CLI/SDK 本地工单入口、Codex/DSH 适配器合同、旧库只读、旧写者升级门槛 |

按阶段运行相关测试文件和类型检查；仅当变更影响已验证模块时追加必要回归，不反复跑全套。仓库要求的 `npm run check` 继续执行；资料变更按项目规则刷新索引。现有退役 `driver: codex` 的历史测试失败单独记录，需要触及的用例才更新，不为“全绿”掩盖迁移约束。

交付时记录实现版本、每阶段状态、实际运行过的检查、仍未验证的系统级行为和支持边界。模拟通过不能写成真实开机/模型验收通过。真实双项目后台验收留到用户明确允许运行时，以两个隔离项目做短验收，不自动启用主仓库。

本轮实施不自动包含提交推送、npm 发布、生产升级、账号切换、GitHub App 权限修改或后台启用。主仓库后台当前已安装但未加载、未运行；计划制定及后续实现期间继续保持停止。
