# 实施路线

目标：从 npm 安装后，在没有 DSH、没有 GitHub 账号的普通项目中建立持续工作闭环，并允许替换 Agent 执行端。

## 阶段进展

| 阶段 | 当前结果 | 完成边界 |
|---|---|---|
| 1. 领域内核提取 | 固定上游提交，原样提取 `src/core/`、Engine 与状态测试，保留 MIT 许可和校验值；提供独立 `/core` 入口 | 不包括上游宿主、具体 Policy 或真实执行器，见[提取记录](core-extraction.md) |
| 2. 独立存储与运行时 | CLI/SDK 已接 Engine；领域仓库、持久化动作与本地收据、SDK 调度、取消、恢复和 v1 工单迁移接通 | 本地可信操作者、原目录串行执行；Driver 仍由宿主注入，见[迁移记录](runtime-migration.md) |
| 3. 真实非 DSH 执行闭环 | Codex CLI 接入、结构化报告、会话持久化与恢复、进程监督、CLI run/serve；真实 Python 修改和验证、提问回复、取消与中断后恢复 | 完成真实 Worker 验收；本地接单仍为确定性策略，语义 Assessor 尚未实现，见[执行端记录](codex-driver.md) |
| 4. 执行端配置与项目工作区 | 执行端持久化设置与调用覆盖；Git worktree、普通目录副本和自动选择；工作区复用、身份校验与变更审阅 | 保留原入口和原地默认行为；两个项目各通过真实修改／验证／恢复与第二工单隔离，见[工作区记录](workspaces.md) |
| 5a. GitHub Issue 渠道 | 原生 `gh` 轮询、明确命令接单、用户允许名单、关联反馈、问题与结果评论回传、持久化去重与发送重试 | 从安装包跑通真实 Issue 与 Codex 三轮执行，复用工单／会话／工作区；本地 CLI/SDK 保留，见 [GitHub 渠道与验收](github-channel.md) |
| 5b. PR 审阅与 CI 续作 | 同仓库 PR 当前提交显式关联、允许账号的审阅／行内／会话反馈、显式 CI 来源政策、原工单续作与双话题结果回传；原始 CI 保留机器人身份 | 安装包、过期反馈回归及真实三轮 Codex／PR／Actions 转绿验收通过；关联不自动 checkout、fetch、push 或 merge，见 [PR／CI 记录](github-pr-ci.md) |
| 5c. GitHub App 与 Webhook | App installation 认证、签名 HTTP 接收、持久化交付去重／恢复、原 REST 渠道重新核对、CLI／SDK 监听和本机注册入口 | 本地回归及真实 App／Webhook 验收通过：两轮 Codex 同工单续作、App Bot 回传、官方重投和重启去重；保留原有轮询，见 [App／Webhook 记录](github-app-webhook.md) |
| 5d. 后台运行与重启恢复 | 新增 macOS launchd 用户服务管理入口，默认轮询、可选 Webhook，保留本地 CLI/SDK 与前台入口 | 真实 App 后台轮询三轮执行、停止补收、空闲／执行中进程崩溃拉起及显式重试恢复验收通过。未实测整机重启／重新登录，固定 HTTPS 未配置，见[后台服务](background-service.md)及[验收记录](phase5-background-acceptance.json) |

现有命令和公开工单视图保留；GitHub 配置可选，CI 默认关闭，HTTP 监听与后台服务均须显式启动，禁用外部渠道后仍可本地使用。5a、5b、5c、5d 的真实验收证据分别保留，不以替身测试替代。5c 使用临时公网隧道完成验收，长期 HTTPS 入口仍需另行配置；5d 已用轮询验证后台持续运行和进程恢复，不要求入站网络。待处理工作自动恢复，执行中断仍须核查后显式重试。阶段 6–12 的新增结果见下表；自动采纳与工作区自动清理仍未开启；目录隔离及凭据排除不代表完整生产环境保障。

## 阶段 6–12 的实现

已经接通独立收件、版本化报告与暂停、真实协调器、受控验证与草稿 PR 交付、多 Worker、原生实时输入、后台任务／子 Agent、本地管理面板，以及可选仓库级 GitHub Source。默认仍是单 Worker、明确接单、本地交付；高级能力按配置启用。

使用方式见 [运行时 v2](runtime-v2.md)，逐项实现、真实验收和未验证边界见 [实施状态](implementation-status.md)。[原计划](implementation-plan.md) 保留完整门槛，不能用模块测试替代渠道或部署实测。飞书按用户决定暂不配置；固定 HTTPS、整机重启和 npm 发布仍未执行。

阶段 13–18 的待实施范围见 [上游对齐与持续运行实施计划](alignment-plan.md)：当前基线补验 → 模型业务工具与上下文 → 跨轮次任务和子任务成果 → 恢复与业务健康 → 管理追溯和提示词 → 最终同包验收与部署。阶段 6–12 的主干实现不代表这些剩余子项已经完成。

每阶段保留行为测试与实际验收证据。测试和示例中的 Driver、Assessor 替身不作为真实 Agent 或真实消息渠道的完成证据。

## 首个真实闭环的验收场景

1. 从本地 tarball 安装，在没有 DSH 和 GitHub 账号的环境中运行。
2. 在没有 Git 或 `package.json` 的 Python 项目初始化并提交明确任务。
3. 使用真实非 DSH Driver 完成修改并执行项目验证。
4. 运行中追加要求，检查保存、投递及处理记录。
5. 中断并重启，核对外部操作后继续，保留完整工作事实。
6. 返回可检查的文件变更、验证结果和未完成项。
7. 同时运行两个项目，确认任务、工作目录、环境与身份不串用。

## 暂缓范围

集中管理多个项目、分布式执行和远程数据库仍为独立扩展。实时会话输入、Worker 后台工具和子 Agent 已有独立真实模型证据，具体支持条件见阶段 9 记录。fork PR、MCP、其他 Driver 及更多系统安装器按需求选择，不作为本轮上游单项目对标的统一门槛。发布包、外部发送及自动合并分别依据用户的明确操作授权。
