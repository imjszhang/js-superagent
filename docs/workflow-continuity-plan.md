# W15–W23：持续工作与六组实际差距补齐计划

日期：2026-11-02（Asia/Shanghai）。状态：**已进入实施；W18 自动采用受当前公开 SDK 限制，未完成。实际结果见文末和[验收记录](workflow-continuity-acceptance.md)**。

接续 [W7–W14](workflow-reliability-plan.md) 及其[交付记录](workflow-reliability-delivery.md)。代码基线为已提交、推送的 `936a436a1405d90f374bf5c04e269336e9e197be`，包版本 `0.5.0-alpha.0`、schema 6；对照上游 `dsh-superagent-prototype` 的 `6337fc823ce20251c8de8085948165c81aaa701e`。本轮只对齐已确认的业务流程差距，不扩展成 DSH 能力搬迁。

本计划的完成标准是：局部 GitHub 故障不拖住健康工单；有充分证据的执行与消息可以接续；行内讨论能在原处完成反馈；执行者能补读授权范围内的 GitHub 上下文；已有工单能在后续轮次采用新规约；用户能看懂模型正在等待什么。

## 1. 固定边界

- js-superagent 自行维护授权、工单、渠道、存储、调度、工作区、工具收据、验证和交付。不依赖 js-agent-runtime，也不加载上游插件来运行业务。
- 保留现有 CLI/SDK、Codex app-server、DSH SDK 和实例级 Harness Registry。业务合同一致，原生差异由适配器处理；不恢复 Codex exec、DSH headless 或旧 Driver 注入。
- 原样领域内核保持不变；优先修改应用层和适配器。确需修改 core 时单独说明来源与原因，不改摘要掩盖差异。
- 生产后台保持停止；本轮计划及后续实施均不安装、启动、切换生产服务或迁移生产数据库。不自动升级 Codex/DSH，不改变默认执行端，不因查询、保存配置或重开数据库启动模型。
- 保留 GitHub 轮询、Webhook、App 和 gh 两种认证路径，本地 CLI/SDK 不依赖 GitHub 可用。
- 自动恢复继续服从现有显式开关、尝试次数和总期限。暂停、取消、结束、授权撤销和明确人工停止优先；升级不会批量唤醒历史失败工单。
- 不扩展 fork PR、任意动态子 Agent、通用技能/provider/联网平台、自动合并或多机运行；不安排飞书配置、固定公网 HTTPS 或生产重启验收。
- 计划阶段只形成文档；用户随后授权实施。提交、推送、发布和生产服务切换仍不包含在本轮实施中。

## 3. 共用数据和兼容约定

不新建调度器、消息平台或通用恢复框架。继续使用 Store 事务、Effects、Outbox、现有工具/任务 journal、输入记录和执行追溯。

| 增量记录 | 必须保留的身份与证据 |
| --- | --- |
| GitHub 对象同步状态 | repository、Issue/PR 身份、配置代次、最后成功观察、head、失败类别、重试时间；发现流游标和对象失败分开 |
| 回传目的地与结果 | message ID、ticket、PR 总讨论/行内根评论、发送顺序、marker、实际目标、终止或回退原因 |
| 恢复检查 | 原 run/session/assignment、检查代次、工具与任务收据引用、结果类型、尝试预算和共享期限 |
| 输入接续 | 稳定 input ID、原生 message ID、原投递 run、新采用 run、接收/消费证据；不覆盖旧回执 |
| 远端读取收据 | run/session/assignment、授权资源引用、head、页面/内容版本、预算、结果摘要和失效原因 |
| 业务规约 | 固定设置绑定、当前规约 revision/digest、实际应用轮次；旧执行快照保留 |
| 原生等待事实 | session/run、事件序号、原因、来源证据、已知次数/起点及终止状态；未知字段不编造 |

以上是逻辑字段约定，最终字段名在类型、CLI、SDK、HTTP 和面板中统一。公开 API 增量扩展，原工单状态不因新增等待原因而全面改名。

计划统一使用 **schema 7**：旧调度器若忽略按对象阻塞、输入采用或新版绑定，可能错误重试，因此不能仅添加可忽略 metadata。迁移保护应在 W15 的首次新语义写入前完成，W23 复核：

1. 先验证配置、期望修订、旧 owner/guardian 已停止，再使用既有维护锁、一致性备份和原子迁移。旧包明确拒绝读取新语义。
2. 查询/status 和 SDK 导入不升级生产库。旧库的对象同步证据初始为待核对，不把旧的整轮成功时间冒充每个对象的新鲜度。
3. 不重放旧评论、重发已完成回传、清空未知输入或替换原会话。旧 failed/recovery 记录按原有设置保留。
4. 适配器合同采用可选增量方法/字段，缺少能力时给出明确原因；不因内部版本变化无条件迫使全部现有会话换会话。
5. 迁移与回退仅用临时副本检查。回退使用升级备份并核对外部动作；不能让旧包强读 schema 7，也不能自动重放备份之后发生的动作。

## 4. W15：GitHub 按对象隔离故障

### 改动

1. 内置 `poll()` 返回结构化结果：成功对象及事件、对象级失败、仓库级失败、核对范围与配置代次。现有 SDK 注入渠道返回的事件数组，在边界兼容为旧式整轮结果；不静默推断其具备对象级核对能力。
2. 已跟踪 Issue/PR 和仓库发现流都按对象隔离。一个对象失败时保存其稳定身份、重试原因和时间，其他成功对象继续入库。能确定身份的损坏对象单独重试；无法确定身份的损坏页面不推进相应发现游标，不能悄悄跳过导致漏消息。
3. 成功事件、对应观察版本、游标和失败记录按可核对单元原子提交；延续已有事件版本去重。重开后只补失败范围，不能重复接单。
4. 将全局 `github:last-error` 执行门禁替换为按工单依赖判断。受影响对象只阻塞依赖它的工单；仓库身份不符、认证失效等仓库级失败仍阻塞该仓库。普通发现流失败不抹掉已验证对象的事实，但旧观察不能无限期充当有效证据。
5. 调度、恢复、输入交付和结果发送均使用同一对象状态检查。领取执行前确认相关对象已被有效核对；产生远端写入前继续执行现有最新 head/授权检查。成功核对 A 不得解除 B 的等待；旧 head 不能因其他对象同步成功而重新变成有效。门禁区分执行/新 POST 与只读对账/结算：目标异常不能同时阻止收据核对或已确认永久不可达的 dropped 收尾。
6. Webhook 按已有 selector/目标范围结算：仅已核对成功的 delivery 标记 processed；失败目标保持待处理。无明确目标的仓库事件需完成相应范围核对，不能因为部分成功把全部投递标记完成，也不能用一个 pending webhook 阻塞所有健康对象。
7. `githubStatus()` 和面板显示整体正常/部分异常/仓库不可用，以及受影响 Issue/PR、最近成功时间和下次重试。保留现有汇总字段用于兼容，不能再把局部展示错误用作全局执行门禁。

### 文件与完成条件

主要修改 `channels/github.mjs`、`channels/github-repository.mjs`、`sources.mjs`、`index.mjs` 的同步、Webhook 和工单门禁，以及类型/状态展示。

一个混合 fixture 证明：A 正常、B 暂时 404、C 数据异常时，A 入库并能继续，B/C 只阻塞自身；重开及修复后不重放 A；仓库认证失效仍全局等待；取消、旧 head、过期配置和分目标 Webhook 不能绕过检查。使用虚拟时间检查退避，不做长时间轮询。

## 5. W16：回传顺序、永久不可达与对账

### 改动

1. App 和 gh 请求路径保留可信 HTTP 状态及有限错误类别。仅明确的 410、已核实讨论锁定的 403 作为目标永久不可达；404、普通 403、认证变化及限流继续等待或重试，不靠自由文本猜测删除。
2. Outbox 增量接受成功收据或目标不可达结果。保留原 `{id,url}` 成功收据；明确不可达时使用现有 `dropped` 状态并保存原因、取消 effect，不修改领域 core。
3. 以 ticket + 目标讨论作为顺序范围。后续消息等待前一条 pending 消息；前项实际失败累计三次后可放行后项，并记录越序原因。纯等待不增加失败次数，不阻塞其他工单或讨论。
4. 保留稳定 message ID 和发送 marker。先核对远端已有评论再发送；远端已接受但本地响应丢失时复用同一动作，不能新建消息身份或重做 Worker。
5. 目的地和收据分离：记录计划目标、实际目标和终止原因，为 W19 行内回退提供依据。目标已失效不表示工单自动完成或授权扩大。

### 文件与完成条件

主要修改 `channels/github-app.mjs`、`channels/github.mjs`、`outbox.mjs`、必要的 `effects.mjs` 查询和通知展示。

用一组表驱动场景验证同讨论顺序、其他工单不受影响、连续失败后的放行、发送成功丢响应后不重复 POST，以及 410/锁定/404 分类。App 和 gh 使用同一结果合同，无远端写入验收。

## 6. W17：异常后只读核对与宿主工具收据联查

### 统一恢复入口

1. 已登记且已收尾的原生进程异常退出、连接丢失和可识别的原生暂时错误，进入统一的有界历史核对入口。连接错误只触发检查，**本身不是安全重跑证据**。
2. 检查必须在原执行 owner、guardian 和工具处理已收尾后进行，绑定原 run/session/assignment、工作区及固定执行设置；仍活跃时等待或报告原因，不同时启动第二个执行者。
3. 继续使用 `inspectRecovery()`，补充结构化结果与原因：已完成、可安全接续、存在已知 pending 输入、仍有活跃任务、证据不足/不支持。只有明确 completed/resume 证据能进入后续动作。
4. 自动检查和接续遵从 `autoResume`、现有次数与共享截止时间；手动 `retry` 复用同一检查合同。查询不调用模型，历史失败记录不在升级时自动排队。连续检查失败不能无限刷新预算。
5. completed 幂等收取报告和真实输入消费证据，继续宿主验证/交付对账，不能重跑 Worker。resume 复用原会话和工作区。权限、对象新鲜度、head、新人工要求及暂停/停止继续决定能否行动。

### 与宿主收据联查

1. 不再按“出现过动态工具/受管任务”整体拒绝。以当前 run 及其仍有影响的任务为边界，关联原生 call ID、宿主工具收据、任务 ID、配置与完成状态。
2. 按明确工具种类核对：只读调用有完整已完成收据即可复用；报告、输入确认等宿主幂等动作核对原动作收据；启动任务必须继续核对任务终态及结果，启动收据不等于任务已完成。
3. Codex 的已完成业务 `dynamicToolCall` 可经宿主收据证明；未知工具类型或未结算外部写入继续人工检查。DSH 的旧 run 已结束任务不再永久污染后续 run，但跨轮仍活跃或结果不明的任务继续阻止不安全恢复。
4. 对 `interrupted` 任务执行只读核对并给出明确结论，不能一直跳过且不解释。能够证明已结束才结算；不根据进程消失伪造成功。
5. 向适配器提供当前工单范围内的收据事实或受限查询回调，适配器不直接读业务 SQLite。原生工具结果缺失但宿主有结果时，除非公开协议能安全接回结果，否则继续人工检查，不补造原生 tool/result。
6. 旧记录缺少关联身份时保留检查状态；不能通过补造 call ID、修改原生日志或删除不确定收据来获得恢复资格。

### 文件与完成条件

主要修改 `index.mjs`、`runtime/recovery.mjs`、`runtime/agent-tools.mjs`、任务 journal 及两个适配器/history 解析器。扩展结果类型保持原有 completed/resume 证据可读。

小型 fixture 覆盖：通道丢失但原生已完成；安全中断；已完成只读宿主工具；旧 run 已结束任务；未知外部动作；owner 未收尾；停止/取消；预算耗尽。关键断言是“报告和外部动作不重复”，不比较提示词字符串来代替状态验证。

## 7. W18：采用 DSH 原生待处理队列

### 改动

1. 固定并只读核对当前支持的 DSH SDK 协议与日志格式，不自动升级。本机 rc.5 的 `session/resume` 会启动原生循环并可能立刻消费 pending inbox，**不能用它作为只读检查**。
2. W17 识别到 pending 后，核对队列中每一项的 message ID、input ID、内容摘要、原 run 和当前授权/版本。只允许完整可解释的本工单消息进入采用分支；混有未知消息、已撤销要求或已被更正的旧版本且无法精确移除时保持人工处理。
3. 调用会启动执行的 resume 之前，先持久化新 run 对原输入的采用映射、进程归属与恢复代次，安装事件监听和业务工具桥，再重查取消、授权和 head。不能在 resume 返回后才开始收集消费事件。
4. 采用原队列时不再发送原消息或重复初始任务。消费事实关联原 input 和原投递收据，同时记录本次采用 run；原生事件先到、RPC 回应后到时也不能把已读降级为未知。接收的最终结果必须晚于被采用输入的消费位置，旧最终报告不能吞掉 pending 要求；仅在证明队列已空且确需继续时才另发恢复说明。
5. 等待原队列消费有总期限，跨重开仍保留采用身份和预算。采用过程中再次中断时重新只读核对；没有确认消费不等于消息不存在，也不能改成盲目重发。
6. 不直接修改原生日志/队列，不要求 SDK 提供尚不存在的精确撤回 API。首期主路径是安全采用原队列；不满足条件的分支明确展示原因和现有人工检查/替换会话选项。
7. Codex 保留自己的原生消息/最终报告确认语义，不伪装成 DSH inbox。两个适配器向宿主报告相同的业务事实，但采用方式按真实能力声明。

### 完成条件

一个短 DSH 原生 SDK + 本地模拟 provider 脚本合并验证：消息已接收未消费时中断、同会话采用、消费事件早于 resume 返回、再次中断后的幂等核对。补一个取消/撤销导致拒绝采用的协议 fixture。原消息只消费一次，未消费不标已读，没有所属进程残留。未能以当前协议证明的分支列为未完成，不以接口存在代替实现。

## 8. W19：行内讨论上下文与原处回复

1. 保留 reviewCommentId、inReplyToId、核实的根评论 ID、原始/当前位置及有界 diff 片段。线程身份不依赖可变行号；旧 head 信息明确标为历史，不能作为当前修复授权。
2. 同线程父评论和必要相邻回复形成可读资源，为“这里也一样”等反馈提供背景。外部内容仍按数据处理，不从引用文字扩大工单权限。
3. 回传明确选择 PR 总讨论或已验证的行内根评论。行内端点限定为 `pulls/<n>/comments/<root>/replies`；同时精确扩展 GitHub App 请求白名单，保留仓库、PR、root 和 head 校验，不能开放任意 POST。
4. 原行内目标已不存在且父 PR 仍可访问时，回退总讨论并保存原因。权限丢失不冒充删除。发送不确定后先检查原目的地及可能的回退目的地 marker，不能先后重复回传。
5. 旧 pending 回传能从已验证的来源链接还原线程身份时才补齐；无法证明时保留原总讨论目的地。已发送收据和旧事件身份不重写。

主要修改 GitHub 规范化/读取/回传、`github-pull-intake.mjs`、App 白名单、必要 Outbox 目的地记录。一个线程 fixture 验证根评论与回复、原处回传、删除后回退、错误 root/外仓拒绝和丢响应去重。

## 9. W20：Worker 受控异步 GitHub 补读

1. 扩展现有 `js_superagent_read`，由宿主列出可读引用：工单来源 Issue、绑定 PR、已授权订阅讨论的正文、评论、审阅线程和 CI。不给模型任意 URL、仓库、API 端点或凭据入口。
2. Codex/DSH 复用宿主读取服务和现有工具桥；请求使用宿主 GitHub 认证，不依赖 Worker shell 中的 gh 登录，不增加通用浏览器或联网工具。
3. 当前工具调用是同步事务合同，需明确拆成三个步骤：事务内检查身份并预留读取预算 → 事务外限时 GET → 事务内重新核对 run/session/assignment、授权、配置代次和 head 后保存结果。保留现有本地同步工具路径，不把网络等待塞进 Store 事务。
4. 读预算沿用已有分页、总字节、总次数和期限。响应带对象版本、观察时间/head及内容摘要；分页中版本改变返回过期提示，不拼接多版本内容。旧缓存每次使用仍检查当前可见范围。
5. 取消、会话替换或授权撤销后丢弃迟到结果，释放并发占用与未用预留；已发生的请求次数、耗时和字节仍累计，不能通过取消/重试刷新总预算。只读请求可安全重取，但不能把旧 run 的返回交给新 run。
6. 读结果与工具收据进入 W17 的联查路径。补读只提供事实，不自动生成新的任务授权、CI 修复请求、推送或合并许可。

主要修改 `runtime/agent-tools.mjs`、source/context 读取服务、GitHub 资源适配、两个工具桥和类型。少量 fixture 验证授权引用、分页变化、取消、超预算及重开收据；两执行端各验证一次桥接合同，合入其原生短脚本。

## 10. W21：已有工单在后续轮次采用团队规约

### 分离固定设置与业务规约

1. 模型、工具、权限、工作区和基础执行约束继续固定。沟通、交付、汇报等团队业务规约独立版本化，不再永久混入静态执行绑定。
2. 新发布的业务规约默认在下一次正常业务轮次应用，不中断当前轮次，不因保存规约主动唤醒 Worker。记录 desired/applied revision、应用时间和运行快照；更新或回滚均形成明确修订。
3. 旧 run 的恢复检查和 completed 报告使用原来的规约/绑定；不能拿新规约重解释已经发生的结果。真正开始后续新轮次时再采用最新规约；DSH 原队列恢复不得插队混入一条未经记录的更新。
4. 复用现有 `configurePrompts()`、`prompts set` 和面板。规约已选择、已被原生接收、已用于该轮分别记录；业务规约不改变 Mandate 或工具权限。子 Worker 采用启动时父任务的规约快照，运行中的子任务不随全局保存而改变。

### 两个适配器的实施主路径

- Codex：当前本机公开 `ThreadResumeParams` 支持 `developerInstructions`，而当前适配器每 run 重建 app-server 并 resume 原 thread。下一轮 resume 传入固定宿主约束与当前业务规约，保留 threadId；以实际模型请求验证旧规约被替换，不能只验证请求参数被接受。
- DSH：现有 `options.prompt` 被装入当轮 `session/prompt` 的用户任务文本。拆开基础文本与团队规约后，注入带 revision 和明确替代关系的当轮业务规约；保留原会话，不引入第二套插件业务循环，也不要求原生系统提示词热更新。
- 原生协议细节仅留在适配器。宿主记录实际应用证据，未知能力不显示“已应用”。不通过普通低优先级追加消息冒充对已有更高优先级约束的替换。

### 旧数据处理

现有 `executionConfig.prompt` 参与 Codex recovery signature 和 DSH prompt digest，不能直接覆盖。保留原始快照、`promptAssembly` 和摘要；只有能用历史 assembly 与精确拼接规则还原并匹配原摘要时，才建立固定基础文本 + 业务规约的 v2 绑定。旧 run 仍使用旧签名；新 run 使用新绑定与独立规约版本。

缺少历史 assembly、摘要不匹配或用户自定义文本无法明确分离时标为 `legacy-unresolved`，保留原会话和旧设置，说明需要明确迁移/替换；不能靠字符串猜测拆分，也不能把这类旧会话计为已支持自动规约更新。

主要修改 `runtime/prompt-registry.mjs`、运行配置/绑定装配、两个适配器、CLI/SDK 与提示词面板。各执行端的短原生脚本合并一次旧/新规约切换断言；另用 fixture 检查精确旧记录迁移、并发修订、回滚及旧 run 恢复仍使用原版本。

## 11. W22：展示原生模型等待原因

1. 适配器把可观察的等待事件投影为业务事实：原因、供应商、已知尝试次数、起始时间和最近事件。优先结构化协议；必须解析兼容格式时限定版本及已知字段，不根据普通日志或模型正文猜测。
2. 预算耗尽与限流、认证错误、普通重试区分。执行端未暴露预算信息时显示“原生重试，原因未知”或“不提供该信息”；不把所有 429 都归为预算耗尽。
3. 以 run/session 和事件序号处理重复/乱序；开始新轮次、恢复响应、完成、失败、取消和替换会话时清理或结束旧等待。重开只能恢复历史观察，需当前执行身份或核对才显示当前仍在等待，不能用当前时间冒充原起点。服务停止按停止收尾，不能显示成模型预算已恢复。
4. 健康汇总与工单详情展示“进程仍在，但正在等待模型”及已知原因。等待不会自动改成成功、改变模型、提高预算、延长期限或开启新重试政策。
5. CLI/SDK/管理接口提供增量字段，面板区分原生重试等待、宿主恢复退避和进程失联；没有原生证据时保留未知，不能把心跳正常等同于模型工作正常。复用本地 incident/acknowledge，不自动对外发送告警。
6. DSH 使用固定版本已知的 `llm/retry` 等事件；Codex 使用带 thread/turn 身份和 `willRetry` 的原生错误通知。账户级限额不直接当成某张工单正在等待的证据。

主要修改两个适配器的事件投影、`runtime/business-health.mjs`、执行追溯、状态接口及面板。一组事件重放 fixture 覆盖 DSH 预算等待、Codex 可见重试、未知原因、重复/乱序和结束清理；只检查新增展示，不重跑完整浏览器套件。

## 14. 实施结果与协议限制

W17 已接入原生历史和宿主收据联查：Codex 已完成动态工具有完整匹配收据时可核对；DSH 按实际消费消息定位各 run，已结束的旧任务不再整体阻断。宿主任务、进程、采纳和外部操作未结算时继续拒绝；查询过程不补造原生结果。正常退出、已完成结果和故障接续分别保留证据，连接丢失本身不代表可以重跑。

**W18 的只读识别与安全拒绝已实现，自动采用原队列未完成。** 实际运行 `0.2.1-rc.5` 发现，`session/resume` 恢复已有 inbox 后不会自动唤醒该队列，`session/wait` 可立即返回空闲；随后正常关闭会取消未处理队列。该版本公开 API 只有携带新消息的 `send`、`followup`、`steer`，没有无消息唤醒入口。具体实现中的 `wakeDriver` 被声明为私有方法。本包不调用它、不发送空提示、不重排队列、不改写原生日志。

当前 DSH 核对结果因此返回 `native-pending-wakeup-unsupported`，包含原输入身份和消息摘要的只读事实，且 `safeToResume: false`。执行端在启动任何恢复进程前拒绝 `adoption`，原 pending 保持未消费。通用采用合同及原始输入因果映射保留，但不据此宣称当前 SDK 支持自动采用。需要上游公开、可验证的无重复唤醒能力后，再补实际采用和再次中断验收。

W21 的 Codex 原定路径也经实际协议校正：`thread/resume.developerInstructions` 虽被公开 schema 接受，却未替换本次模型请求中的旧规约。实现改用公开 `turn/start.collaborationMode.settings.developer_instructions`，保留原生返回的 mode、model、reasoning effort；实际请求已确认当前高优先级项含新规约。DSH 通过健康会话下一正常轮的任务文本应用新规约。两者均保留旧配置摘要供历史核对。

两个真实 CLI 加本地模拟 provider 的短脚本已通过，覆盖范围和明确未完成项见[验收记录](workflow-continuity-acceptance.md)。等待原因分类采用限定原生事件 fixture；本轮没有制造真实账户限流或预算耗尽。不能将此次结果表述为 W15–W23 全部完成，亦不代表真实外网模型、生产后台或 GitHub 远端端到端验收。
