## 已有 Worker 按原问题回传

授权人在另一个讨论中明确关联已有工单后，原 Worker 可以回答该条问题，由宿主回到原讨论发送答案，不需要结束原任务。例如 Issue #1 的工单收到 Issue #2 的问题，Worker 使用 #2 对应的原始 `triggerId`，答案回到 #2；原任务仍可保持 waiting。

通用 v2 报告新增可选 `answers: string`，值为已交给该工单的原问题 `triggerId`；`summary` 是要发送的完整答案。`progress` 和 `waiting` 可以携带答案，不能同时提出非空 `attention` 问题。省略 `answers` 保持原有报告行为。业务工具 `js_superagent_report` 也支持该字段；Codex/DSH 的最终报告、工具结果及原生历史恢复保留同一答案标识，工具报告与最终报告标识不一致时拒绝收取。

宿主核对当前工单与执行归属、初始委派或实际交付的原输入、真人身份、来源修订和当前授权。支持在后续轮次回答此前已读问题；启用有界上下文的 Worker 必须有完整原文读取证据。纯旁观上下文、其他工单的输入、已退回协调器的请求和撤回的输入不能作为答复目标。模型只能给出原问题标识，不能指定任意收件人或扩大仓库范围。

PR 答案保持已有执行边界：必须仍关联当前工单及许可的提交版本，解除关联后不能用已读的旧问题重新排队回传。普通评论回到 PR 讨论，行内评论保留原审阅线程；答案标识不授予未绑定 PR 的执行权。

答案与领域报告、持久回传记录在同一事务内保存；同一工单对同一原始问题只创建一份答案。后续报告或重放不能改写已入队答案，也不会重复排队。多个负责工单对同一问题给出相同答案时，复用首次回传并保留它的来源证明。发送前再次核验来源和权限，失效时撤回新的外部写入；结果未知时沿用已有回传标记进行只读对账。暂停、重启和暂时发送失败不要求 Worker 重做任务。相关实现见 [Worker 答案核验](../src/runtime/worker-answers.mjs)、[报告协议](../src/runtime/reports.mjs)及 [Worker 回传测试](../test/worker-answers.test.mjs)。

## PR 明确重关联后的反馈补投

PR 从 head A 变为 B 时，负责工单仍固定在 A。B 上的授权真人反馈可以先到达旁观工单，但宿主为未收到它的负责工单另存待补投记录；旁观者的收据不再永久挡住负责人的投递。

操作者核对工作区与新 head 后，仍须明确重新关联。**关联本身不回放缓存消息**；下一次 GitHub 同步重新读取原事件，确认当前 PR 版本、评论修订、作者、授权与工单状态后，才补投给此前漏收的负责人。后台同步和手动同步使用同一路径：

```bash
js-superagent --project /absolute/project github link <ticket-id> <pull-number>
js-superagent --project /absolute/project github sync
```

这条补投只处理已记录的授权真人讨论反馈，包括普通 PR 评论、审阅及行内评论。不会自动采用更新的 head，不会把 CI 或 bot 观察转为真人请求，也不会重新分发给历史旁观者或后来加入的旁观者。原反馈已到达、来源修订失效、人工取消、退回输入或解除关联时，不再补投；重复同步和重启使用同一负责人工单的持久收据去重。实现与场景见 [补投记录](../src/runtime/pull-feedback-redelivery.mjs)和 [PR 补投测试](../test/pr-feedback-redelivery.test.mjs)。

持久补投证明从 0.12 新收取的受阻事件开始记录。0.11 的历史收据缺少稳定的原负责工单关联代次，升级不会推断归属并自动回放；这类旧漏投需核对后在原讨论补充新回复。CI 继续使用既有当前提交同步路径。

## 升级与部署

schema 12 → 13 声明最低写入版本 `0.12.0-alpha.0`，用于区分新的 Worker 答案发送及按负责人工单补投语义。升级前停止项目服务、前台执行和受管子任务，再用新版 `js-superagent --project /absolute/project upgrade` 核验、备份并迁移。旧写者不能继续写入 schema 13；不要混用新旧运行时。升级保留项目身份、工单和既有会话绑定，不自动启动后台。
