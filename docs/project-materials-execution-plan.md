# 项目材料与执行环境：实施计划

日期：2026-11-11（Asia/Shanghai）。状态：**用户已确认实施，代码与兼容性验证进行中**。

本计划接续已讨论的项目材料、工作区、验证与恢复方案。用户已审阅本计划并明确要求实施。各阶段先通过相应检查，再推进发布与项目切换。

## 1. 目标与设计依据

让一张工单能够读取任务真正需要的材料，并在合适的环境中执行。材料来源与执行目录分开表达；协调者转交原始请求，Worker 判断技术步骤，宿主检查授权并落实环境。

本版必须验证五个完整场景：

1. 调查当前项目，包括允许范围内的未提交文件和业务回执。
2. 调查指定提交或已经冻结的材料。
3. 基于当前材料，在隔离目录中修改，准确区分用户原有修改与 Worker 增量。
4. 在合适环境中运行验证，并交付可核对的结果。
5. 联合调查多个显式配置的项目材料，保持工单归属与输出边界。

对齐上游 [设计原则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/000-philosophy.md)、[领域模型](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/001-domain.md)和[执行说明](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/003-execution.md)：扩展既有工单执行属性和 Executor 准备能力，不新增 ExecutionPlan 领域实体、独立规划调度器或另一套工单状态机。材料入口不是事件 Source，不引入新的 Source/Thread/Trigger 语义。

本计划不恢复已撤销的 [DSH 通用能力扩展计划](dsh-capabilities-recovery-plan.md)。不顺带建设通用沙箱、跨项目中央后台、自动合并平台或长期任务调度平台。

## 2. 当前基线与实际缺口

| 组件 | 检查基线 | 相关现状 |
| --- | --- | --- |
| js-superagent | 0.14.0-alpha.4 / state schema 14 | 有工单、工具桥接、工作区、验证、交付、会话绑定和恢复；缺少受控本地材料 provider |
| js-longrun | 0.1.0-alpha.2 | 冻结回合输入，绑定 task/run/ticket；适配器尚未传递本次材料合同 |
| js-superagent-skill | 0.5.3 | knowledge 包装入口精确接受 alpha.1–alpha.4 / schema 14 |
| 执行器 | 使用项目已有准确配置 | js-superagent 可直接调用原生执行器，不以 js-agent-runtime 为必经层 |

实施不能忽略的现有约束：

- `auto` 在 Git 仓库根选择 worktree，内容来自提交；执行目录并不代表当前源项目文件。
- `agent-tools.mjs` 已有授权、预算、分页、版本和持久回执；外部读取当前主要用于 GitHub。
- DSH 的 `read-only` 不自动限制全部可读路径；宿主验证命令使用真实宿主权限。
- 工作区后续 generation 当前仅支持特定 GitHub worktree 续作，不能直接套用于任意 copy 重准备。
- 现有 `replaceSession` 要求项目暂停；不能直接作为在线工单局部切换接口。
- 正常 waiting Assignment 不能调用失败 retry 来制造新的 Assignment。
- 现有 worktree 差异按 Git baseCommit 计算；导入未提交内容后会混入用户原有修改。
- `delivery.mode=local` 交付清单与工作区信息，不自动把改动应用回源项目。
- longrun 已有 `executionProfile: local-worker@1`，不能复用该名称表达本次新语义。

| js-superagent 执行适配器 | 能力声明、工具装配、停稳及会话绑定 | 原生工具与受限工具模式分别声明，不夸大系统隔离 |

协调者不生成工作区技术方案、验证命令表或权限清单。建单仍保留原始请求；明确的人类限制可以原样转交，不能借路由摘要增加要求。

## 4. 本版固定的接口与行为合同

下述新增名称是本计划的接口草案，当前版本不可调用。M0 定稿后各组件按同一合同实现；不在消费端猜字段。

### 4.1 项目材料配置

新增 `getMaterialSettings()` / `configureMaterials(settings, { expectedRevision })`，使用版本化项目设置。配置通过公开 SDK/CLI 维护，knowledge 只提供导航。

一个材料入口包含：稳定逻辑 ID、来源项目身份、允许路径、排除路径、允许视图、允许读取的来源身份及输出目的地。项目根路径只能来自可信部署配置，不能由模型填入。

- 自身项目与额外项目分别配置；额外项目默认关闭。本机 registry 登记不等于访问授权。
- 来源检查使用 project/instance 身份与规范化根，搬迁或同路径换身份后旧引用失效。
- 路径规则限定为明确的相对文件/目录规则；必要的文件筛选使用小型、可测试的模式，不暗含完整 Gitignore/正则/命令语义。
- ignored 文件与其他文件一样按 allow/deny 处理；业务回执与凭据缓存分别配置。
- 读取者使用渠道自己的身份，不建立跨渠道身份映射体系。
- 不访问额外项目的工单数据库、会话、账号凭据或控制状态。

### 4.2 工单材料绑定

在宿主执行元数据中新增版本化材料绑定，记录配置 revision、来源身份、视图、授权依据和输出约束。公开提交入口可接受可信调用者提供的材料约束；旧调用省略时保持旧语义。

视图固定为三类：

| 视图 | 含义 | 恢复规则 |
| --- | --- | --- |
| current | 实时读取允许范围内的源文件 | 新一轮重新观察，不能用旧回执冒充当前状态 |
| commit | 已核验的固定提交 | 保持提交身份，不自动推进 HEAD |
| snapshot | 宿主或上层适配器冻结的材料 | 按快照引用读取，不回退到同名源文件 |

普通消息的来源与任务授权仍由现有准入流程处理。材料 grant 不能只依据 Worker 自报或协调者摘要产生；新增读取能力不自动授予写入、发布或新的来源权限。

### 4.3 Worker 材料读取

复用 `js_superagent_read`，增加 `materials` 资源，沿用 `references / prepare / validate / read` provider 合同。只接受宿主签发引用，提供：

- 来源状态：视图、观察时间、Git 提交和允许范围内的变更概况。
- 目录索引：分页子项、版本及后续引用。
- 文件正文：内容版本、分页位置及来源身份。

初始上下文分别说明执行目录和材料来源。根/子目录规则、技能文档和省略的工单历史也必须可达；关闭原生文件工具时，不再指示模型读取不可达的 manifest 路径。

路径处理拒绝越界、符号链接、非常规文件及超限内容；校验路径段、打开后的文件身份和读取期间变化。受控读取第一版拒绝链接数大于 1 的普通文件，固定材料由宿主保存为独立文件；明确记录这一限制，不能宣称实现操作系统级路径隔离或通用秘密识别。

Git 状态使用固定宿主调用，不开放模型填写 Git 命令。材料与 GitHub provider 共享既有 ContextLimits 和调用预算，不形成第二套额度。超限返回明确覆盖不足。

同一个 tool call ID 的结果是历史回执，重放时不得换成最新内容。更新材料必须使用新观察和新调用。文件分页变化拒绝混页，目录版本覆盖新增和删除。

### 4.4 执行器能力与整体限制

新增适配器能力声明，如 `boundedMaterialReadsVersion: 1`；内部有效执行配置区分原生工具访问与宿主受控读取，并进入既有执行摘要/会话绑定。

- 受控只读模式：只读、开启工具桥、关闭原生 fs/fs-search/shell/jobs 及其他可绕过入口。
- 普通编码模式：保持适用的原生工具；不宣称拥有受控只读模式的强制路径保证。
- 能力不支持时明确返回原因，不静默回落到更宽权限。
- 在任何 prepare 脚本之前解析有效约束，随后统一用于 Worker、子任务、验证、预览与交付。
- 子任务只能收窄父任务的约束；旧运行回调必须匹配当前执行代次。
- 验证继续区分可信宿主命令与执行器真实限制；不新增任意命令的系统级隔离承诺。

读取前及含材料输出发送前检查目的地。输出约束覆盖会话实际接触过的材料，不能靠删除入口清除旧会话的披露限制；覆盖报告、进展、提问、PR 和文件交付。固定、不含材料的接单回执继续走原通道。

### 4.5 工作区组合与初次选择

| 需求 | 本版处理 |
| --- | --- |
| 调查当前文件 | 保留工单独立目录，通过材料入口读取 current，无需切换工作区 |
| 调查固定提交/快照 | 从固定引用读取，不刷新源文件 |
| 基于当前未提交材料隔离修改 | 冻结允许范围后准备 copy；保存导入基线 |
| 基于提交修改 | 使用现有 worktree / 固定提交能力 |
| 允许的原目录修改 | 沿用已有明确配置与授权，不能因材料可读而自动启用 |
| 多项目联合调查 | 多个允许材料入口，工单仍归属一个主项目 |
| 多材料来源、单项目修改 | 额外材料只读，明确一个修改/交付目标 |
| 当前脏材料作为修改基线导入 worktree | 本版不支持该组合，该需求选择 copy；commit→worktree 保持支持，copy 不自动转换为 PR |
| 同一工单同时修改多个项目 | 本版不提供跨项目原子写入；需要分别授权、分别交付的独立工作 |

保留现有全局 `auto` 默认语义。新准备请求明确要求当前材料隔离修改时选择 copy；不能在遇到 Git 仓库时悄悄退回旧 HEAD。

### 4.6 Worker 请求重准备的实际流程

新增受控的工作区准备请求（建议工具名 `js_superagent_prepare_workspace`，SDK 使用同一校验入口）。参数只引用已授权材料、允许的准备方式、当前 provision/generation 与幂等身份，不接受任意路径、命令或新权限。

1. Worker 发现环境不满足原请求，提交具体准备需求。宿主先保存请求及原授权/绑定摘要，重复请求返回同一结果。
2. 当前执行到达受管交接边界，暂缓该工单的新输入派送；其他工单继续运行。不能在同一个活跃 native turn 中改变 cwd。
3. 核对旧 turn、子进程、jobs、预览、输入与交付；未知结果进入明确检查状态，不直接清理或重放。
4. 检查原工作区已有 Worker 增量。非空增量不能丢弃；先交付/保存或走明确的迁移决定，不在本版静默合并进新环境。
5. 准备新的工作区 generation，完成基线核验后，原子登记新 provision、会话 lineage 和有效配置；保留旧目录与会话记录。
6. 正常 waiting 的场景沿用同一 Ticket 和已有 Assignment，通过宿主事实输入开启新 run/new native session；只有原本满足 retry 条件时才建立新 Assignment。不得伪造 failed 或 host-restarted。
7. 新执行获得原始请求、已完成动作和重准备结果；旧代次的工具回调、验证和交付不能作用于新工作区。

准备请求受理后设置完成门禁：本 run 的普通 final、业务 report 和恢复报告都不能以 ready/dropped 结束工单，或触发自动验证、交付、结果通知。保留原报告用于审计，按宿主已保存的准备事实进入受管 waiting/交接；旧 run、所属进程与回调停稳后才切换 generation，并以准备操作身份幂等投递宿主 note。支持该受管交接协议的 Driver 才能暴露准备工具。用户停止或授权撤销优先取消准备意图，不继续准备，不伪造业务失败或宿主重启。

需新增可恢复的准备操作记录，但它只服务这项宿主操作，不成为新的领域计划状态机。现有 GitHub continuation 保持专用语义；抽取共享身份/停稳能力，不能伪造 GitHub 来源来准备 copy。

### 4.7 基线、验证和交付

记录 Git 基线、导入材料 manifest 和 Worker 增量。当前材料快照完成后进行整个纳入范围的复核；变化则有界重试或返回冲突，不能宣称获得混杂快照的一致性。

`inspectWorkspace`、验证和 `changes()` 对新材料工作区明确区分导入变化与 Worker 增量。验证绑定当前 generation、材料基线、验证 profile 版本和实际结果树。准备/验证产生的文件按声明范围记录，不能把它们默认为 Worker 业务成果。

本地结果先形成可审阅交付。新增显式本地应用操作：预览增量、检查源文件基线、取得目标写入保护、保存逐文件操作记录、应用并保存收据。支持新增/修改/删除及冲突检查；不默默跨项目应用，不承诺多文件跨系统原子事务。恢复按每个文件的 before/after 身份核对，出现第三种状态即冲突。

正式成果写入者由已有授权和项目适配器声明。longrun 拥有的成果禁用 superagent 直接回写；发布仍沿项目原有授权与流程。本版不把 copy 自动转换为 PR，也不把导入材料视为获准公开。

### 4.8 报告、时效和恢复

报告与本地证据保存实际来源、观察窗口、范围、遗漏、基线和验证结果。普通 final、业务工具 report、恢复采用的 native completed report 共用同一材料核验。

- current：检查已使用文件和目录版本；变化后有限补读，持续变化则明确未稳定部分。
- commit/snapshot：保持固定身份，恢复不更新材料。
- 验证已过期：保留历史结果，不能沿用为新树验证。
- 已完成外部动作：仅核对/补收，不能借刷新材料重放。
- 准备失败：恢复已保存准备操作，不新建替代工单。
- 输出失败：只重试 Outbox，不重跑 Worker。

沿用现有预算和恢复链，重准备/补读不刷新超时或恢复次数。错误至少区分格式、能力、授权、来源变化、准备冲突、输入/外部结果未知与交付冲突；每类返回可处理的下一步，不全部包装为 assessment_format。

## 5. 数据、兼容与升级

建议在当前 schema 14 基线上使用 schema 15 承载新语义，使旧写者明确拒绝新库，避免忽略材料约束后继续执行。M0 检查编号是否被其他工作占用；若已占用则顺延并同步所有消费者。

- 只读检查不迁移；显式升级在停止相关写者、取得维护权并完成一致备份后进行。
- 旧工单缺少材料元数据时保留旧行为，不自动获得本地/跨项目读取能力，不更换工作区或会话。
- 不自动恢复历史 failed 工单，不重放消息，不启用长期任务或额外项目入口。
- 新能力由公开 capability/合同版本判断，不能仅凭 npm semver 推断。
- 工单 ID、原始请求身份、Mandate、输入收据和通知收据保持。
- 新状态不能直接让旧包打开；回退前核对新版本期间的执行与外部动作。

| M6 时效与恢复收口 | `src/runtime/recovery.mjs`、报告检查、来源绑定、Outbox/交付发送门禁 | 所有报告路径检查来源；旧回执不变；输出目的地受检；原恢复预算保持 | M1、M2、M4、M5 |
| M7 longrun 适配 | longrun `src/superagent.mjs`、`src/core/runtime.mjs`、`src/types/common.mjs`、集成文档与测试 | 冻结合同贯通提交和结算；合法 generation 切换可验证；旧类型行为保持 | M0、M3、M6 |
| M8 skill 适配 | skill `references/`、`scripts/knowledge.mjs`、必要的 `inspect.mjs`、架构文档、版本和兼容测试 | 新旧包/状态兼容矩阵通过，公开配置部署，原 wrapper 与知识保留 | M0；最终验证依赖 M6、M7 |
| M9 包与真实验收 | 各仓包检查、独立消费者、隔离 DSH/飞书验收、发布与项目切换记录 | 五场景及升级/恢复证据齐全，精确发布包可复验 | M0–M8 |

M0 完成后，M1 provider 与 M3 基线/快照底层实现可依据同一合同并行；M3 集成验收等待 M1 的材料引用接口完成。M8 文档和兼容夹具可提前准备。共享 `index.mjs`、类型和恢复入口由一名集成负责人顺序合并。每阶段形成可检查提交，不将全部改动压成一次巨大提交。

## 7. longrun 的具体适配

1. `src/superagent.mjs` 的 submit 透传可信材料/执行约束，snapshot 返回实际材料身份、工作区 generation、准备基线和 Worker 增量。
2. `binding.json` 保留 task/run/ticket/definitionHash，增加不可变输入/输出/能力合同摘要。允许同一合同下的合法工作区 lineage，不能把首次 generation 永久钉死。
3. 新合同缺少工作区或材料证据时阻塞，不能使用旧 `workspacePath ?? root` 回退掩盖缺失。
4. collect 按冻结合同、Worker 增量、审核证据和原成果基线核验；通过后仍由 longrun 结算。
5. `local-worker@1` 继续冻结原文、禁止受管子任务并沿用原额度。跨项目材料由明确支持的业务适配器先冻结，不能自动给旧内置类型开放实时读取。
6. 上层取消/结算/invalid 状态与回合预算不能被下层普通恢复绕过。提交结果未知继续按原路径核对，不创建替代工单。
7. 新合同能力预检发生在写入本轮 draft、递增回合/额度和进入 submitting 之前；明确不支持时直接阻塞，不消耗一次已开始的回合。只有提交已发出且结果未知时，才进入现有 needs_attention 核对流程。

不创建长期任务，不新增 watcher/定时器，也不把普通调查强制包装成长运行回合。

## 8. skill 与项目部署适配

- 更新 `references/setup.md`、`operations.md`、`tasks.md`、`knowledge.md` 和组件架构说明。
- 材料、准备方式、验证和成果所有者都使用公开接口；知识 Markdown 只维护项目背景和导航。
- knowledge 兼容从单一 schema 断言改为经过测试的“准确包版本 → schema”映射，保留已支持旧版，不使用无限制 `>=`。
- 候选包先通过兼容矩阵，再加入支持列表；不能只扩大白名单。
- 保留原业务 wrapper、服务参数、知识文档与运行状态；Worker 不因接入材料而获得协调者专属知识。
- 公开夹具只用独立虚构项目；真实项目路径、账号、消息、正文、回执及验收数据留在目标项目。

## 9. 验证矩阵与停止条件

| 类别 | 必须通过的场景 |
| --- | --- |
| 材料正确性 | 修改/暂存/新增/允许 ignored 文件可见；固定提交与快照不漂移；删除和新增使目录观察失效 |
| 读取边界 | 未授权入口、伪造引用、路径穿越、软链接、非常规文件、读取中身份变化与大小超限被处理 |
| 回执与时效 | 同 call 重放结果不变；分页拒绝混页；新观察可读新版本；普通/恢复报告一致检查 |
| 工具能力 | host-only 不暴露绕过入口；原生编码模式正常；规则/技能/历史入口可读；provider 共享预算 |
| 工作区 | current→copy 保留允许材料；复制中变化被发现；dirty worktree 请求不静默降级；默认旧模式保持 |
| 切换竞态 | 活跃进程、未知输入、待交付、已有未保存增量时阻止切换；待准备时 ready/dropped 不提前完成；停止/撤权取消准备；其他工单不被暂停；旧回调失效 |
| 准备崩溃 | 保存意图后、目录创建后、绑定提交前后分别注入故障；恢复不重复创建、不丢旧目录/会话 |
| 增量与交付 | 用户原有修改不被误交付；验证过期拒绝；新增/修改/删除应用冲突；逐文件中断恢复不覆盖第三方新改动 |
| 跨项目与输出 | 注册不等于授权；换身份引用失效；私有来源不能发到未授权渠道；排队发送前撤权有效 |
| longrun | 冻结后源文件变化无影响；同合同重准备合法；未知提交不重复；越界/证据缺失阻塞；只有一个成果写入者 |
| 兼容升级 | 旧库显式迁移、旧工单不变、旧写者拒绝、新旧 skill 矩阵、单份运行库和公开导出可用 |
| 真实链路 | 隔离 DSH 验证五场景；飞书原请求→执行→恢复→结果，重复请求不重复开工；业务文件没有意外改动 |

发生未知外部结果、材料持续变化、权限/身份改变、能力不足或连续同类失败时，保留事实并返回具体检查原因；不无限补读、重准备或增加权限。

定向测试随阶段执行。集成收口运行现有检查入口：

```sh
# js-superagent
npm run check

# js-longrun
npm run check
npm run test:package

# js-superagent-skill
npm run check
```

真实模型/网络验证不混进默认单元测试。用候选 tarball 建立干净消费者，核对公开接口、单份运行库、升级、包装入口和完整组合。测试统计、真实执行与发布结果分别记录，不以服务健康代替业务验收。

## 10. 发布、同步与回滚顺序

此节在实现和候选验证通过后依次执行；账号验证仍按实际发布平台要求处理。

1. 合同/schema 冻结后确定候选版本；先构建 js-superagent 候选包，供 M7/M8 的 longrun 和 skill 适配及完整组合测试。
2. 完成 M0–M8 后，各仓分别提交并通过 CI；从最终准确提交构建发布包，核对与验证产物的一致性，最终产物变化时重新执行受影响的消费者检查。
3. 发布 js-superagent，核对 registry 可下载及 integrity；需要账号验证时交接该一步。
4. 发布完成适配的 js-longrun，按真实合同调整 peer；skill 通过 Git 版本交付，不发布 npm。
5. 从 registry 再建干净消费者复验后，才切换目标项目。
6. 记录目标项目原依赖、wrapper、配置、知识、身份、工单与服务状态；保留全部业务未提交内容。
7. 停止需要重载的相关服务，使用公开入口完成一致备份。先同步兼容新旧运行库的 skill，再安装准确版本，并在需要时显式迁移。
8. 配置目标项目实际材料范围、验证及交付归属；不顺带升级 js-agent-runtime、DSH 或其他业务依赖。
9. 按原状态恢复原入口，检查知识、身份、能力和旧工单。项目规则/技能入口变化按目标项目要求同步并检查。
10. 在明确授权的验收范围内，用 lark-cli 发送新调查请求并核对真实回复；恢复测试保持原工单，不能用直接 SDK run/retry 替代飞书链路。修改与冲突测试使用隔离夹具，不以真实业务成果作为破坏性测试材料。

回滚分三种：未迁移且无新执行可恢复准确依赖和配置；已迁移但无新副作用使用验证过的一致备份恢复；已有新执行/回写/外部消息时先核对收据，优先前向修复，不能简单恢复旧数据库造成重复执行。无法安全恢复时明确保留停止状态和原因。
