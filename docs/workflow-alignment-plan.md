# 对齐 dsh-superagent 工作流程的实施计划

日期：2026-11-02（Asia/Shanghai）。状态：**W0–W6 已实现并完成限定范围验收，已由 `f814f11` 提交推送，未部署**。基线：js-superagent `991b457 / 0.4.0-alpha.0`；对照公开 dsh-superagent-prototype `6337fc823ce20251c8de8085948165c81aaa701e`。实际结果、用法与保留差距见 [交付记录](workflow-alignment-delivery.md)。下文保留实施时的目标和约束；矩阵中的“已有能力”指实施前基线。当前后续计划为 [W7–W14 实际差距补齐](workflow-reliability-plan.md)。

本计划替代上一版“DSH 配置、受控工具与分级恢复计划”，其阶段 27–33 撤销。本轮使用 W0–W6 编号，只补齐 **接单 → 判断与分派 → 执行 → 接收反馈 → 持续跟进 → 交付与恢复**，不是补齐 DSH 的所有能力。

## 1. 目标与边界

把工作交给 js-superagent 后，它持续维护这件事：普通失败时收到人的补充可以继续；执行中接收反馈；超范围输入回到协调者；结果交回原讨论；短暂故障和重启不丢归属，也不盲目重复外部动作。

- js-superagent 独立运行，无 js-agent-runtime 依赖，不加载上游 dsh-superagent 插件来代管工单。工单、授权、渠道、工作区、调度和交付由本包负责。
- 保留 CLI/SDK 产品入口与 Codex、DSH 支持；先完成统一适配器，Codex 采用 app-server、DSH 采用 SDK 主路径。移除重复执行实现和旧 Driver 运行分支，仅保留必要的配置/历史记录迁移。此条取代此前“所有旧执行方式继续保留”的要求。
- 生产后台保持停止；制定计划和后续实现都不自动部署、迁移生产、切换默认执行端或启用常驻服务。
- 只安排直接相关的少量检查，不重复大规模测试或长时间观察。

**明确移出本轮：**通用 provider 扩展、模型/推理参数扩展、技能注册或快照平台、联网搜索平台、OAuth、任意插件安装、新 Harness、完整聊天产品、DSH 原生界面接管、自动合并、飞书实测。若具体工作流程被缺少工具阻塞，只补必需的最小调用，不顺带建设一类 DSH 能力。

## W0：先做好 Codex / DSH 适配器并清理旧实现（P0，前置）

**结果：**用户只选择 Codex 或 DSH，CLI/SDK 共用同一个运行时；以后新增 Harness 主要新增适配器，不在工单和渠道中增加品牌分支。本轮已完成实现与定向检查，见 [W0 交付记录](w0-adapter-consolidation.md)。

### 一套合同、两种实现

沿用现有实例级 Harness Registry 收敛，不另建注册框架。适配器边界覆盖配置校验、角色创建、执行、会话恢复、追加输入、取消、事件/结果规范化及进程归属。Worker/Child/Coordinator 共用各自适配器的原生连接和会话管理；角色权限、上下文和报告要求仍由 js-superagent 决定，不把协调者做成不受限 Worker。

| 产品选择 | 主连接方式 | 本轮处理 |
| --- | --- | --- |
| Codex | app-server | Worker、子任务与协调者统一走此适配器；替换仍走 exec 的协调路径 |
| DSH | SDK 协议 | Worker、子任务与协调者统一走此适配器；复用必要的薄业务工具桥 |
| 自定义 Harness | 同一公开适配器合同 | 保留扩展入口，给出最小示例；不继续维护绕过注册表的旧 Driver 路径 |

底层连接、原生 ID、协议事件和工具桥留在适配器内。宿主只处理业务事件与受限能力：会话恢复、运行中反馈及确认、所需业务工具/任务支持。不建立任意特性目录，不把所有原生事件提升为公共接口。未知结果、取消、已接收与已读取必须明确区分，不能为了统一接口伪造成功。

CLI/SDK 的 submit/run/reply/cancel 等工单操作保留。执行设置和扩展接口允许必要的明确迁移，不再承诺旧 Driver v1/v2 原样永久兼容。公开配置按 Codex/DSH 两个产品选项展示；内部原生会话标识不因改名而直接改写。

### 清理范围与迁移

1. 删除独立 Codex exec 与 DSH headless 执行路径、重复工厂/选项/导出及其专属示例；协调者同步迁移，不能只清理 Worker。实际删除前核对调用关系，保留主路径仍使用的进程监督等共享代码。
2. 删除运行时中旧 Driver 注入、旧结果转换和品牌分流的重复执行逻辑；自定义执行端只通过统一 Registry 接入。旧扩展提供迁移说明和明确错误，不隐式绕过新合同。
3. 旧配置 ID 在边界集中识别，不在核心散布兼容判断。已采用 app-server/SDK 的设置做可核对的等价迁移；exec/headless 转换属于连接方式变更，提供迁移预览、备份和显式应用，不能静默替换正在绑定的会话。
4. 历史工单、原生 ID、日志、交付收据及已完成结果保留可读。未完工旧会话只有证明能被新连接恢复才续接，否则标为需要显式替换；不把重新创建会话写成原生恢复。生产库本轮不迁移。
5. README、类型、配置界面和当前使用文档只介绍新入口；移除过时教程、废弃选项和只测试被删实现的用例，保留仍有价值的业务/迁移断言。历史验收材料归档标注，不能改写过去结果。被撤销的计划从现行导航移出，必要链接只保留短跳转。
6. 提交前按删除清单核对引用和包导出，不能仅将旧代码改名放进 legacy 目录继续维护。迁移兼容仅用于读取/转换旧数据，不成为第二套执行引擎。

**文件边界：**`src/harness/registry.mjs`、`src/drivers/*`、`coordinator.mjs`、运行时创建/结果入口、配置/类型/CLI/面板与相关文档示例。业务领域内核、渠道、存储职责不下沉到适配器；无 js-agent-runtime 依赖。

**完成条件：**Codex 和 DSH 都通过同一宿主入口完成执行、提问后续作和取消；相关会话绑定/恢复、协调角色及不支持能力有少量定向合同检查；一个最小自定义适配器可接入且不修改工单运行时。旧配置的等价迁移、需替换提示和历史记录读取各验证一例。不新增全平台或模型矩阵，真实执行并入 W6 的两条场景，不单独扩张验收规模。

## 3. W1：人的反馈能继续原工单（P0）

**结果：**普通失败或缺信息时，人在原Issue/PR或本地补充说明即可继续，不必先另做一次retry；CI/机器人消息保留，但不能单独解除失败。

1. 统一本地 `reply()`、Issue follow-up、PR review/comment：先去重、检查来源/授权并持久保存，再决定立即交付、排队或待人工处理。
2. 区分领域blocked、普通failed、interrupted、cancelled。保留旧公共状态字段，新增原因/允许动作，不因blocked被投影为failed就拒绝回复。
3. 原Mandate仍有效、旧执行已停止时，授权真人消息通过既有Engine解除普通失败/阻塞，保留工单、会话、工作区和PR。多条补充不产生并发重复执行。
4. bot/CI输入继续积压，未授权人不能唤醒。取消、撤权、未知外部结果、旧进程未退出保持阻断，并说明需要什么处理；任意评论不复活取消任务。
5. 修正 `local-retry-required` 去重处理，不能永久吞掉人的修复信息。历史已忽略消息不批量自动重放，使用已有重评/明确重试入口。

W1先补最小失败来源判定（如failureOrigin/requiresInspection）：当前业务报告、原生错误、宿主验证或交付错误都可能显示为failed，不能仅凭这个公共状态开放自动接续。区分可由补充说明解除的业务失败与需要检查的外部结果；无法辨别的旧记录保守提示检查。这是反馈判断必需的信息，不等待W4再补，也不扩大为故障分类平台。

**文件边界：**`src/index.mjs` 的本地/Issue/PR入口和状态投影、必要的渠道规范化与管理呈现。复用核心hold规则，不改原样领域内核。

**完成条件：**小型表驱动检查覆盖blocked/failed收真人回复后继续、bot只记录、多次回复去重，以及取消/不明中断保持阻断。

## 4. W2：协调者持续处理工作事件（P0）

**结果：**协调者能跟进需要重新路由的请求、工单报告与跨工单事实；人可以从现有产品入口询问项目进展。问题和结果仍及时交回原讨论。

### 收件与唤醒

在现有Store/Effects增加项目协调收件记录，复用协调会话和owner，不增加另一套常驻调度器。记录来源身份、关联trigger/eval/ticket/report、版本、处理状态和动作收据。

| 输入 | 行为 |
| --- | --- |
| candidate、handback形成的新candidate | 继续现有Assessor，引用同一eval，不另建一份决策 |
| 普通progress、已回传结果 | 更新上下文，默认不唤醒模型或重复通知人 |
| Worker提问 | 原渠道立即回传并等待回答；协调者获知事实，不替人回答或新建替代任务 |
| 需协调的blocked/failed报告、工单结束、订阅变化 | 持久记录；有路由/补充事实需求才调用模型，纯状态变化可合并为通知 |
| 已归属Worker的真人跟进 | Worker继续拥有输入；协调者不抢单，仅按明确停止意图走核心停止规则 |
| 操作员项目消息 | 绑定本地操作者；可查进展、要求已有授权内协调，或明确提出新工作 |

状态通知可合并，候选、问题和人类消息不能被合并丢失。事件重投/重启不重复执行动作；处理时读最新领域状态，提交动作时重查政策和事件版本。协调动作不能触发无限自我唤醒。

### 动作与人的入口

只开放已有Engine能力：候选decide/attach、note、requestStatus、合法reply，以及有明确人类依据的stop。新工作先成为本地Trigger经过准入；不能凭Worker报告自行扩出一个未经授权的任务。note只传事实，不能借跨工单信息扩大范围。

协调者不执行项目命令、不改机器配置、不替Worker验证/交付、不直接调用GitHub写API。答复走现有Outbox与渠道授权；已回传问题/结果只有一个发送归属。上游主会话能做的部署配置编辑不是本轮对齐目标。

保留 `assess(candidate)` 和原“仅候选”模式，新增可选工作事件处理合同。自定义协调实现通过 W0 的适配器合同接入；Codex与DSH分别用现有协议返回有限结构化动作，宿主执行，不依赖DSH原生主界面。新协调模式显式启用，旧配置不增加模型调用。

拟新增 CLI `coordinate <text>`、SDK `coordinate({text})` 与面板的“项目协调消息及记录”，只入队；显式run/serve才推进。`submit()`仍是直接委托工单。新收件参与运行循环空闲判断，但查询、入队、导入SDK、init、status均不启动服务或模型。

**文件边界：**`coordinator.mjs`、`index.mjs`、Effects/Store、Harness注册表、CLI/类型/面板；可抽出一个协调收件模块，不造通用工作流框架。

**完成条件：**handback→研判→正确路由；报告→一次note/requestStatus；重开后不重复动作；普通progress/已发送结果无重复模型调用或评论；连续协调复用已有原生会话。

## 5. W3：DSH执行中接收反馈（P1）

**结果：**追加要求后，用户能区分“待交付”“执行端已接收”“Worker已读取”；执行端允许时，Worker在下一步处理。

复用现有 `sendInput()`、`inputRead()` 和Codex app-server通道，只补DSH适配。先用固定rc.5核验运行中 `session/prompt`、messageId、`user/message` 与取消后的未读输入。入队回执不等于模型已读。

公开SDK能证明关联则直接接入；不足时只扩展已有companion plugin的工单消息桥接，不增加provider、技能、网页或跨会话通信能力。每个业务Input有稳定身份，断连后核对原生收据，不能盲目重发。只有实际消费证据匹配才标为已读；结束前未读的消息按核心规则进入下一轮或Eval，不能被ready吞掉。

现有通用inputRead只接受model-final-ack；DSH若用原生消费事件，应增量增加对应证据类型与适配器校验，保留Codex原合同，不把原生事件伪装成模型最终确认。能力声明、实际证据和界面状态必须一致。

反馈/取消/暂停/新Assignment竞争时核对owner与代次。沿用现有人的反馈优先调度；如满槽时仍无法接续人的请求，只修这一调度边界，不重造多Worker。

如果固定rc.5仍无法可靠支持，保留“下一轮处理”和capability=false，列为未对齐项；不得以新会话、重复prompt或自动升级CLI冒充实时输入。Codex原有实时能力不退化，已退出主路径的 headless 不再单独适配。

**文件边界：**`drivers/dsh.mjs`、`dsh-process.mjs`、现有薄插件与通用输入路径。

**完成条件：**一个受控长Worker收到一条反馈，界面状态与消费一致；取消/重开后未读消息只交一次；旧报告不覆盖新要求。采用真实rc.5+模拟provider检查，不做长时间负载测试。

## 6. W4：故障和重启后接着工作（P1）

**结果：**可恢复的短暂故障不会让已接单工作永久挂起；重启后知道该继续谁、哪些事必须先检查。

| 情况 | 最小处理 |
| --- | --- |
| 可确认未执行的启动失败 | 沿用启动前有限重试；第三方Registry Driver不因尚无guardian就自动认定安全 |
| 可识别的短暂模型/连接失败 | 原生自身重试结束后，按配置最多补三次恢复尝试；保留原会话，给恢复说明，不重复原用户任务 |
| 宿主意外退出时正在工作的Assignment | 确认旧owner/所属进程退出，核对会话、工作区、未读输入，再走核心assignmentInterrupted等已有路径，顺序排队 |
| 等人、ready、blocked/failed且无新输入 | 保留状态，不因重启启动Worker |
| 准备/验证失败、认证配置错误、无效协议结果、业务问题 | 等修复或人补充，不套网络自动重试 |
| 原命令/外部写入结果不明 | 查已有journal、原生记录、交付收据；无法确认则人工处理 |
| 人工取消、撤权、明确停服 | 不继续、不建唤醒器、不因查询复活 |

DSH只保留判定所需的错误类型、输入收据、原生事件位置和工具状态，不建设完整通用故障分类平台。没有可靠证据就人工恢复，不能只凭“429/5xx”或错误文本重跑。

恢复说明要求检查现有改动和交付状态；它是有来源的新恢复输入，不是再投一次原请求。结果不明的原生shell不能安全重放。恢复传输重复送达旧工具调用时只能复用原收据；新runId不能让同一已记录意图重新执行。

在现有恢复记录/Effects保存次数、下次时间和原失败关联，重启不清零。退避释放Worker槽位，到期遵守并发和人的反馈优先。原生与宿主重试共享总期限，不能叠成无限循环。恢复前重查授权、取消、暂停、新输入与归属；人工retry/replace使旧自动计划失效。

## 7. W5：关联PR正确结束和继续跟进（P0）

**结果：**原工单跟随正确PR，close/merge/reopen与后续要求不导致提前结束或永久错误阻断。
